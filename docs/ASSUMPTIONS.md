# Working Assumptions & Concerns

Code was started before the Debian 13 rootless prototype (TASKS 1.2) was run. This file lists what the code **assumes** that prototype will show, so each item can be checked on a real VM and the code adjusted.

Status: items are **unverified** unless marked. ✅ = verified on the Debian 13 dev VM (`scripts/dev-vm.sh`, Podman 5.4.2, 2026-09-26). ❌ = failed. ⚠️ = could force a redesign if wrong.

## N. Backup credentials that can't delete (SPEC §10.10, review H1)

Checked on the dev VM (2026-10-16) with restic 0.18.0 against a small fake S3 server (in-memory; it either refuses `DELETE` from the server's key with `AccessDenied`, or, like Backblaze, turns a delete by name into a hidden version). The controller's side ran from another hostname (`unshare --uts`), as it would on another server.

| # | Finding |
|---|---|
| N1 ✅ | **A credential that can't delete at all breaks restic.** `backup` exits 0 but can't remove its lock (`Remove(<lock/…>) failed`), and every lock refresh fails the same way; after about 22½ minutes restic tries a stale-lock refresh, fails, and stops the backup (`Fatal: unable to save snapshot: context canceled`, exit 1). The leftover locks then block anything that needs an exclusive lock: the server's `restic check` and the controller's `forget --prune` exit 11 ("already locked"), even once the locks are over 30 minutes old (restic doesn't skip stale locks when locking; only `restic unlock` removes them, and only stale ones). `check --no-lock` works. So no destination may hand a server a key without delete; append-only has to come from the storage keeping what's deleted (rest-server, Backblaze hiding, bucket versioning). |
| N2 ✅ | **Backblaze: a key with `writeFiles` but not `deleteFiles` can delete a file by name through the S3-compatible API, which hides it; erasing a version needs `deleteFiles`.** Verified against a real B2 bucket (us-west-004, 2026-10-16) with a key made by Roostack's own `b2.Client.CreateKey` (capabilities `listBuckets, listFiles, readFiles, writeFiles`, limited to the server's folder): restic's lock deletes became hide markers and no locks were left; `check --read-data-subset` and `stats` worked; a throttled backup of 381 MB that took 32 min 38 s finished (exit 0, no locks), where N1's key is stopped at ~22 min; erasing a version with that key (`b2_delete_file_version`) was refused (401). |
| N3 ✅ | With deletes that only hide, restic works as usual with the server's key: backups, `check --read-data-subset` and `stats` leave no locks, and the controller's prune runs (first on the fake, then on real B2). A "ransomware" run with the server's key (`forget --prune` of every snapshot) succeeds but only hides the files: on B2, all 49 were still there as hidden versions. |
| N4 ✅ | **What a taken-over server can still do on B2, and getting it back** (real bucket, 2026-10-16). Deleting the hide markers with the account's key brought every snapshot back (`check --read-data-subset=20%` passed); it also brings back old lock files, which `restic unlock --remove-all` clears (with nothing else running). With `writeFiles` the server can also **overwrite** a file (a new version): overwriting `config` broke the repository ("config cannot be loaded"), and deleting that newest version with the account's key fixed it. So recovery is "roll every file back to its versions before the attack", which only Backblaze's own tools do for now (TASKS). The controller's prune with the account's key hides too (21 hide markers, the data still there), so pruned data is stored, and paid for, until the lifecycle rule erases it. |
| N5 ✅ | **Lifecycle rules** (real bucket): `b2_list_buckets` returned the bucket's `lifecycleRules` to any key with `listBuckets`, with or without `readBucketLifecycleRules`, and `KeepsHidden` read "keep all versions" as 0 (for good), and 1 and 30 days correctly. An answer without the rules is treated as unknown, not as "for good". |
| N6 ✅ | **Keys made on Backblaze's website can't make keys.** A key limited to one bucket came without `writeKeys`, `deleteKeys` and `listKeys`, and Backblaze doesn't appear to allow them on a key limited to one bucket. A key that can make keys (all buckets) has to come from Backblaze's command-line tool, signed in with the master key: `b2 key create <name> listBuckets,listFiles,readFiles,writeFiles,deleteFiles,writeKeys,deleteKeys,listKeys`. With any other key, Roostack falls back to giving every server the account's key, which can delete (TASKS). |
| N7 ✅ | **`restic unlock` clears a killed restic's lock and keeps a running one's** (restic 0.18.0 on VM1, 2026-10-17, `TestUnlockClearsStaleLocks`): a `backup --stdin` holding its lock survived `unlock` ("removed 0"); once it was killed (SIGKILL, so its lock stayed), `forget --prune` exited 11, `unlock` removed 1 lock, and the prune then ran. restic treats a lock as stale when its process (same hostname) is gone or it wasn't refreshed for 30 minutes, so a server's crashed backup is cleared by the controller's weekly prune 30 minutes later at most. |

## P. Public access (SPEC §6.11)

## Q. The edge (SPEC §10.5)

Prototyped on VM2 (2026-10-10) with throwaway containers: Roostack's Caddy image plus `github.com/mholt/caddy-l4@v0.1.2`, both on pasta as Roostack's Caddy. An "edge" Caddy on 9443 with the `layer4` listener wrapper (`tls sni` → `proxy { proxy_protocol v2; upstream … }`, then `tls` for its own sites), and a "home" Caddy on 8443 with the `proxy_protocol` wrapper (`allow` the overlay, `fallback_policy reject`). The overlay was a dummy interface with `10.88.0.1` (the WireGuard hop itself not yet: Q6); the outside visitor a network namespace with `203.0.113.10` (VM2's firewall opened for it, then closed).

| # | Result |
|---|---|
| Q1 ✅ | **A visitor through the edge reaches home with their real address:** home's `{remote_host}` was `203.0.113.10`, and a private path answered "refused: 203.0.113.10 is not private". TLS passed through: the certificate was home's. |
| Q2 ✅ | **The edge's own sites still work** behind the layer-4 wrapper (names it doesn't route fall through to its `tls` and HTTP server), and **a name it neither routes nor serves fails the TLS handshake**. |
| Q3 ✅ | **A faked PROXY header is refused:** a visitor sending one straight to home's port, claiming `10.0.0.5`, had the connection closed (`fallback_policy reject`: an untrusted source may not send one). |
| Q4 ⚠️ | **`fallback_policy reject` doesn't require a header**, it only refuses one from an untrusted source: a visitor connecting straight to home's 8443 without a header was served (with their real, public address, so nothing private opened). So the edge port must be reachable only over WireGuard (the firewall), and `allow` lists only the edges' overlay addresses, never the whole overlay. A trusted source that sends no header counts as its own overlay address (private): the edge always sends one, and an edge that didn't could claim any address anyway. |
| Q5 ✅ | **Inside pasta, the host's own address is the container's:** the edge dialling `10.0.2.15` (VM2's address) reached itself ("connection refused"). The edge dials home's overlay address, which leaves through the host (`10.88.0.1` worked), as WireGuard addresses will. |
| Q6 ✅ | **Over real WireGuard and the internet (2026-10-11):** VM3 at home (Vaultwarden public), `roostack-test` (a Linode in Sydney) as the edge, and this machine as the visitor over the internet: `vault.smiths.roostack.dev` pointed at the Linode and answered 200 with VM3's own certificate (`*.smiths.roostack.dev`, Let's Encrypt), `/admin` (a private path) was refused, HTTP redirected with 308, `roost.smiths.roostack.dev` (not public) failed the TLS handshake at the edge, HTTP/3 had nothing listening, and **VM3's access log showed the visitor's real address** (the home's public address, not the edge's WireGuard one). The Nanode compiled Caddy with the layer-4 plugin in about 9 minutes. |
| Q8 ✅ | **The controller dialling a cloud server (2026-10-11):** VM3 (at home, behind QEMU's NAT and the home router) made a join code for `roostack-test` (a Linode in Sydney) with **None: this server connects to the new one instead**; the Linode listened on UDP 51820 and VM3's hub dialled it with a 25 s keepalive. The join went through, the switch to the server's own key held, and the link stayed up through both Roostacks restarting, with nothing forwarded at home. |
| Q9 ⚠️ | **Dev VMs: QEMU's UDP forward swallowed the VM's own WireGuard packets.** `dev-vm.sh` forwarded UDP 51820 from the host's 127.0.0.1 into each VM, and QEMU sends the VM's outgoing packets from a forwarded port through that forward's socket, which, bound to 127.0.0.1, can't reach the internet: VM3's handshakes never left the machine (other ports did). The forward now binds every host address. Not a real home's problem (nothing is forwarded there). |
| Q10 ⚠️ | **A provider's firewall can be on the network interface, not the server.** `roostack-test` had a Linode Cloud Firewall attached to its interface (Linode Interfaces), allowing UDP 443 and 51821 but not 51820: the API's list of a Linode's firewalls says to look per interface instead. The join's error says to open the port in the provider's firewall; the help page names Linode's. |
| Q11 ✅ | **The controller's side, on its normal port 443 (2026-10-11):** a global `servers :443 { listener_wrappers { proxy_protocol { allow <edge>/32; fallback_policy reject } tls } }`, and the private matchers as "not (private ranges and not the edge)": `not { remote_ip private_ranges 100.64.0.0/10; not remote_ip <edge>/32 }` (a nested `not`, accepted by `caddy validate`). Live on VM2, from a dummy interface holding the edge's overlay address: a visitor through the edge (header for `203.0.113.10`) got the public part, and its private path and a private service were refused; **the edge without a header was refused both too** (it counts as itself, public, so a forwarding bug fails safe); a home device (`192.168.77.10`) reached the private path and the private service; a home device faking a header was refused. So no second port: the edge dials the controller's 443 over WireGuard, and WireGuard guarantees which peer an overlay address is. The edge's own config (`layer4` global option: `tls sni <names>` → `proxy { proxy_protocol v2; upstream 100.96.0.1:443 }`; HTTP redirects for those names, everything else aborted) validates. |
| Q12 ✅ | **An edge claiming a home address (2026-10-16, review H4):** Q11 tested the edge without a header and a home device faking one, not the edge faking a home device; with headers believed on 443, `PROXY TCP4 192.168.1.5 …` from the edge reached private routes. Now Caddy believes headers only on its edge listener (8474), whose sites set `vars roostack_edge yes` and whose private checks are `not { remote_ip <private>; not vars roostack_edge yes; not remote_ip <edge> }`, and the firewall redirects the edges' 443 (and the relay's) there. On VM4, Roostack's Caddy image (2.11.4 with its plugins) rootless on pasta like the real one, the edge a network namespace at 100.96.0.2 on a veth named `roostack`, its connections to the server's 443: a header claiming 192.168.1.5 was refused for a private service and a public service's private path (the stream aborted), and the UI's name got the 404 page (no Roostack pages on the edge listener); a header for 203.0.113.9 got the public service, logged as 203.0.113.9; no header was refused for the private service. A home device (192.168.77.10) on 443 reached the private service and the UI, and a header from it failed the TLS handshake (443 believes none). Caddy ran the site-level `vars` before the imported handlers' matchers (else the edge's 192.168.1.5 would have been private). Plain HTTP still redirects to `https://<name>/` (443, not 8474) with the same names on both ports, and Caddy accepts the two site blocks sharing names and certificates. A joining server (100.96.0.9, not one of the lab's servers) reached the lab API and not SSH, 443 or a home-only port; a server (100.96.0.2) reached SSH and the lab API; a home device couldn't reach the edge listener or the lab API. Not tried: the real relay interface and a real lab edge (the redirect is the same rule by interface or source). |
| Q7 | **No HTTP/3 through the edge:** Caddy's listener wrappers (`proxy_protocol` among them) wrap a TCP listener, and HTTP/3 uses a UDP packet connection, so home couldn't learn a visitor's address over it (Caddy's docs say nothing either way; this follows from the interfaces). The edge forwards TCP only, and home doesn't advertise HTTP/3 for names routed through an edge. |
