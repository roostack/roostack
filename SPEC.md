# Roostack Specification

This document records decisions (locked and pending) and the reasoning behind them. See PLAN.md for the project brief and TASKS.md for progress.

Status legend: **Locked** = agreed, **Pending** = under discussion, **Open** = not yet discussed.

**Name (2026-09-28):** the project is **Roostack**, pronounced "Roost Stack" (`roostack` in code, packages, paths and the Linux user). Its domain is **roostack.cloud** (the Go module path is `roostack.cloud/roostack`); **roost.ac** is for subdomains Roostack hosts for people's labs (§6.5). Earlier drafts called it MyLab; there was no release, so nothing migrates from that name.

---

## 1. Guiding Principles — Locked

1. **Recoverable by default.** A user can rebuild their entire lab on new hardware from a single backup. This is the main test for design decisions.
2. **Declarative state.** Roostack stores the *desired* state (services, domains, settings) as files; podman is reconciled to match. This simplifies backups, workers, and debugging.
3. **Local-first.** Everything works without Roostack Cloud or internet access, except public TLS issuance and image pulls.
4. **Transparent output.** Generated artifacts (container definitions, proxy config) are human-readable and inspectable. A comfortable homelabber can always find where things live and what Roostack did.
5. **Simplicity.** Small codebase, minimal dependencies, each chosen collaboratively for maintainability.
6. **Secure by default.** Rootless where possible, nothing public unless explicitly opted in.

## 2. Target Users — Locked

- **Primary:** less technical users who manage a lab after someone else has installed it (e.g. a NUC set up by a family member). Day-to-day management, including installing new services, must be possible entirely from the web UI.
- **Secondary:** comfortable homelabbers, who must be able to inspect and understand everything on disk.
- **Rationale:** Installing Linux and Roostack is an acceptable technical barrier; managing the lab afterwards must not be.

## 3. Deployment Targets — Locked

- **v1:** a dedicated, freshly installed server. Roostack assumes it owns the host.
- **Reference hardware:** x86_64 Intel NUC-style device.
- **Later:** ARM64 (Raspberry Pi, ARM VPS).
- **Rationale:** A dedicated host avoids conflicts with existing software (ports, podman config, firewall) and greatly reduces the support burden.

### 2.1 Licence — Leaning (2026-10-13)

- **Apache-2.0, assumed for now; may change before launch** (the project's Owner). Roostack is open source.
- **Why:** permissive like MIT, plus an explicit patent grant and a statement that contributions come under the same licence, which suits infrastructure others build on. Roostack Cloud imports Roostack's public packages (`cloudapi`, `authkit`), so a permissive licence lets it use contributors' code without a contributor agreement.
- **Considered:** MIT (the simplest, but no patent clause; the Owner's first thought); AGPL-3.0 (would stop a closed hosted fork, but Cloud's use of contributed code would then need contributors to sign over rights, and it puts some contributors off).
- Packaged services keep their own licences; the website shows each one.

### 3.1 Supported Distros — Locked

| Tier | Distros | Meaning |
|---|---|---|
| **Fully supported** | Debian 13 | Tested; installer supported; full host OS management (§3.2) |
| **Planned** | Ubuntu 26.04 LTS | Add when practical; avoid Debian-only assumptions that would make it hard |
| **Unsupported** | Anything else with Podman 5+ | May work; no host OS management, no support |

- **Rationale:** Debian 13 ships Podman 5.4, has a ~5-year support cycle, rarely changes, and has built-in unattended security updates, which makes it well suited to servers nobody logs into. Supporting a single distro keeps the installer, testing and docs simple.
- **Rejected:** Fedora Server (a major upgrade every ~13 months doesn't suit unattended servers); Ubuntu 24.04 (Podman 4.9 has no `.pod` Quadlets); Fedora CoreOS (unfamiliar and harder to troubleshoot).
- Distro-specific logic (package management, update tooling) should sit behind a small internal interface so Ubuntu can be added cleanly.

### 3.2 Host OS Management — Locked

- **Look — Locked (2026-09-27):** a design system with built-in colour themes (docs/DESIGN.md). The default is Teal and violet; each user can choose another (Ocean and magenta, or themes from popular open-source palettes: Catppuccin, Gruvbox, Nord, Solarized, Everforest, Rosé Pine, Tokyo Night) and light, dark or follow the device. Every theme must pass WCAG contrast checks in both modes (a test enforces it).
- **Brand mark and wordmark — Locked (2026-10-01), as built:** chosen with the project's Owner from mock-ups. Files, colours and how to regenerate them: `assets/brand/README.md`.
  - **Marks:** **Perch** (a hen on two rack servers with green "online" lights) is the primary mark; **Nest and egg** (a cracked egg on three woven layers) is the alternate. Each has a Roostack Cloud version (the hen on a cloud server, the egg in a cloud). A simpler **small mark** (the hen on one server) is the favicon, the app's top-bar mark and the help site's logo, because the full mark's details blur below about 32px.
  - **Colours:** the default theme's own: text colour on a `--highlight-soft` tile, the comb, wattle and cloud in `--highlight`, the egg's crack and every other cut-out in the tile colour, and the online light in the status green that shows on a text-coloured shape (`--ok-on-fg`). In Roostack the mark follows the user's theme; the files in `assets/brand` use Teal and violet. Considered: the first draft's own palette (red comb, amber beak, blue cloud: red reads as "danger" in Roostack, and it ignored the themes), a violet bird, and gold or coral accents outside the themes; the Owner preferred the quieter tile.
  - **Wordmark:** lowercase "roostack" in Space Grotesk (OFL): "roo" medium and "stack" bold for Perch, all medium for Nest; Roostack Cloud adds "cloud" in the highlight. The text is converted to outlines, so nothing loads a web font (the UI and help keep the device's own fonts, §6.3.1).
  - **Taglines** (for the website, not the UI): Rule your own roost. · Bring your stack home to roost. · Every service, home to roost. · Hatch your own cloud. · Your whole lab, under one roost. · Free-range servers. Fenced-in security.
- **Feedback on host operations — Locked (2026-09-27):** anything that acts on the host (OS updates, backups, applying service changes, setup hooks, restores) shows a one-line status that updates live ("OS updates: Installing updates…", then "✓ … finished: Installed 3 updates"), with the full step-by-step log and command output under a collapsed **Details** for technical users. Pages refresh their results when the operation finishes. Logs are kept in memory (latest run of each kind); results that matter later are stored separately.

- On fully supported distros, Roostack manages the host OS: security/package updates, reboot handling, and eventually major version upgrades.
- Users must be told clearly (docs and UI) that major manual changes to the host OS may limit Roostack's ability to manage it.
- **Rationale:** The primary user (§2) cannot maintain a Linux host. An unpatched host undermines everything else.

#### Time zone — Locked (2026-09-26)

- Roostack shows and schedules everything (nightly backups, maintenance windows) in the **host's** time zone.
- The setup wizard's first step confirms it, pre-filled from the browser's zone; the Owner can change it in Settings. `roostack-agent` applies it with `timedatectl set-timezone`, then Roostack restarts, because Go reads the local zone once at startup.
- If the browser's UTC offset differs from the host's, every page shows a prominent banner saying times are the server's, with a link for the Owner to change it.
- **Rationale:** cloud images and VMs default to UTC, which silently moved the "02:00" backup to midday for a user in Melbourne.

#### Update & reboot policy — Locked

| What | Policy |
|---|---|
| Security updates | Automatic, daily (`unattended-upgrades`, managed by `roostack-agent`) |
| Other Debian stable updates | Automatic (stable only receives bug and security fixes) |
| Reboots | "Reboot pending" shown in the UI; automatic reboot in a maintenance window (default 04:00). The Owner can change the window or choose notify-only |
| After reboot | Services return through systemd; Roostack health-checks them and flags failures |
| Major upgrades (e.g. 13 → 14) | Never automatic. Owner-initiated, guided, only once Roostack supports the new release, and only after a fresh successful backup |
| Roostack itself | Patch releases automatic; minor/major releases notify and need approval (same as services, §7) |
| Unknown host changes | Basic detection (extra apt sources, held packages, a changed firewall) triggers a warning; more thorough checks later. As built (2026-09-28): per server, on its Updates page and in "needs attention"; the Owner can mark the current changes as made on purpose, and anything new warns again |

- `unattended-upgrades`' own automatic-reboot option is **disabled**; only Roostack decides when to reboot.
- **How it runs (2026-09-27):** Roostack ships `/etc/apt/apt.conf.d/52roostack-unattended-upgrades` (adds stable-updates, no automatic reboot, removes old kernels). Every night after the 02:00 backup, the coordinator runs an "OS updates" job: `roostack-agent` runs `apt-get update && unattended-upgrade` in a transient unit (outside its own sandbox). The job is queued separately from the backup, so a failing backup doesn't hold back security fixes. Debian's own apt timers stay enabled as a fallback. `/run/reboot-required` (written by the kernel's postinst hook) is checked after each run and every 30 minutes; the coordinator then reboots in the window through the agent.
- The Owner sees the last run, any pending restart and why it waits, and can **check for updates now**, **restart now** (refused while a maintenance job runs), and choose automatic restarts at a chosen hour or notify-only (`lab.yaml`: `maintenance.restart`, `maintenance.restart_hour`).
- **Rationale for automatic reboots:** otherwise the primary user may run an unpatched kernel indefinitely. A brief overnight interruption is the better trade-off.

#### Maintenance coordinator — Locked

A single coordinator in `roostack` sequences every disruptive operation (backups, prunes, restores, service updates, package upgrades, reboots) so that conflicting operations never overlap.

- **Nightly order:** backup → automatic service updates → reboot if needed. This means there's always a fresh backup just before any automatic change.
- **Reboots wait** for running backups, restores and updates, then happen once they finish, within the window.
- **Never interrupted:** restores, major OS upgrades, and a backup's prepare step (services stopped or database dumps being written).
- **Resumable long jobs** (e.g. a multi-day first off-site upload) may be paused for a reboot that has been pending for longer than a deadline (default 24h, configurable), and they resume automatically afterwards. restic's repository stays consistent when interrupted.
- The UI explains why a reboot is waiting (e.g. "waiting for backup to finish, 62%").
- **Rationale:** fixed time windows can't handle jobs of unpredictable length. Delaying kernel security fixes for days is worse than pausing a resumable upload.

## 4. Roostack Cloud — Locked (scope), Open (design)

- A future paid hosting service for: resilience (critical services away from home internet), off-site backup targets, and users without their own hardware who still want to own their data.
- **Out of scope for v1**, but worker communication and backup formats must not preclude it.
- Implication: data portability is essential. A user must be able to move services and backups between home, VPS, and Cloud freely.

## 5. Users & Access — Locked

- **Roostack accounts are separate from service accounts in v1.** Roostack manages who can log in to Roostack; each service (Immich, Vaultwarden, …) manages its own users. Unifying them is part of the deferred SSO decision, and the design should allow Roostack to become the identity source later.
- **Fixed roles (not customisable in v1):**

| Role | Permissions |
|---|---|
| **Owner** | Everything: host settings, OS updates, backups and restore, recovery key, user management. At least one Owner must exist. |
| **Admin** | Install, configure, update and remove services; run backups; view logs. No host-level settings, no user management. |
| **Member** | View the dashboard (service links, status) only. |

  - Rationale: the person who sets up the lab (Owner) keeps control of risky host settings, while the day-to-day user (Admin) can still manage services freely.
- **Authentication:** local accounts, passwords hashed with argon2id. **TOTP 2FA** in v1, required for Owners and for any public admin UI. Passkeys later.
- **Shared with Roostack Cloud — as built (2026-10-07):** the password, token and two-factor code is a public package, `authkit`, which Cloud's repository imports: one implementation. Both use the same argon2id settings (a lab has far fewer logins than Cloud, so it can always afford at least as much). Cloud, holding many accounts, also turns on a **pepper** (a key outside the database mixed into passwords) and **sealed two-factor secrets** (encrypted with a key outside the database), so a stolen database alone gives neither; a lab's database and keys are on one machine, where they wouldn't help. Fuzz tests try random input against it: the first runs found that a stored hash with out-of-range settings made argon2 panic (now refused, with limits on memory and rounds), and that base64 accepted several spellings of one value (now strict). Considered: two independent implementations, against a bug shared by both (twice the security-sensitive code to keep right).
- **Password recovery:** host command line only (`sudo roostack user reset-password <name>`, `reset-2fa <name>` for a lost phone). No email reset (it would need mail setup and adds attack surface), and no recovery codes: the command line is simpler for a home lab.
- **People page (2026-09-27):** the Owner adds people (a temporary password is shown once and must be changed at first login), changes roles, gives someone a new temporary password, turns off someone's two-factor, and removes people. Not on their own account (use Account), and the last Owner can't be demoted or removed. An Owner who forgot their own password uses the command line.
- **Signing out after inactivity — Locked (2026-10-03):** a session ends after a while without activity, 30 minutes by default; the Owner chooses 15 or 30 minutes, 1 or 4 hours, or never (Settings → People → Signing in). Activity is opening a page or sending a form; parts of pages refreshing themselves (htmx requests) aren't, so an open tab doesn't keep a session alive, and once it has ended they take the page to the login page, which says why. Without "keep me signed in" the cookie also ends when the browser closes. **"Keep me signed in"** on the login page (offered unless the Owner turns it off) keeps that browser signed in for 30 days with no idle limit, for someone's own device; it carries through the two-factor step and a password change. Sessions record when they were last used (saved at most every 30 seconds); the hourly session clean-up also deletes those past the idle limit, so relaxing the limit later doesn't bring old ones back. Considered: counting refreshes as activity (a tab left open would never sign out), and a countdown warning before signing out (more code and noise; the page simply goes to the login page).
- **Audit log:** records who did what and when, to support remote help and troubleshooting.

### 5.1 Roostack Data Storage — Locked

- **Desired state:** readable YAML files in `/var/lib/roostack/` (Principles 2 and 4).
- **Runtime data** (users, sessions, audit log, job history): a **SQLite** database in `/var/lib/roostack/`. A single file, no server, easy to back up. The backup prepare step must take a consistent copy (SQLite online backup / `VACUUM INTO`), not a raw copy of the file.

## 6. Container Runtime — Locked (principle)

- Podman, **rootless where possible**; rootful only where a service genuinely requires it (e.g. low ports, host networking, device access), and this is visible to the user.
- **Rationale:** security is a priority; rootless limits the blast radius of a compromised container.

### 6.1 Roostack Process Architecture — Locked

Roostack runs **directly on the host** (not in a container), as two processes shipped in one `.deb` package:

| Component | Runs as | Responsibilities |
|---|---|---|
| `roostack` | Unprivileged `roostack` user, strict systemd sandboxing | Web UI, API, desired state, rootless service management (Quadlets, status, logs) |
| `roostack-agent` | root | A small fixed set of privileged operations only: OS updates, reboots, rootful Quadlets, firewall. Also sets the host time zone. Listens on a local socket reachable only by `roostack`. |

- Nodes in a multi-server lab run the same package (§10).
- Roostack updates itself through apt, alongside host OS updates (§3.2).
- `roostack` is hardened with systemd sandboxing (`ProtectSystem`, `ProtectHome`, `NoNewPrivileges`, `PrivateTmp`, system call filtering, limited writable paths) to get most of a container's isolation.
- **`roostack` never runs `podman` directly — Locked (2026-09-26).** Rootless Podman needs the setuid `newuidmap`/`newgidmap` helpers, which `NoNewPrivileges` disables. So `roostack` only talks to the `roostack` user's systemd manager (`systemctl --user`, `systemd-run --user`), which runs Podman outside the sandbox. One-off commands (creating secrets, database dumps, `podman unshare` for backups) go through `systemd-run --user`.
- **Rationale:**
  - Keeps root code small and easy to review; privileged operations are explicit, not implied by broad socket access.
  - Podman/Quadlets rely on host systemd for lifecycle, so a containerised manager would need root-equivalent host access anyway.
  - Two components, a standard Debian install and update path, and no "container updating itself" problem.
- **Considered:**
  - *Container + many host mounts (Portainer/Komodo style):* those tools rely on the Docker daemon socket, which is root-equivalent. Under Podman they would also need the Quadlet directory, systemd D-Bus access, and a root agent regardless.
  - *Container web UI + host agent (A′):* a valid design that isolates the web-facing part. Rejected for now: it means either much more root code or three components, and the gain is limited because the agent API must allow arbitrary service deployment. The roostack↔agent API boundary leaves this option open later.
  - *Single root process:* rejected; the web UI would run as root.
- This deviates from PLAN.md's original "roostack orchestration container" wording. Services still run in containers; Roostack itself does not.

### 6.2 Language: Go — Locked

- Both `roostack` and `roostack-agent` are written in Go, in a single codebase.
- **Rationale:** Builds a single static binary, which makes `.deb` packaging trivial. Low memory use suits NUC-class hardware. Podman is written in Go and there are mature systemd/D-Bus libraries. The language is small, readable and widely known, which fits the simplicity principle. The maintainer wants to learn it.
- **Considered:** Rust (steeper learning curve, slower to build with); Python (easiest to write, but harder to package and ship as a host service).

### 6.3 Web UI: Go templates + htmx + Alpine.js — Locked

- Server-rendered HTML, embedded in the `roostack` binary. No JavaScript build step.
- Step-up approach for interactivity. Use the lowest level that works:
  1. **htmx** for server interactions (default)
  2. **Alpine.js** for small in-browser behaviour (toggles, show/hide, simple validation)
  3. **Standalone JS libraries** for heavy widgets (e.g. xterm.js for a terminal, a chart library)
  4. **A separately built component** only when a feature genuinely needs it, decided case by case
- **Architecture rule:** business logic lives in core Go packages. HTTP handlers are a thin layer on top. This keeps the UI replaceable and supports the master/worker API and a possible CLI.
- **Rationale:** Roostack's UI is mostly forms, lists, status and logs, with state held on the server, which is htmx's strength. Validation lives in one place (Go). A small toolchain suits the simplicity principle and a maintainer learning Go.
- **Rejected:** React islands. They bring back a Node build toolchain and a second UI paradigm for limited gain.
- **Known limits:** UIs with a lot of browser-side state (drag-and-drop dashboards, visual editors) would need step 4.
- **Live updates — as built (2026-09-29):** parts of pages that show changing state (the home page, Services, the Backups status card, the drive list) poll with htmx, and are kept cheap: they poll **only while the tab is visible** (and refresh once when it becomes visible again); each poll sends a fingerprint of what the part shows, and the server answers **204 No Content** when it's unchanged, so htmx leaves the page alone (nothing to download or redraw; open panels, selection and scroll stay put); the controller **shares its reads of other servers** for 10 seconds, so several open tabs cost one round of calls (any change forgets them); and responses are **gzip-compressed** (a page is about a third of its size). Activity logs poll every 2 seconds only while something runs. **Later:** push instead of poll, once Roostack moves to htmx 4, with its WebSocket support (`hx-ws`); see TASKS.
- **Sizes — Locked (2026-09-28):** shown in decimal units everywhere (1 GB = 1,000,000,000 bytes; kB, MB, GB, TB), as drive makers, macOS and most people count them, so an "8 GB" USB drive reads 8.0 GB. One formatter (`internal/units`) serves the UI, logs and the CLI, and sizes people type (e.g. a storage quota in GB) use the same units. Binary units (GiB) were considered: exact, but unfamiliar to most people, and a drive would read smaller than its label.

### 6.3.1 Help site — Locked (2026-09-29)

- **What:** a help site for the person running Roostack, in plain language, with a collapsed **For technical users** section on each page (exact paths, commands, logs), plus a technical reference (files, command line, ports, package format). Source in `help/` (Markdown), separate from `docs/`, which stays developer-facing.
- **Tool: [Zensical](https://zensical.org)** (from the Material for MkDocs team), pinned exactly in `help/pyproject.toml` and `uv.lock` (pre-1.0, so releases may break), run with `uv run zensical`. Chosen by the Owner of the project.
- **Where it's read:** both **inside Roostack** at `/help` (built at `make build` and embedded in the binary, so it works offline and matches the installed version; the UI's "Tell me more" links can point into it) and as a **public site** (address to be decided; `help.roostack.cloud` for now). Pages use relative links, so one build serves both.
- **Look:** Roostack's "Teal and violet" colours (`help/docs/stylesheets/roostack.css`, kept in step with `themes/teal.css`), the Roostack small mark (`help/docs/assets/logo.svg`, generated by `assets/brand/generate.py`), light/dark following the device. No web fonts or anything loaded from other sites.
- **In Roostack — as built (2026-09-29):** `make build` runs `zensical build --strict` (a broken link fails it) and copies the site to `internal/web/helpsite/site`, which is embedded; only a README there is committed, so `go build` and the tests work without Python, and `/help/` then says the help isn't included. Without `uv`, `make build` warns and carries on; `scripts/build-deb.sh` refuses to package a build without the help. `/help/` is served to anyone, logged in or not (it's public anyway, and "Locked out" must be readable before logging in). The top bar has **Help**; the login page links to "Locked out". Considered: committing the built site (every help edit would change ~60 generated files).
- **Page help — as built (2026-09-29):** every page with a matching help page (or section) links to it, top right above the title, on the back link's row: a question-mark icon and the help page's title, opening in a new window like **Help** (the `help` component). A test checks each page and `#section` exists in `help/docs`. Considered: a "Tell me more" link in each page's text (the UI already uses "Tell me more" for details that open in place; mixing the two would surprise people), and a link at the end of each page (easy to miss).
- **Its Content-Security-Policy — Locked (2026-09-29):** `/help/` gets its own policy; the rest of the UI keeps its own. **Scripts:** only the pages' inline scripts, by SHA-256 hash, worked out from the embedded files when Roostack starts (so they always match the build). **Styles:** `'unsafe-inline'`, because Zensical's search box injects a stylesheet held in its minified script, and pages have style attributes; hashing that stylesheet would mean picking a string out of minified code, which would break silently with a new Zensical. Inline styles can't run code, and the help has nothing written by users to inject into. Browsers ignore `'unsafe-inline'` if a hash is also listed, so there are no style hashes. Rejected: `'unsafe-inline'` for scripts.
- **The public site — Locked (2026-10-12):** at `help.roostack.cloud`, on Cloudflare (static files), deployed from this repository's `zensical build` output; the website, roostack.cloud, is hosted the same way. Considered: a path under roostack.cloud (`/help`; the two sites are built and released from different repositories), and Caddy on a server of our own (one more thing to keep up).
- **Considered:** plain MkDocs with Material (Zensical is its successor, by the same team, and reads the same Markdown); writing help pages as Go templates inside the UI (no search, and no public site without Roostack running).

### 6.3.2 Reaching the UI — Locked (2026-09-30)

- **The UI listens on `127.0.0.1:8480` only.** With a roost.ac name, it is served at the name itself (`https://smiths.roost.ac`, §6.6); with an own domain, at `https://roost.<domain>` (named `roostack.<domain>` until 2026-10-01; shortened by the project's Owner) through Caddy, to the home network only (private). Without one, it's reached over an SSH tunnel (`ssh -L 8480:127.0.0.1:8480 …`), which works the same on Windows 10/11 (PowerShell), macOS and Linux, but is a hard first step for people who don't use a terminal. The installer shows the command with the server's address filled in; on a server joining an existing lab, it points to `sudo roostack node join <code>` first, which needs no setup page.
- **Considered (2026-09-30), not built:** serving the setup page to the home network until setup is finished (plain HTTP, only on a server with no public address). A server with a public address would keep the tunnel either way: plain HTTP there crosses the internet. Rejected for now: an option to listen publicly.
- **Open, for later: HTTPS by IP address.** Let's Encrypt issues certificates for bare IP addresses (short-lived ones), which could give a cloud server's setup page `https://<its address>` with a real certificate and no domain. Check whether Caddy can get one and how it renews, once public access has settled.
- **On a lab on the internet, the UI is public — Decided (2026-09-30) by the project's Owner, as built:** at `roost.<domain>`, as a public route: CrowdSec's bouncer (CrowdSec runs whenever the UI is public), 1000 requests per 10 s per visitor, and 10 a minute on `/login` and `/backups/recovery-key` (not `/setup`: the setup code can't be guessed, and the wizard's pages are under it). 2FA is required for Owners already (§5). The Owner can keep it to an SSH tunnel instead (`public.ui_tunnel_only`), in the wizard's first step or Settings. Considered: tunnel only (safest, but the Owner of a cloud lab would need a terminal for everything).
- **Open: serving the UI through the domain as an explicit choice (at home).** At home, a domain automatically serves the UI at `roost.<domain>` (home network only). Proposed by the project's Owner (2026-09-30): make that something the Owner turns on once a domain is set. Questions: what is the UI reached by if it's off (the tunnel only?); does the wizard offer it at the domain step. (On the internet it's the choice above.)

### 6.3.3 Installing, step by step — Locked (2026-09-30)

- **Why:** a first install can take minutes (downloads, and on a brand-new server Caddy's image build), and the UI showed "stopped" with an **Open** link, or nothing at all, so people couldn't tell whether it had hung. Agreed with the project's Owner from a mock-up (2026-09-30).
- **As built (2026-09-30):** a new service (all its containers new) shows **installing** until its last step is done. Its page lists each step (done, in progress with "for …", or to do): *Downloading* and *Starting* each container ("the database (Postgres)", "the cache (Valkey)", or the service), *Making it reachable at its web address* (or *Waiting for Roostack's web proxy to finish building* while Caddy's image builds; left out while Caddy waits for the domain step), and *Finishing setup* if the package has install hooks. The log is under **Details** (the apply's, then the setup's). The Services list and Home show "Step 3 of 5: …" and no **Open** link; the address is shown greyed until it's running. Before its apply begins (e.g. waiting for another change), it shows one step, *Waiting for other changes to finish*. After 5 minutes on one step, the notice says it's taking longer than usual and when its log last changed. When it finishes, the page reloads to show it running.
- **How:** the node tracks installs in memory (`node.InstallProgress`, part of `ServiceDetail`, so other servers' installs show too), fed by the reconciler's progress events. Each new container's image is pulled first as its own step (`podman pull` through `systemd-run --user`, output in the apply log), so the download isn't hidden inside the unit's start (and its 5-minute pull timeout under systemd doesn't apply). New services start before a new Caddy, whose first start waits for its image build, so downloads run while it builds.
- **Not done:** download progress in MB (podman prints a line per layer, not progress, without a terminal); a **Try again** button for a failed download (the next apply retries); the step list after a restart mid-install (the containers' state is shown instead).

### 6.4 Service Execution: Podman Quadlets — Locked

- Roostack generates **Quadlet** files (`.container`, `.volume`, `.network`, etc.) and systemd runs them. Rootless units go in `~/.config/containers/systemd/`.
- Users never write Quadlets directly. They are generated from Roostack's own service definitions (see §8).
- **Rationale:**
  - Official Podman feature (4.4+), maintained by the Podman project, and an open, well-supported format.
  - systemd provides start-at-boot, restart-on-failure, dependency ordering, and logging (`journalctl`) with nothing extra to build.
  - Designed for rootless operation (§6).
  - The generated files are plain text a homelabber can inspect (Principle 4), and they are declarative (Principle 2).
- **Rejected:** podman-compose. It is community-maintained, supports only part of the Compose spec, and needs extra pieces for boot and restart handling. Also rejected: running docker-compose against the Podman API socket, which brings back a daemon-style model with the same lifecycle gaps.
- Rootless services need `loginctl enable-linger` for the service user so they start at boot without anyone logging in.

### 6.5 Reverse Proxy & TLS — Locked

- **Proxy: Caddy**, run as a rootless container from a Roostack-built image that includes the DNS provider plugins.
- **DNS providers — Locked (2026-09-26):** Cloudflare, Amazon Route 53, Porkbun, Gandi, GoDaddy, Namecheap and Spaceship, defined in one registry (`internal/dns`). Each provider's credentials are stored as Podman secrets and passed to Caddy as environment variables, so they never appear in the Caddyfile. Before saving, the wizard checks credentials by **creating and deleting a temporary TXT record** through the provider's public HTTP API (Namecheap: a read-only check, since its API can only rewrite whole zones). That tests what certificate issuance needs.
- **Dependencies for provider APIs:** prefer plain HTTP calls or small generic libraries; avoid large vendor SDKs (e.g. the AWS SDK). Roostack's checks use the standard library only (including AWS SigV4 signing for Route 53).
- Roostack generates a readable Caddyfile from desired state and reloads Caddy (same pattern as Quadlet generation).
- **Not user-selectable.** One proxy keeps testing and config generation manageable. Users can add custom Caddy snippets, globally and per service.
- **Rootless on 80/443:** `roostack-agent` lowers `net.ipv4.ip_unprivileged_port_start` so the proxy needs no root.
- **Proxy networking (Option C) — Locked (2026-09-26):**
  - Caddy runs in its **own pasta network namespace** (`Network=pasta:--map-host-loopback,169.254.1.3`), publishing 80/443. Pasta keeps each visitor's **real IP**, which the private-route check and CrowdSec rely on.
  - Each routed container stays on its service's private network and is **published on `127.0.0.1:<port>`** only. Caddy reaches it at `169.254.1.3:<port>`, which pasta maps to the host's loopback. The Roostack UI listens on `127.0.0.1:8480` and is reached the same way.
  - Ports come from a central range (20000–29999), are allocated once, and are stored in the instance file (`routes.<name>.port`) so they never change.
  - **Why:** on the Debian 13 VM, rootless bridge networks replaced client IPs with `10.89.0.x` (Podman's `rootlessport`), which Caddy would treat as private, exposing "private" services to the internet. Rootless Podman can't put one container on both pasta/host networking and a bridge network, and the host side can't reach bridge addresses.
  - **Rejected:** Caddy on host networking (works, but shares the host's network namespace); a host-network forwarder using the PROXY protocol in front of a bridge-network Caddy (two proxies, no HTTP/3).
- **TLS: Let's Encrypt via DNS-01.** This is required so that private (LAN/VPN-only) services get valid certificates without being reachable from the internet.
- **Wildcard certificate by default** (e.g. `*.lab.example.com`), with services on subdomains sharing it. Rationale:
  - One issuance and renewal instead of one per service, so fewer rate-limit issues.
  - Subdomain names don't appear in public Certificate Transparency logs, so the list of services you run isn't published.
  - DNS-01 is already required, so there's no extra setup.
  - Trade-off: one certificate covers all services. That's acceptable on a single-owner host.
- **Rationale for Caddy:** best automatic HTTPS, readable config, easy custom snippets. **Considered:** Traefik (many DNS providers built in, but verbose config tied to container labels); Nginx + certbot (familiar, but TLS is a separate tool and config is verbose).

### 6.5.1 DNS Records & Local Access — Locked (2026-09-26)

Roostack manages the DNS records its services need, through the same DNS provider credentials used for certificates.

- **Private services (default):** one **wildcard record** (`*.<domain>`) pointing at the lab's **LAN IP**, in public DNS. Devices at home reach services without local DNS. Anyone can look the record up, but only the home network can reach the address, and service names stay out of public DNS (like the wildcard certificate).
- **Router DNS rebinding protection:** some routers drop DNS answers containing private IPs. Roostack **detects** this by comparing the home network's resolver with a public resolver, and shows instructions (allow the domain in the router, or use local DNS).
- **Local DNS** (e.g. Pi-hole) is optional, for later. Getting every device to use it means changing the router's DHCP DNS setting (router-specific, sometimes impossible). Roostack running DHCP itself was **rejected**: if the lab dies, the home network stops working.
- **Public services (stage 2):** explicit records pointing at the **public IP**; explicit records override the wildcard. Devices at home reach them via the router's NAT loopback (Roostack can test this).
- **Dynamic public IPs (stage 2):** Roostack updates the records itself (§6.11, 2026-09-30; ddns-updater was the earlier plan).
- **Cloudflare proxy (stage 3):** offered per public service, **off by default**, with advantages and disadvantages listed in the UI:
  - For: hides the home IP; DDoS protection; works around some ISP port blocking.
  - Against: Cloudflare decrypts the traffic (at odds with "own your data"); free plan upload limit of 100 MB per request; Cloudflare's terms restrict large media streaming on the free plan.
  - When proxied, Caddy trusts `CF-Connecting-IP` **only from Cloudflare's published IP ranges**, so the private check and CrowdSec still see real visitors.
  - Packages declare proxy warnings, e.g. large uploads (Immich, until its chunked uploads land) or media streaming (Plex, Jellyfin, stricter). The format is to be designed.
- **Ownership:** Roostack only changes records it created (tracked in its state, plus a comment where the provider supports it). An existing record with the same name that Roostack didn't create is never overwritten automatically; the UI explains the conflict. A record that already has the right value is adopted.
- **Taking over a record:** the Owner can explicitly take over a conflicting record from the dashboard. A confirmation page shows the current and new values, warns that anything relying on the current value stops working, and needs an "I understand" tick. The takeover is recorded in the audit log.
- **Switching management on or off** is done from the dashboard's "Home network access" card (Owner only), with the Namecheap risk opt-in where relevant, and applies without a restart. Turning it off leaves records in place.
- **Namecheap:** its API can only replace a domain's whole record set, so record management there is **off unless the Owner ticks an opt-in** with a clear warning, and strongly recommends another provider (e.g. Cloudflare).
- **No usable public IP (CGNAT):** public exposure needs a relay. Future options: Cloudflare Tunnel, or a Roostack Cloud relay (§4).
- **Stages:** 1) wildcard to LAN IP + rebinding check; 2) public records + dynamic DNS (with public exposure, firewall, CrowdSec); 3) Cloudflare proxy.

### 6.6 A lab's address (domains) — Locked, changed 2026-10-06

- **Changed (2026-10-06): an own domain is optional.** A lab gets its addresses from either **its own domain** (with a supported DNS provider, API token for DNS-01, as today) or **a free `roost.ac` name** from Roostack Cloud (e.g. `smiths.roost.ac`, with services at `photos.smiths.roost.ac`), whose DNS and certificate challenges Cloud handles for the lab. A lab can switch between them later. Getting a name means linking the lab to Cloud (a free account); nothing else about Cloud is needed.
- **Before (2026-09-26 to 2026-10-06):** v1 required a user-owned domain, set up once at install, with `roost.ac` names planned for later. Built that way: the package installs a placeholder domain, and until a domain is set up nothing gets an HTTPS certificate. Untangling this is a task (TASKS, "Domain optional").
- **Certificates for an own domain — Locked (2026-10-06):** Roostack picks the best way available, automatically:
  1. **A supported DNS provider:** DNS-01 through the provider's API, one wildcard certificate (as today).
  2. **Benched (user, 2026-10-10): an unsupported provider.** Options 2 and 3 below were locked on 2026-10-06 and are kept as the design, but aren't being built now. The people they serve are few: they must be able to add CNAME records by hand, yet be unable to use any of the seven supported providers, when moving a domain's DNS hosting to one (Cloudflare is free) keeps the domain where it's registered. Meanwhile the help page says to do that. When this is built, both come together, and **reaching the lab on port 443 is a first-class choice** in the address step, not a hidden fallback.
     - **Through Roostack Cloud (lab linked):** DNS-01 by challenge delegation. Let's Encrypt wants a TXT record with a new value at every renewal (every 60 days, sooner as certificates get shorter), which nobody can keep up by hand; a CNAME added once (`_acme-challenge.<domain>` → a name Cloud gives the lab) moves that record to where the lab can write it, the mechanism a roost.ac name already uses. Still one wildcard; Cloud only touches that challenge name and never holds the certificate or its key. **Refined (2026-10-10):** the addresses should be a CNAME too (`*.<domain>` → a name under Cloud the lab keeps pointed at the right address, as for a roost.ac name), so the owner adds two records once and never touches DNS again, even when the server's or the home's address changes; otherwise they'd also keep A records up to date by hand. Needs a provider that allows a wildcard CNAME (nearly all); the bare domain can't be one, and isn't needed (Roostack is at `roost.<domain>`). A side benefit: Roostack holds no key to the domain at all, where most providers' API keys can rewrite the whole domain or account.
     - **Without Cloud, the lab reachable on port 443** (a VPS, port forwarding, or a relay): TLS-ALPN-01, a certificate per name. Let's Encrypt only issues wildcards after a DNS check, so each service gets its own certificate, and the names appear in public certificate logs (a wildcard hides them). Services only on the home network can't get a certificate this way.
- **Three states — Locked (2026-10-06), agreed from a mock-up:**
  - **No address yet:** a real state, not a placeholder domain. Services install and run but have no web address: each shows "Waiting for an address" with a link to give the lab one, and its Details give technical users the local port and an SSH tunnel to reach it meanwhile. **Until then, a service's own address is its local one** (`http://localhost:<port>`, host `localhost`), where a tunnel reaches it: apps that must know their address (Vaultwarden's `DOMAIN`, Forgejo's root URL) refuse to start without one (found on a fresh install, 2026-10-06). Packages use the route's `.URL` for it. One item on the home page's attention list. Caddy, DNS records and public access only act once there's an address. The UI is reached over the SSH tunnel (§6.3.2), as without a domain today.
  - **A roost.ac name:** services at `photos.smiths.roost.ac`; **Roostack itself at the name** (`smiths.roost.ac`), not `roost.smiths.roost.ac`.
  - **An own domain:** as before, Roostack at `roost.<domain>`.
- **Choosing it — Locked (2026-10-06):** the wizard's step 3 is **"Your lab's address"** (was "Your domain"), and Settings → Domain and certificates becomes **Your lab's address**. Two choices: **a free roost.ac address** (recommended: type a name, see whether it's free, "Continue to Roostack Cloud" takes the same tab there to sign up or log in, Cloud sends it back, and the lab finishes by itself) or **your own domain** (then the domain, an email address and who runs its DNS, as before), with a link to a help page on buying and managing a domain (which registrars' DNS Roostack supports, and how). **"Set this up later"** stays, saying services can't be reached until the lab has an address. The roost.ac option is always offered (Roostack Cloud is meant to be permanent), unless Cloud is turned off (below).
- **Switching — Locked (2026-10-06):** from a roost.ac name to an own domain, back, or to another name: every service's address changes, so **the old addresses keep working for 30 days** (Caddy serves both names; the old certificates kept), with a notice listing what to update (bookmarks, phone apps such as Bitwarden's or Immich's server address). Then they stop.
  - **As built (2026-10-07), for own domains** (roost.ac names come with Cloud's DNS): saving a different domain keeps the one being left in `lab.yaml` (`old_address`: the domain, its DNS provider settings, and when it stops), and copies its provider's credentials to their own Podman secrets (`roostack-caddy-dns-old-<field>`) before the new ones replace them. Caddy then has a second wildcard site for the old domain, with its own certificate (it can still renew, through the old provider), and every route answers to both names (`host photos.new photos.old`), with the same protections. **The old addresses work exactly as before, not as redirects** (agreed 2026-10-07): many phone apps don't follow a redirect to another host. Apps' own settings that hold the address (Vaultwarden's `DOMAIN`) use the new one at once. Home shows everyone a notice until then (a warning in the last week); the Owner's links to Settings → Your lab's address, which lists every old → new address (Roostack's too), says passkeys made for the old address don't move, and offers **Stop the old addresses now**. Each service's page shows its old address and until when. An hourly check ends it: `lab.yaml` first and a restart, and the old credentials are deleted only after that (Podman deletes a secret a running container uses, which then can't restart: ASSUMPTIONS C12). Only one old address is kept: switching again within 30 days stops the earlier one at once (the change form says so). **Not handled:** Roostack stops updating the old domain's DNS records (if the home's address changes meanwhile, old addresses pointing to it stop sooner), and can't delete them afterwards (providers' APIs here only set records): the page says they can be deleted by hand. Considered: redirects (break apps), keeping several old addresses (more secrets and certificates for a rare case).
- **A roost.ac name alongside an own domain — Leaning (2026-10-06):** the lab's addresses are a **primary** (used for every service by default) and, later, **extra** ones: e.g. an own domain as primary, plus a roost.ac name for one service shared through the relay without touching the domain's DNS, alongside custom domains (§6.11). The records are designed for several addresses from the start; the extra addresses come after the single-address version.
- **Turning Roostack Cloud off — Locked (2026-10-06):** `cloud: { disabled: true }` in `lab.yaml` turns off every Roostack Cloud feature: nothing is offered (the roost.ac choice, Cloud backups, checks from outside) and Roostack never contacts Cloud. It's deliberately only in the file, not in Settings: for people who want Roostack fully self-contained.
- **Linking a lab to Roostack Cloud — Locked (2026-10-07), agreed from a mock-up.** Everything Cloud does for a lab (a roost.ac name, later backups and checks from outside) starts with linking it to a Cloud account, from the lab. The lab's side:
  - **Only the controller talks to Cloud.** It makes a key pair (ECDSA P-256) whose private key never leaves the server, and asks Cloud for a **link code**, sending the lab's name, the roost.ac name it wants (if any), Roostack's version and a certificate request for that key. Nothing else: no email address, no list of services. Because the key goes with the first request, someone who sees the code can't swap in a key of their own. Cloud answers with the code, the page to open, and a secret only the lab holds, used to ask about it.
  - **The Owner confirms in Cloud — same tab, as built (2026-10-10).** The button posts, and Roostack sends that tab on to Cloud's page with the code in it (a short "Going to Roostack Cloud…" page with a meta refresh). There they sign up or log in, check the code matches the one the lab shows, and confirm ("Link and go back to Test lab"). The link request carries a **return address**: the lab's own waiting page, built from the address the Owner's browser used (the form's `Origin` header), so it works however the lab is reached. Cloud sends the browser back there, and the page shows the steps (linked, address claimed) and **moves on by itself**: in the wizard to the next step (with a note saying the lab's address), in Settings to Roostack Cloud; if the link failed, back to the address step to try again. Meanwhile the lab asks Cloud every few seconds (no incoming connection needed), so nothing secret passes through the browser; Settings still shows the code and its expiry (10 minutes) for anyone who comes back another way. Cancelling just forgets it. Considered: a new window (the first build), dropped because the desktop app's browser turned its form post into a GET, and the leftover tab plus "Continue setup" confused people (user, 2026-10-07).
  - **Once confirmed,** the lab gets its certificate and uses it for every request to Cloud from then on (mutual TLS, as between a lab's servers). It renews itself (a new key each time) once two thirds of its life has passed, and the lab checks in once a day (and when Roostack starts): "last contact" on the page.
  - **Never magical:** Settings → **Roostack Cloud** (hidden when Cloud is turned off) shows the account, since when, what Cloud is used for, the last contact, and under Details the certificate (fingerprint, expiry), where its key is (`<state>/cloud/`, 0600), Cloud's address, and a log of the lab's recent requests to Cloud.
  - **Unlinking** from the lab asks for confirmation, naming what stops working (a roost.ac address, and with it every service's address: the lab goes back to "no address yet"), tells Cloud, and deletes the key. If Cloud can't be reached it unlinks anyway and says so: the account page can remove the lab too.
  - **Unlinked from Cloud's side, and restores — Locked (2026-10-07):** the link is in Roostack's state, so it's backed up and a restored lab is still linked. If the lab was unlinked meanwhile (from the account, from the lab before an older backup was restored, or the certificate expired while the lab was off), Cloud refuses the certificate at the next contact; the lab then forgets the link and "needs attention" says it's no longer linked and offers to link it again. Cloud being unreachable is different: the link is kept and the page says since when it couldn't be reached.
  - `cloud: { url: …, ca_file: … }` in `lab.yaml` points a lab at a test Cloud (`ca_file` trusts a test certificate authority); `disabled: true` still turns all of it off.
  - **For development,** Roostack's tests use a fake of the API (`internal/cloud/cloudtest`), and a dev VM links to a development Cloud run from Cloud's repository (since 2026-10-07; `cmd/roostack-fakecloud` did it until the real endpoints existed). The contract both sides import is the public package `cloudapi`. Roostack's default Cloud address is its API, `https://api.roost.ac`; people confirm links on its website, `roost.ac`.
  - **Not yet:** the recovery key's proof for account recovery (Cloud's design: its cryptography first).
- **A roost.ac name as the lab's address — Locked (2026-10-07), as built:** a linked lab claims its name from Cloud (with its certificate) and gets back the full name and **an acme-dns account** that can only write that name's records. Roostack treats Cloud as one more DNS provider (`roostack-cloud`, never offered in the list): the account's fields are its Podman secrets like any provider's, so the rest is unchanged.
  - **Certificates:** Caddy's `caddy-dns/acmedns` module (added to Roostack's Caddy build, chosen 2026-10-07) writes the challenge record through Cloud's acme-dns API, for one wildcard certificate covering the name too. The module reads placeholders only in its password, so the account's other fields (none secret) are kept in `lab.yaml` (`dns.values`) and written into Caddy's config as they are; only the password is a Podman secret (ASSUMPTIONS C13). **Tried for real (2026-10-07):** VM3, linked to a development Cloud publishing to roost.ac's real DNS, got Let's Encrypt certificates for `smiths.test.roost.ac` and its wildcard, both served over HTTPS and verified. Considered: our own Caddy module using the lab's certificate (no extra credential, but our code inside Caddy, and Caddy would need the lab's key). The account can already get certificates for the name, so letting it also set the name's A records (Cloud's records API, same account) adds no power.
  - **Records:** as for an own domain, Roostack manages them: `*.name` and the name itself to the server's home-network address (Roostack's pages are at the name), public services' own records to the home's public address. Cloud allows nothing outside the lab's name, and no public wildcard.
  - **Getting it:** in the address step, **Continue to Roostack Cloud** links the lab (same tab, back again afterwards) and then claims the name by itself; once linked, **Use this address** claims it at once. The lab then restarts with it, the address step done. A previous address keeps working for 30 days, as when switching domains.
  - **A held name** (kept for the account that had it, after its lab was unlinked) isn't refused before linking: until then Cloud can't know whose account is asking, so it says the name is held, Roostack says "if that's yours, you'll get it back once the lab is linked to it", and the claim, once linked, decides (found by trying it, 2026-10-07: unlinking and linking again lost the lab its own name).
  - **Losing it:** unlinking, or Cloud no longer knowing the lab, takes the address away: the lab goes back to "no address yet" (the name stays held for the account for a year, Cloud's side).
  - **Checked when claimed (2026-10-11):** before the lab uses a newly claimed name, it writes a test value through Cloud's challenge API with the new login and waits (up to 45 seconds) to see it at `_acme-challenge.<name>` on the zone's own name servers (not for `.test` names, never in public DNS). A failure says what's wrong and leaves the lab as it was. Without it, a cached certificate would hide broken credentials until the next renewal, two months later. Tried on VM3 against the test Cloud: the claim took 11 seconds, and the certificates for the new name followed.
  - **The suffix comes from Cloud (2026-10-11):** names end in whatever the lab's Cloud says (`GET /v1/info`, asked once a day): roost.ac, a test Cloud's roostack.dev, the fake's roost.test. The pages show it wherever they named roost.ac; until a Cloud has answered they say roost.ac.
  - **Trying it:** the fake Cloud gives names under `roost.test`, so a dev VM goes through everything except Let's Encrypt actually issuing a certificate (it refuses `.test`).
- **Open:** a lab with neither (no domain, not linked to Cloud) beyond "no address yet". Options: stay as it is (services wait for an address), or HTTPS by IP address (§6.3.2, later).
- **Rejected for v1:** a local CA (a root certificate on every device is bad UX); plain HTTP (browser warnings, and some clients such as Bitwarden require HTTPS).

### 6.7 Storage Layout — Locked (defaults may change before launch)

Default paths:

```
/var/lib/roostack/                 # Roostack's own state: desired state, secrets, users
/srv/roostack/services/<service>/  # per-service data (bind mounts)
    data/
    db/
/srv/roostack/media/               # large shared media; can be a separate disk
```

- **Paths are configurable**, and all defaults are defined in **one central place** in the code so they can be changed easily. No migration support is needed before launch; the defaults will be locked before release.
- **Bind mounts, not Podman named volumes.** Data sits in a visible, predictable location (Principle 4), and it's easy to back up and move (Principle 1).
- The media location can be configured separately, e.g. a small system SSD plus a large data drive.
- **Open / to prototype early:** rootless user ID mapping. Files owned by UIDs inside containers appear as mapped IDs (e.g. 100000+) on the host. We need to settle how this affects browsing, backups, and media shared between services (e.g. Jellyfin and Immich), and where Podman's `keep-id` option helps.
- **Disk space — as built (2026-09-28):** each server reports the disk holding its Roostack data (`statfs` of `/srv/roostack`: total, used, free to the roostack user, and what the filesystem keeps back), with what Roostack's parts take: its services' data, the backups it keeps for the lab's servers, and those it keeps for other labs. Free and used space come from `statfs` alone (instant); only the breakdown is counted, with `du -s -B1` (space on the disk, as `df` counts it) at the lowest CPU and disk priority (`nice -n 19 ionice -c3`). `du` reads every file's metadata: quick on an SSD (300,000 files: under a second), but a large photo library on a spinning disk can take a minute or more and fills the kernel's metadata cache. So sizes are counted **once a day, right after the nightly backup**, while restic's reads of the same metadata are still cached, and otherwise only when a size is missing or over a day old (no backups set up, a new service); pages show the last count and when it was made, and never wait for one; while a count runs, the disk block says "counting…" and refreshes itself until it's done (2026-10-03: it said "not counted yet" until the page was reloaded). Settings → Servers shows it for each server, with a bar coloured by part (2026-10-03: services' data, the lab's backups, other labs' backups, the system; then the space promised to other labs and not used yet, striped; then free; and at the far end what the filesystem reserves for the system, striped grey), each part named with its size in a key underneath, and on the server storing other labs' backups, the space promised to them (their quotas) and how much of it they don't use yet. **Low space** is a warning below 5 GB or 10% free, and a problem below 2 GB or 5%, shown on the home page and on Servers; so is having promised other labs more space than is free, and (2026-10-03) earlier, a warning once the space they could still add reaches into the 10% of the disk kept free for the lab's own services and backups. The backup plan shows the free space where each backup is (this server's drives, or another server's disk) and warns when it's nearly full. **Every disk — as built (2026-10-03):** each server reports every disk holding a folder Roostack uses: the system's (`/`), a separate disk for services' data or the backup store, a separate media disk, and each backup drive (the repository folder on it). Folders on the same disk (same device) count once; a disk is named by the most important folder on it (System disk, Data disk, Media disk, Backup drive <name>) and shows where it's mounted when a server has more than one. Each disk's parts are what's on it: services' data split by folder (a service's `services` and `media` folders can be on different disks), the backup store's two parts, and a drive's backups; on a drive the rest is "Everything else". Low space, and the space promised to other labs, are per disk (promised space on the disk holding the backup store), and warnings name the disk when there's more than one ("This server's backup drive BACKUP is running out of disk space"). An unplugged drive isn't listed. Considered: listing every mounted filesystem (most mean nothing to Roostack's user, such as /boot/efi).

### 6.8 Databases — Locked

- **One database container per service** (e.g. Immich gets its own Postgres), not a shared instance.
- Roostack **standardises the pattern**: every package uses the same Roostack-managed Postgres/Redis setup, with the same data location (`<service>/db/`), backup method, health checks and upgrade process.
- **Rationale:**
  - Each app runs the exact database version and extensions it's tested with (e.g. Immich needs specific Postgres versions and a vector extension).
  - Upgrades and failures are isolated to one service.
  - Each service is self-contained, so moving it to another host or Roostack Cloud means moving one folder plus its definition (§4 portability).
  - The cost, roughly 30–50 MB RAM per idle instance, is acceptable on NUC-class hardware.
- **Rejected:** a single shared Postgres. It saves RAM, but it couples versions and upgrades, makes it a single point of failure, and makes backing up or moving one service harder.

### 6.9 Backups — Locked

**Tool: restic**, called as a CLI (`--json` output) behind a small internal interface (backup, restore, list snapshots, prune, check), so the tool can be swapped later.

- **Rationale:**
  - A Go single binary; encrypted and deduplicated, with many backends (local, SFTP, S3, B2, rclone, REST server).
  - Users can recover independently with the plain `restic` CLI and the recovery key, even if Roostack is broken. There's a large community and many docs (Principles 1 and 4).
  - Roostack owns scheduling and retention as part of desired state, so there's no competing policy engine.
  - The append-only `rest-server` gives simple ransomware protection and is a natural future Roostack Cloud target.
- **Considered: Kopia.** It's faster, uses less memory (≈4 MB average chunks vs ≈1 MB, plus a memory-mapped index) and has a richer server. It's a realistic fallback if restic's memory or performance becomes a problem with very large libraries; the interface keeps switching cheap.
- **Expected resources** (estimate, ~750 GB / 100k photos and videos): ~150–400 MB RAM for nightly backups, up to ~1 GB for prune/check. Mitigations: `GOGC=20`, infrequent pruning, a systemd memory limit on backup jobs, quiet-hours scheduling.

**Backup process:**
1. **Prepare:** per-package hooks create a consistent state (e.g. `pg_dump` to `<service>/db-dump/`, SQLite's backup command, or a brief stop if there's no safe live method).
2. **Snapshot:** `/var/lib/roostack` plus each service's folder. Since 2026-10-04, one snapshot per service (tagged `service=<name>`, with its secrets) and one for the server's own state (tagged `server`): see §10.10, "Restoring across the lab".
3. **Verify:** periodic `restic check` and occasional test restores.
4. **Restore — Locked (2026-09-27):** per service, by the Owner, from the Backups page: choose one of the backups that contain the service (newest first), confirm, and it runs as an uninterruptible coordinator job with a live log. The service stops, its current data is moved aside (`<dir>.before-restore-<time>`), the backup's files and database dump come back, and it starts again. If getting the files back fails, the current data is put back (a partial restore is kept as `<dir>.failed-restore-<time>`) and the service starts again; if the data can't be put back, the service stays stopped and the log says where the data is, rather than claiming it's back (2026-09-29: a failed put-back used to go unnoticed and the service stayed stopped either way). Kept copies are listed on the restore page and deleted only when the Owner chooses. Restoring a whole lab onto a new server comes with the installer.

**Restore:** per service, or the full lab onto a new server (install Roostack → point at the backup → enter the recovery key).

**Full-lab restore — as built (2026-09-28):** on a fresh install, the first-run page offers "Restore a lab from its backups" next to creating the Owner (both need the setup code). The Owner says where the backups are (an S3-compatible bucket, a disk mounted on the server, or any restic address) and enters the recovery key; Roostack looks for every server's repository there (`roostack/<lab>/<server>`, a few levels deep for a disk), opens each with the key and shows the lab, server and latest backup of those it opens. Only the controller's (or a single server's) backup can be restored: its files go back where they were (Roostack's state, Podman secrets, every service's data, owners included), the recovery key becomes the backup key, and Roostack restarts. At that start the backed-up copy of Roostack's database becomes the live one (same accounts, settings and server identity); once the first apply has set the services up again, each service with a database is stopped, loaded from its dump and started, while "needs attention" says so. Backups carry the servers' WireGuard keys (`wireguard-keys.json`, kept by Roostack like the CA key), and the agent reuses a saved key for an interface that has none, so a restored controller keeps the keys its nodes and friends' labs know; they reconnect if they can reach it the way they reached the old one. Backups then continue at the lab's configured destination. Not yet: restoring from storage at a friend's lab (its link is in the lost state), and restoring a node on its own (restore the controller, then move the node's services).

**Defaults & policy:**
- Nightly; keep 7 daily, 4 weekly and 6 monthly.
  - **Two copies of one lab — as built (2026-10-04):** a full-lab restore makes the new machine the same lab (IDs, keys, domain), so if the old one comes back (it was only offline), both would back up into the same repositories and update the same DNS records. Fencing: the lab has a generation (`lab-generation` in the state folder, backed up with it), which a full-lab restore raises; every snapshot is tagged `gen=<n>`; before uploading, a server lists its repository, and a snapshot of a newer generation means this copy is out of date: it stands down (no backups anywhere, no DNS updates; a problem on Home and its Backups page, which explain). Its services aren't stopped: a false alarm mustn't take anything down. "This is the right copy → Keep this copy" (Owner) raises its generation past the other's, so the other stands down at its next backup (a test restore that fenced the real lab). The same mark serves a server the controller removed while it couldn't be reached (a gone server, once nothing waits on it): the controller adds a `fence=removed` snapshot to its repositories, and if it comes back it stands down and its own page says it was removed. Considered: a new ID for restored services (the clash is the lab's and its servers' identity, not a service's; and it would cut their backup history); stopping the old copy's services (a false alarm would take the lab down). Not covered: an old copy that can't reach its backups at all (it then can't harm them either; DNS is the remaining risk).
  - **When "nightly" isn't simple — as built (2026-10-04):** the time is the server's local 02:00. On the night clocks go forward it runs at 03:00 (02:00 doesn't exist), and on the night they go back at the second 02:00: once either way (checked with Australia/Sydney). The schedule looks at the clock every minute rather than waiting once, as Go's timers don't count time asleep: after a suspend (or a paused VM) the backup runs as the machine wakes, not hours late. A night the server was off is caught up: 10 minutes after Roostack starts, then hourly, a backup runs if none was tried for 26 hours (an attempt counts: failures have their own retries). The controller's weekly clean-up tries a repository that's locked (its server still backing up, e.g. a big first backup) again an hour later, up to three times. Considered and left: starting each server's backup a few minutes apart (they share a destination only sometimes), and waiting for the clock to sync at boot (a machine without a clock battery; not a NUC).
- Packages classify data as **critical** (backed up by default: photos, passwords, repos) or **replaceable** (not backed up by default: media libraries, caches).
- **Destinations:** local disk, remote (S3/B2/SFTP), and Roostack Cloud (below). **Local-only is allowed, with a persistent warning** recommending off-site.
  - **Roostack Cloud backup — as built (2026-10-13):** for a lab linked to Roostack Cloud, the chooser offers "Roostack Cloud: off-site, set up for you", with the lab's use of its space ("This lab uses 1.2 GB of 50 GB"). It is online storage in Australia that Cloud runs; each server gets its own folder there, and backups are encrypted with the recovery key before they leave, so Cloud can store them but not read them. Nothing to configure: no account, keys or address to type. How it works:
    - **Short-lived keys.** No server keeps a storage password. Before each backup a server asks for keys that last 12 hours and open only its own folder, and only to add backups (they can't delete). The controller asks Cloud over its link (§4); any other server asks the controller over the lab API (`POST /v1/storage-keys`, mutual TLS), so nodes never talk to Cloud themselves. Keys are kept 0600 in the state folder (`cloud-backup-keys.json`), renewed when under an hour is left, and used while more than 5 minutes are left if Cloud can't be reached meanwhile. They're left out of the lab's own backups (they expire, so a copy is no use).
    - **The lab prunes, Cloud never holds a restic key.** Like every destination, the controller prunes each server's repository weekly with the recovery key. For that it asks Cloud for the lab's prune keys (`cloud-prune-keys.json`), which may delete within the lab's folders only. Cloud keeps deleted and overwritten files for 90 days, so neither a compromised server nor a stolen prune key can destroy backups at once.
    - Considered: one long-lived storage key per server (a key leaked from a backup or a stolen disk would work until someone noticed), and Cloud pruning for the lab (Cloud would need a key that opens the backups, which breaks "Cloud can't read it"). restic exits 0 when a delete is refused, so tests check the snapshots, not the exit code.
    - Not yet: a second, archived copy kept by Cloud (see TASKS).
  - **Restoring from Roostack Cloud — as built (2026-10-13), the user agreed the design the same day:** after losing the controller (a fire, a dead disk), a fresh install's "Restore a lab" page offers "Roostack Cloud", which needs only the recovery key: no account login, address or keys. It rests on the lab's **recovery identity**, an Ed25519 key derived from the recovery key (HKDF-SHA256; the key is 256 random bits, so no slow password hashing is needed). The controller registers the public half with Cloud when it links, at each daily check-in if it changed, and as soon as a new recovery key replaces the old (the old key then stops working with Cloud too). To restore, Roostack asks Cloud for a challenge, signs it, and gets keys that read the lab's folders (12 hours, as a big restore takes hours; they may write only restic's locks) and the list of its servers' repositories; the usual search and restore follow. The recovery key never leaves the server. Anyone with the recovery key can already decrypt every backup, so reading them gives nothing more away; Cloud still emails the account each time, with where from and what to do if it wasn't them (change the recovery key).
    - **Relinking:** the restored controller's backup holds its Cloud certificate, which usually still works (certificates last 90 days and renewing doesn't cancel the old one). When Cloud refuses it (expired while the lab was off, or a restore from an old backup), the daily check signs a challenge to get a new certificate instead of forgetting the link, at once rather than after a waiting period (the user's choice: someone restoring after a fire needs their address back now; the email lets the real owner react). It must be the same lab, and Cloud refuses it for a lab that was unlinked on purpose: that one links again as usual. Its backups can still be read while Cloud keeps them.
    - Signatures are for one purpose ("access" or "relink" is part of what's signed), each challenge works once for 5 minutes, and proving is rate-limited in Cloud, per address and per lab (2026-10-13). A relink refused because Cloud is busy (rate limited, or failing) keeps the link and tries again at the next check; only a refusal forgets it.
    - Considered: logging into the Cloud account to restore (it needs no new cryptography, but the person restoring often isn't the account's owner, and account recovery may be the very thing lost; it may come later as a second way); Cloud holding a copy of the recovery key (it could then read the backups, which breaks "Cloud can't read it").

### 6.10 Host Security — Locked

Layered defaults:

1. **Firewall:** default-deny inbound. Allow 80/443 plus ports that specific services need (e.g. WireGuard, Pi-hole DNS on the LAN). `roostack-agent` generates a readable **nftables** ruleset file and reloads it (nftables is Debian 13's default, so no extra dependency).
   - **SSH access — Locked (2026-09-27):** the Owner chooses in the setup wizard (step 2) and in Settings: home network only (recommended, default), anywhere, or nobody. The page lists current SSH connections (read from `/proc/net/tcp`) and a choice that would cut one off must be confirmed. Stored in `lab.yaml` (`firewall.ssh`).
   - Roostack applies the firewall after every apply, so enabled package ports are opened (home network only unless public). Until the SSH question is answered, Roostack leaves the firewall alone.
2. **Admin UI is LAN/VPN-only by default.** Public access requires explicit opt-in **and** mandatory 2FA. Rationale: the UI controls the whole host and is the highest-value target.
3. **SSH hardening:** key-only authentication, no password login, no root login. Applied by the installer with a warning and confirmation to avoid lockout. The user can opt out, but **the UI shows a persistent warning** while hardening is disabled.
4. **Intrusion protection: CrowdSec**, enabled automatically once any service is public. It uses a Caddy module ("bouncer") to block at the proxy, and scenarios for Caddy and SSH logs. Not run on fully private labs (little benefit, saves resources).
   - **fail2ban is not run alongside it.** CrowdSec covers the same local log-parsing and banning, and running both would mean duplicate bans, two configs, and two tools changing the firewall.
   - **Signal sharing: on by default, opt-out.** Opting out is a **prominent choice when something first goes public** (changed 2026-09-30 from "during install", since CrowdSec only runs from then on; §6.11), and can be changed later in Settings. Only attack data is shared (attacker IPs, attack types, timestamps), nothing about the user's own users or data.
   - **If the user opts out:** local detection and banning keep working fully, like fail2ban but with better parsers and blocking at the proxy. They lose the community blocklist, i.e. pre-emptive blocking of IPs already seen attacking others. Rule and parser updates from the CrowdSec Hub are separate and still work.
   - **Web application firewall (WAF) — Locked (2026-10-06), not built yet:** adopted, not built from scratch. A WAF reads requests (paths, headers, bodies), so it runs where TLS ends: in the lab's own Caddy, in front of each public service. That protects every public lab, whether its traffic comes through port forwarding, its own VPS or an edge (an edge never decrypts, §10.5).
     - **First: CrowdSec's AppSec component, on by default for public services.** Its "virtual patching" rules block exploits of known vulnerabilities in popular apps (often before people update), with few false positives since they target specific exploits. It uses what's already running (CrowdSec and its Caddy bouncer, item 4); *to verify:* that the bouncer version we pin passes requests to AppSec.
     - **Later: generic rules (the OWASP Core Rule Set), per service:** broad protection (SQL injection, cross-site scripting and so on) but notorious false positives on modern apps (large uploads, JSON APIs, sync clients). Run in "detect only" first, and each catalog package ships the exclusions it needs (e.g. no body inspection on its upload path), tested with the package. That per-package knowledge (logins, uploads, exclusions) is Roostack's contribution, alongside the login paths it already rate-limits.
     - **Considered:** Coraza (the OWASP engine, with a Caddy module) running the Core Rule Set directly: a possible engine for the later step, but a new Caddy plugin (a dependency to agree). ModSecurity, BunkerWeb, open-appsec and SafeLine are built around other proxies (nginx, Apache, their own), a poor fit for Caddy.
5. **Baseline:** automatic security updates (§3.2), Caddy rate limiting on login pages, secrets in files readable only by Roostack (0600), and container images only from trusted registries, pinned to specific versions.
6. **Wrong two-factor codes — as built (2026-09-29):** limited per account, not per login, since someone with the password could otherwise log in again for more tries. Every fifth wrong code in a row locks the account's codes (even the right one) for 15 minutes, doubling each time up to a day; the right code resets the count. That leaves a guesser about five tries a day, while someone mistyping waits 15 minutes. The count is in the database (a restart doesn't clear it), covers the login and the recovery key page (§6.9), and each lock is audited; the password step says so when locked, telling people that wrong codes they didn't enter mean their password is known. Checks run one at a time, so parallel guesses can't slip past. `roostack user reset-2fa` ends a lock. Considered: a limit per login (what we had; it limited nothing), locking the whole account (the lock is only on codes, so it can't be used against an account whose password the attacker doesn't have), and relying on Caddy's rate limiting alone (per address, so it doesn't stop guesses from many addresses).

### 6.11 Public access — Locked (2026-09-30), details Open

Nothing is public unless the Owner makes it so (§1 principle 6). The Owner makes one of a service's addresses public from the service's page; the Roostack UI itself stays private (§6.10 item 2).

- **Ways in ("entries"), all to be supported:**
  1. **Port forwarding at home:** the router forwards TCP 80 and 443 (and UDP 443) to the server; public records point at the home's public address. Built first: it needs nothing beyond the home router.
  2. **Through a cloud server in the lab** (an "edge", §10.5): no router change, and the home's address stays hidden.
  3. **Through Roostack Cloud** (later, §4): the same edge mechanism, run by Roostack Cloud, for people without a cloud server of their own or behind CGNAT.

  A service that runs on a cloud server is reached at that server directly. The entry is a seam in the code from the start (where public records point, and how traffic reaches the service's server), so 2 and 3 slot in without reworking 1.
- **Changing it — as built (2026-10-01):** making an address public asks for confirmation (a dialog, like other hard-to-undo actions); making it private again uses a red confirm button. While it's public, the package's private parts can be opened or closed again ("Parts kept private"); links into the app that lead to a private part say who can open them. "Home only" became "Private", explained for each kind of lab.
- **What can be public:** packages mark addresses that aren't safe to make public (admin pages, APIs meant for home), with the reason. The Owner can still make one public, after a warning that gives the package's reason and a tick to confirm; the override is audited. Considered: never allowing it (too rigid for technical Owners who know what they're doing); allowing anything with no mark (non-technical Owners can't judge an admin page's risk).
- **Protection first:** CrowdSec and Caddy's rate limiting (§6.10) run before anything goes public, and the switch waits for them. Dependencies agreed (2026-09-30): the CrowdSec container, and two Caddy plugins, `caddy-crowdsec-bouncer` and `caddy-ratelimit`.
- **Checking it works from outside:** for now, the Owner checks from a phone on mobile data (on a lab on the internet, from any browser, §6.12). Roostack Cloud will check automatically later. Considered: port-checking websites (they learn the home's address and domain); checks from the lab's own cloud servers (maybe later).
- **DNS:** each public address gets its own record pointing at the entry's public address, overriding the private wildcard (§6.5.1 stage 2).
- **The home's public address — Locked (2026-09-30):** found with a DNS query (OpenDNS's `myip.opendns.com`, Cloudflare's `whoami.cloudflare` as a fallback), checked every few minutes, and public records updated by Roostack's own record code (§6.5.1), with the same ownership tracking. This replaces ddns-updater (§6.5.1 stage 2): one less container, and one owner for every record. Considered: ddns-updater (more providers, but a second writer to the same zone); HTTP "what's my IP" services (they see every check).
- **CrowdSec signal sharing — Locked (2026-09-30):** asked in the "Protection" step the first time something goes public (CrowdSec only runs from then on), not during install (§6.10 item 4 updated), and changeable later in Settings.
- **CrowdSec and SSH — Deferred (2026-09-30):** CrowdSec reads Caddy's logs only for now. The rootless container can't read the host's journal, and SSH is home-network-only by default. To revisit: the agent passing SSH log lines on, or blocking with nftables (TASKS.md 1.18).
- **Rate limits — Locked (2026-09-30):** every public address gets a generous limit per visitor address, and the login pages a package names get a strict one.
- **As built (2026-09-30):**
  - Packages: `routes.<r>.public` with `unsafe` (a reason), `private_paths` (each with a reason) and `login_paths`; the Owner's opened paths are the instance's `public_paths`.
  - Caddy, for a public address, in one `route` block: private paths refused to outside visitors, CrowdSec's bouncer, 1000 requests per 10 s per visitor and 10 a minute on login paths, then the service. The only path that reaches Roostack is the check link (a 32-digit token).
  - While anything is public, the lab runs CrowdSec (pinned image) reading Caddy's JSON access log; the bouncer's key is a generated Podman secret. The sharing opt-out travels in the assignment.
  - The entry is `internal/public.Entry`; port forwarding finds the home's address over DNS. `dnsrecords` sets each public address's record once CrowdSec's health check answers, re-syncing every 5 minutes (30 s while waiting), and points it home again when the address goes private: the providers' record APIs can't delete yet.
  - UI: "Reachable from" on the service page; a page per address (warning, reasons, private paths, the sharing question, then the checklist: protection, DNS record, the router, the phone check); Settings → Public access. Owner only, audited.

### 6.12 Where the lab is: at home, or on the internet — Locked (2026-09-30)

- **Why:** Roostack assumed every lab sits behind a home router. On a cloud server (a VPS) that's wrong everywhere: "home network only" meant the provider's private network (shared with other customers) or nobody; the public checklist asked about a router and a phone on mobile data; DNS talked about home. Found running a lab on a Linode (2026-09-30).
- **The setting:** `network` in `lab.yaml`: `home` (the default) or `internet`. It's about the controller, whose Caddy serves the lab's addresses: a cloud server that joins a home lab needs nothing, since the controller at home serves its services. Asked in the wizard's first step ("Where is this server?", with the time zone), changeable in Settings → Where it is and DNS (Roostack restarts).
- **Detected, then confirmed:** a public IPv4 address on one of the server's own interfaces suggests "on the internet" (IPv6 isn't counted: home servers often have public IPv6 addresses behind the router). A cloud server behind its provider's NAT (some AWS or Oracle setups) looks like home, so the Owner confirms. While nothing is saved and the server looks like a cloud server, Home and Settings say so.
- **On the internet — Decided (2026-09-30) by the project's Owner:**
  - **Private means only through an SSH tunnel**, and the UI says so plainly: a private service's page says "Only through an SSH tunnel (for technical users)", linking to the help's steps (tunnel to the server's port 443, a hosts-file line, open the address). Caddy's private addresses become "this server only": loopback, the server's own address (a tunnel's requests, to the host's 127.0.0.1, reach Caddy's pasta network from it) and pasta's host-loopback address (docs/ASSUMPTIONS.md P9). The provider's private network isn't allowed.
  - **Services start public** (the install form's "Anyone on the internet can reach it", ticked, with the CrowdSec sharing question the first time), except addresses their package marks unsafe, which start private. Rejected: private by default (unusable without a tunnel); waiting for a Roostack VPN for the Owner's devices (a bigger feature, later).
  - **The UI is public** at `roost.<domain>` unless kept to a tunnel (§6.3.2). So CrowdSec can start before anything has asked about sharing attack reports: it shares nothing until the Owner answers (on the first install form or public-access page), on any lab.
  - **DNS:** the wildcard `*.<domain>` points at the lab's public address (from the entry, so a provider's NAT doesn't matter) and covers public services: no per-service records, and nothing waits for CrowdSec. Messages talk about "this server", not home.
  - **Public access checklist:** protection, DNS, **your provider's firewall** (naming Linode, Hetzner, AWS, DigitalOcean and Oracle Cloud; TCP 80 and 443, UDP 443) instead of the router, and **a check from any browser** instead of a phone on mobile data.
  - **SSH** defaults to "from anywhere" (recommended there); "only from private networks" says it would need the provider's console to get back in.
- **Both kinds of lab:** when the check link doesn't open, the page lists what to look at, in order: Roostack's firewall (always open for web traffic), the router or provider firewall (Roostack can't see it), public DNS (checked), and at home whether the connection takes incoming connections at all (CGNAT).
- **Checking from outside — Locked (2026-10-06), not built yet:** a lab linked to Roostack Cloud can ask Cloud to check it from the internet, as a visitor would: public services work (public DNS, port 443, a valid certificate for the name, the right app answering); **private services are *not* reachable** (a mistaken port forward or a router's UPnP would otherwise go unnoticed: flagged as a problem at once); risky ports open on the home's public address (a short list: SSH, databases, remote desktop, router and NAS admin); later from each region. Checks run on demand ("Check from outside now", offered right after a service's public setting changes); scheduled checks are a Cloud plan feature. Roostack's side: "Reachable from outside: checked today 09:14" on each public service, problems in the attention list and by email. Cloud only checks names the lab has proven it controls and the address the lab connects from. **Without Cloud,** the manual check (a phone on mobile data) stays.
- **Later:** a warning when home DNS answers a public address with something else (the "overridden" check applied to public names). Package ports ("extra connections") on a lab on the internet: "home network" there means the provider's network.

### 6.13 Email and notifications — Locked (2026-10-03)

**Sending — as built (2026-10-03):** Settings → Email (Owners) sets the SMTP server: host, port, STARTTLS (587, the default) or TLS (465), username, password, and the sender address (suggested: `no_reply@<domain>`, once the domain is set up). The settings are in `lab.yaml` (`mail:`); the password is in its own file (`mail-password`, 0600), never shown again ("leave empty to keep it", or "forget the saved password"). The password is only sent over an encrypted connection: a server that doesn't offer STARTTLS is refused with a sentence suggesting TLS. Messages are plain text (UTF-8, quoted-printable) and marked `Auto-Submitted: auto-generated`. "Send a test email" sends one, to your own address by default, and says which step failed if it didn't (reaching the server, the login, the sender, a recipient). Each person sets their own address on their account page; empty means no email. Only the controller sends (it knows the whole lab). The standard library's SMTP client is used (no new dependency); it's frozen but complete for this. Checked against Fastmail from VM1. Considered: a relay service's API (another account and dependency), and sendmail on the host (needs a local MTA, more to secure).

**Notifications — Locked (2026-10-03), as proposed; as built the same day (below the table).** Baseline: **email when something needs a person, or when something important happened while they weren't looking; never for routine success.** Most of it already exists as "needs attention" on the Home page, so the proposal is to email those items, once, with a few security events added.

*What, and to whom by default:*

| Group | Events | Owner | Admin | Member |
|---|---|---|---|---|
| **Problems** | A backup failed after its retries ran out, or none finished for two days; an extra backup failing; a disk running low or other labs' promised space reaching into what's kept free; a server unreachable for 15 minutes; a service down or restarting in a loop for 15 minutes; OS updates failing; a certificate that can't be renewed; DNS records in conflict; storage at a friend's lab removed, or its backups there deleted | on | on (services, backups, disks) | off |
| **Waiting for you** | A restart waiting (notify-only mode), for more than a day; service updates that need approval; a recovery key change waiting on a backup that can't be reached | on | on (service updates) | off |
| **Security** | Your account: a password or two-factor change, a reset from the command line, a login from a new device, two-factor locked after wrong codes. The lab: a new Owner or Admin, a server joining, another lab starting to store here | on | on (own account) | on (own account) |
| **Weekly summary** | Backups made, space used and trend, updates installed, attacks blocked on public services, anything still needing attention | off | off | off |

*How:*
- **One email per problem**, when it has lasted a few minutes (so a blip that fixes itself sends nothing; retried backups only once the retries are over), then **a daily reminder** while it lasts, and **"It's fixed"** when it clears. Several problems at once go in one email.
- Each email says what happened, what Roostack already tried, and what to do, with a link to the page (the "needs attention" sentence, plus detail). Plain text; no tracking.
- Security emails go straight away, without waiting or grouping.
- Members never get lab problems: they can't act on them.

*Configurability (proposed):* each person chooses, on their account page, which **groups** they get (Problems, Waiting for you, Security, Weekly summary), with the defaults above; Security about their own account can't be turned off. Per-event switches considered and not proposed: too many choices for the people Roostack is for; groups cover "too much email". Owners can see who gets what on Settings → Email. Later: other channels (ntfy or similar push) as another way to receive the same notifications.

*As built (2026-10-03):* a notifier on the controller runs every minute. Problems and things waiting come from "needs attention" as each person would see it on Home (so roles filter them the same way), problems and warnings only; an item is the same problem while its link and its words are, numbers and times aside ("3.0 GB free" and "2.9 GB free" are one). Problems are emailed after 10 minutes, things waiting after a day; reminders daily; "Fixed" once an emailed item clears. "Needs attention" gained "<service> has stopped working" (systemd gave up restarting it). Security events come from the audit log (so command-line resets count too): password changed, two-factor turned on, a password or two-factor reset (to the person, and to Owners), codes locked after wrong tries (newly audited, at login and when checking it's you), a login from a new browser (a long-lived device cookie, `devices` table; not for someone's first login), a new Owner or Admin, a role changed to one, a server joining, another lab starting to store here (both newly audited). The first run starts from the newest audit entry: history isn't emailed. One email per person per run, subject "[Lab name] Security: …" / "Needs attention: …" / "Still needs attention: …" / "Fixed: …", with links to `roost.<domain>`. The weekly summary goes on Monday from 8 am: each server's last backup and disks, and anything still needing attention. Groups are chosen on the account's Email and notifications page; Members see only the line that their own account's security emails always come. Nothing is sent until Settings → Email is set up; problems start being followed once it is. The account became area pages with a sidebar like Settings (Your account, Two-factor, Email and notifications, Appearance), tabs on phones. Settings → Email lists who gets what (each person's address and groups). The weekly summary also says what CrowdSec saw on the public addresses that week (`cscli alerts list --since 168h` in its container: attacks, from how many addresses, how many blocked, the commonest kinds), when CrowdSec is running.

*Changed (2026-10-08), after a day of alternating "Needs attention" and "Fixed" emails about a server that had gone* (a test VM reinstalled as a lab of its own, still listed in another lab): **"Fixed" waits as long as a new problem does** (an emailed item must stay gone 10 minutes; the controller's retries showed the server as "applying" for a moment, which had counted as fixed); **items can carry their own key**, so an error whose words change between attempts stays one problem (a failed change is keyed by its server); and **a server that can't be reached has its own item**, "Roostack can't reach <server>. It may be switched off, or its network down.", linking to its server, instead of "the last change didn't finish" with whichever network error the last attempt got.

### 6.14 History — Locked (2026-10-03), as built the same day

Nothing Roostack does should look like magic, afterwards too. **Settings → History** (Owners) lists, newest first:
- **What Roostack did** on each server: every finished log of work in the background (applying changes, backups, updates, restores, moves, backup set-ups), with its full output ("Log"), how long it took, and whether it failed. Each server keeps its own in its database (`events`), and the controller asks each one (lab API `/v1/history`). Runs that changed nothing (most applies at start-up) are "routine": shown as the latest on Settings → Servers, not kept.
- **What people did**: the audit log (logins, installs, settings, account changes), kept on the controller.
- A filter by kind, and "Older" for paging back.

**Applying changes says why** it ran: the controller sends a reason with each assignment ("Installing forgejo", "Changing who can reach vaultwarden", "Roostack started (after a restart or an update)"), and the server's log starts with it, then what it did, or "Nothing to change". Settings → Servers shows each server's latest apply under its Changes, live while it runs, and Home's "Applying changes…" links there.

**Limits:** history is kept for 30 days, 90 (the default) or a year, the Owner's choice; older history is deleted every day on every server (the controller asks each), and at once when the choice shortens. Each server keeps at most 5,000 events, and each event its log's last 2,000 lines (at most 256 kB). "Delete all history" deletes everything on every server; the deletion is then audited, so there's a trace. Considered: a size limit in megabytes (harder to explain than days and a count), and keeping everything forever (the database grows without bound on a small server).

## 8. Service Definitions & Catalog — Locked (principle)

- The service definition format is user-facing from early on (custom services is a nice-to-have; the planned registry, §8.3, makes them its "local" tier).
- Breaking changes to the format are acceptable before 1.0.
- **Official packages are curated and opinionated.** Upstream `docker-compose.yml` files are a starting reference, not something we import directly. Each official package includes Roostack-specific configuration so it runs production-ready in the Roostack ecosystem:
  - automatic TLS / reverse proxy wiring
  - backup definitions (what data to back up, how to quiesce it)
  - use of Roostack-managed shared resources (e.g. common databases)
  - standard storage locations
- **Rationale:** Upstream compose files are rarely production-ready as a one-click install. Being opinionated is what makes one-click install and management reliable for less technical users.

### 8.1 Format — Locked (initial; may be revisited)

- **Two file kinds:**
  - **Package** (`catalog/<name>/package.yaml`): authored by Roostack or the community. Describes how to run the app well: containers, settings, storage, databases, routes, health checks.
  - **Instance** (`/var/lib/roostack/services/<name>.yaml`): the user's choices (package version, subdomain, exposure, setting values, update policy). This is part of desired state.
- Roostack combines package + instance and **generates** Quadlets, Caddy site snippets, and backup jobs.
- **Our own YAML schema** (`schema: roostack/v1alpha1`) models what Roostack needs to understand, with a **raw Quadlet passthrough** for unusual needs.
  - Rejected: packages shipping Quadlet templates plus a manifest. Every package would do things differently, and Roostack couldn't reason about them as well.
- **Backups are declared, not scripted:** `databases` entries (`sqlite`, `postgres`, …) and `storage` classes (`critical` / `replaceable`) drive Roostack's standard backup methods.
- **Secrets** are declared (optionally `generate: true`) and delivered as Podman secrets, so they never appear in generated unit files.
- **Images are pinned** by tag + digest. Roostack's own images too (2026-09-29): rest-server by digest, and the Caddy image, built on each server, from base images pinned by digest and DNS plugins pinned by version (`build/caddy/Containerfile`). Digests are the multi-arch index, so the same pin works on ARM.
- **Templating:** Go templates (e.g. `{{ .Routes.web.Host }}`, `{{ .Settings.x }}`).
- **Versioning:** `<upstream version>-roostack.<package revision>`.
- **Additional schema features** (from the Immich stress test):
  - **`when:` conditions** on containers and devices, for optional components (e.g. Immich machine learning), so disabled features don't use RAM.
  - **`devices:`** as abstract requests (e.g. `gpu: intel`) that Roostack maps to device paths and groups (rootless `/dev/dri` needs `keep-groups`).
  - **`depends_on:`**, which becomes systemd ordering (`After=`/`Requires=`).
  - **Route options** at the Caddy level (e.g. `max_body_size`; more expected: timeouts, websockets).
  - **Storage `location:`** (e.g. `media` → the large data disk) and **per-directory storage classes**, so regenerable data (thumbnails, transcodes, caches) is excluded from backups.
  - **Database `image` override** for custom builds (e.g. Immich's Postgres), still following the standard database pattern; **`backup: false`** for transient stores (e.g. Redis job queues).
- **`ports:` — Locked (2026-09-26):** for protocols Caddy can't proxy (SSH, DNS, WireGuard), a package declares a container port with a title, a suggested host port (≥1024) and a protocol. Ports are **off unless the package enables them**; an Admin turns them on per service and can move them. Enabled ports are published on every host address (`PublishPort=<host>:<container>/<proto>`) and are **private** (home network only) via the firewall. Public ports come with the firewall and CrowdSec, like public routes. Roostack rejects clashes with other ports, the UI port and the web-service range (20000–29999). Templates see `{{ .Ports.<name>.Enabled }}` and `.HostPort` (e.g. for clone URLs).
- **`hooks:` — Locked (2026-09-27):** commands run inside a service's container.
  - `on: install` runs once after the first successful start (e.g. creating Forgejo's admin). It is retried while the app starts, so it must be safe to re-run; a failure shows under "Needs attention" with **Try again**.
  - `on: action` is a button on the service page for Admins (e.g. "Reset a password"), with optional `inputs` (string or secret).
  - User-provided values reach hooks **only as environment variables** (`env:` templates, `secrets:`), never templated into the command, so they can't change what a shell script does.
  - Settings can be `required`, have a `min_length`, and be `install_only`: asked at install, used only by install hooks. An `install_only` secret is **deleted once the install hooks succeed**, so Roostack doesn't keep a copy of e.g. the admin password.
  - Only `install` and `action` for now; `upgrade` hooks when a package needs them.
- **Service settings — Locked (2026-09-27):** most of an app's settings stay in the app. Packages list `links:` into its own admin pages (Forgejo's site administration, Vaultwarden's admin panel), shown first under Settings on the service page. Roostack's own settings (not secrets, not `install_only`) and the web address are editable there; saving regenerates and restarts the service. A secret marked `reveal: true` (e.g. Vaultwarden's admin token) can be shown to Admins on request, and each view is audited.
- **Future:** storage shared between services (e.g. Jellyfin reading Immich's library, read-only); package upgrade notes and migration steps for upstream breaking changes.
- **Reference examples:** `docs/examples/vaultwarden.yaml` (simple), `docs/examples/forgejo.yaml` (Postgres, an optional SSH port), `docs/examples/immich.yaml` (complex).

### 8.2 Several copies of a package — Locked, as built (2026-10-04)

Any package can be installed more than once (two Forgejos at different addresses, say), each copy treated as a separate service in everything.

- **Every installed service has an ID that never changes**, separate from the package it's an instance of: the instance file's `name` (the file is `<name>.yaml`); empty means the package's name, so the first copy is called after its package (`forgejo`) and nothing changes for it. Units, the Podman network, secrets, database names, data and media folders, Caddy's site file, backup tags (`service=<name>`), setup progress and the UI's URLs (`/services/<name>`) all use it. The package (`package:`) is what it runs.
- **People see a title**: the instance's `title`, or the package's. The ID is shown only where it matters (Details, folders).
- **Its name starts with its package's (decided 2026-10-04):** an ID is the package's name, or that, a dash and more (`forgejo`, `forgejo-work`; lowercase letters, digits and single dashes, up to 40 in all). So names say what they are in folders, containers and backups, and a package's own name is always free for its first copy. Considered: any name (a Vaultwarden called `immich` would take Immich's name).
- **Installing:** every install asks for a title (the package's by default) and the name's own part after `forgejo-` (empty for just `forgejo`), which follows the title as it's typed ("Forgejo (work)" gives `work`, the package's title taken out) until it's edited, and the web address follows the name (`git-work`) until that's edited. The catalog's "Add another…" on an installed package starts at "Forgejo (2)", `forgejo-2` and `git-2`. A name or address already used is a form error.
- **Renaming:** the service's page changes its title ("Rename"); its name is shown there and stays.
- **Considered:** renaming a service's ID later (it would mean renaming units, folders, secrets, databases and backup tags: rejected; the title changes instead); one set of data shared by copies (not what copies are for).

### 8.3 Service registry — Locked (2026-10-13), not built

**What the Owner asked for (2026-10-13):** a proper registry of services: every package Roostack can install (not only the hero services on roostack.cloud/services), each with its definition file, and a way for the community to add their own. Planned the same day with options for each question; the Owner decided most of them (each subsection says which). The rest was decided in a second and third round the same day; the index's format was locked last (8.3.3). Nothing here is built, except where a section says so.

**Where things stand (checked in the code, 2026-10-13).** These shape the plan:

- The catalog is `docs/examples/*.yaml`, copied into the `.deb` as `/usr/share/roostack/catalog/<name>/package.yaml`: **one version of each package per Roostack release**.
- An instance must name exactly its package's version (`instance.Validate`). So a release that bumps a package makes services already installed from it invalid, and §7's service updates aren't built yet.
- **The package isn't part of the lab's desired state.** Backups hold the instance files but not the packages they used, so restoring onto a Roostack with a newer catalog can't find the version the instance names. That breaks principle 1 (recoverable by default) as soon as packages change between releases.
- **Raw Quadlet passthrough accepts any key** in the `Unit`, `Container`, `Service` and `Install` sections. `Volume=` with a host path or `PodmanArgs=` could reach anything the `roostack` user can: every service's data, secrets and the lab's own files. Fine for packages the project writes; not for packages from strangers.
- An image not pinned by digest is only a warning.
- Packages carry no facts about the project itself (licence, website, source, maker, icon). The website's Services page keeps them by hand (`site/src/data/services.ts` in the roostack-cloud repository).
- Nodes already receive their services' package files from the controller over the lab API (`node/wire.go`), so only the controller needs to know where packages come from.

#### 8.3.1 The lab keeps the packages it uses — Locked (2026-10-13), a prerequisite

Whatever else is chosen: when a service is installed or updated, the controller **copies the exact package file into the lab's desired state** (e.g. `/var/lib/roostack/packages/<name>/<version>.yaml`), and generation reads that copy, not the catalog. It is backed up with the lab and replicated like the instance files.

- **Why:** a restore then needs nothing but the backup (principle 1); a newer catalog never changes a running service behind the Owner's back; local and community packages (below) work the same way as official ones; and the Owner can see exactly what is running (principle 4).
- The catalog becomes only *what can be installed*; the lab's copy is *what is installed*. Copies no service uses are deleted.
- **Considered:** keeping every past version in each release's catalog (grows forever, and still fails for packages that didn't come from a release).

#### 8.3.2 Where definitions live — Locked (2026-10-13): their own Git repository, from the start

| Option | For | Against |
|---|---|---|
| **A. This repository** (`catalog/<name>/package.yaml`, out of `docs/examples`) | No new infrastructure; package and generator change together; golden tests next to the code | Every package fix waits for a Roostack release; community pull requests mix with Roostack's own; the repository's licence and review rules apply to packages |
| **B. A separate public Git repository** ("the registry repository": [`roostack/services`](https://github.com/roostack/services), created by the Owner 2026-10-13) | Transparent: every package and every change is a reviewable commit, forkable; packages can be fixed between releases; contributors don't need to touch Roostack's code; its CI builds the index (8.3.3) and the website reads it | A second repository to keep in step (its CI checks out a Roostack version to validate and render) |
| **C. A registry service on Roostack Cloud** (uploads, an API, a database) | Accounts, download counts, ratings | A lab would depend on Cloud to find packages, against principle 3 (local-first) and the rule that everything works without Cloud; server code to run and secure; less transparent than Git |

**Decided: B, right away** (the Owner, 2026-10-13). The packages move from `docs/examples` into the registry repository, not into a `catalog/` folder here first, so there's one move and package fixes never wait for a Roostack release. This repository keeps a few small packages as test fixtures for the generator's golden tests; releases bundle a snapshot of the registry (8.3.3). The registry is static files, so anyone can mirror it; Cloud may mirror it too, but is never needed.

- **Considered:** A first and splitting later (the earlier leaning: one place while the format moves fast, but two moves, and the split would come when it's busiest).

#### 8.3.3 How a lab finds and updates packages — Locked (2026-10-13): a bundled snapshot plus a signed index fetched when online

| Option | For | Against |
|---|---|---|
| **A. Bundled with each release only** (today) | Simple; works offline; packages are covered by the `.deb`'s own signature (once the apt repository is signed) | Package updates (security fixes, new upstream versions) wait for a Roostack release; community packages would all have to ship in every release |
| **B. Fetched from the registry only** | Packages update on their own schedule | A new lab without internet, or with the registry down, has no catalog |
| **C. Both** | The bundled snapshot is the offline baseline (principle 3); a newer index replaces it when the controller can fetch one | Two sources to reason about (the newer index wins) |

**Decided: C** (the Owner, 2026-10-13). The registry's CI publishes a static **index** (every package, every version, each file's SHA-256, its tier, schema, minimum Roostack version and architectures, and any withdrawals) plus the package files. The controller fetches it every few hours and when the catalog page is opened; nodes get packages from the controller as now.

- **Git is the source of truth; the index is generated from it — Locked (2026-10-13).** In the repository each package is a folder with a file per version, and its tier, maintainer and any withdrawals are files there too, so every change is a reviewed commit. After each merge, CI builds the index from the repository (like a lock file): one JSON file and its signature, beside the root key's statement naming the current signing key (below). The index holds a serial number and a date, then per package and version: the file's path and SHA-256, schema, minimum Roostack version, tier, the image architectures CI checked, and any withdrawal (level and reason). A lab downloads the index, checks its signature, and fetches only the package files it needs, checking each hash. That needs only Go's standard library (an HTTPS request and Ed25519), works from any mirror, and carries facts Git doesn't hold (the architectures CI found).
  - **Considered:** the lab reading Git directly (a clone or pull: a new dependency on every server, either the `git` package called from the sandboxed daemon or a large Go library, plus code to check commit signatures); GitHub's API to list files (ties labs to GitHub, no mirrors, and unauthenticated calls are limited to 60 an hour per address, which several labs behind one connection could reach).
- **Hosting — Locked (2026-10-13): GitHub** (the Owner's suggestion): the repository on GitHub, the index on GitHub Pages, reached through an address of ours (e.g. `services.roostack.cloud`) so the host can change without a Roostack release. Considered: GitHub's raw file URLs (rate-limited, and the address is GitHub's); Cloudflare like the help site (§6.3.1; fine too, one more moving part).
- **The index is signed.** HTTPS proves a lab is talking to GitHub, not that the files are what the maintainers published: a leaked GitHub token, a bad workflow change, a mirror or a DNS hijack of our address could serve a changed package. A signature checked by the lab catches all of those, lets anyone mirror the files, and stops an old index being replayed (the index carries a serial number and a date, and a lab refuses one older than it has). Package files are trusted through their hashes in the index. Ed25519 is in Go's standard library, so no new dependency.
- **Two levels of key — Locked (2026-10-13).** A **root key** kept offline by the Owner, with the lab's other keys, whose public half is built into Roostack; it signs only a short statement naming the current **signing key**. The signing key lives in the registry's CI and signs every index, so publishing stays automatic (needed for 8.3.8). If the signing key leaks or CI is compromised, the Owner signs a new one with the root key and labs drop the old one, without a Roostack release. Losing the root key itself needs a Roostack release with a new one. Considered: one key, offline (every publish waits for a person); one key in CI (a leak means a Roostack release to replace it); the full TUF framework (the same idea with more roles and a dependency); minisign's file format (a known format, but it signs files, not key delegations; our own small JSON format is a few dozen lines).
- Settings → Updates shows when the catalog was last fetched and from where, and the Owner can turn fetching off (only the bundled snapshot is used then).
- **Considered:** per-author signatures (e.g. sigstore): more infrastructure, harder for contributors, and the trust that matters is the review (8.3.4), which one registry key states; Git commit signatures alone (a lab would need Git, and the history, to check them).

#### 8.3.4 Trust and review — Locked (2026-10-13): three tiers; a package policy of risky lines; the policy as built (2026-10-14)

**Tiers**, shown as a badge on the catalog and the service page:

- **Official:** maintained by the Roostack project, reviewed, and tested on a real lab for each Roostack release (install, backup, restore, update, remove).
- **Community — a fast follow** (the Owner, 2026-10-13): opened soon after the registry starts with official packages, not before 1.0 is needed. In the registry, written and maintained by its author, reviewed against the checklist below before each version is published, but not tested by Roostack for each release. The UI says who maintains it and when it was last reviewed.
- **Your own (local):** a package file the Owner adds themselves ("custom services", §8). Never fetched or reviewed; installing one shows a plain warning that Roostack hasn't checked it. It still has to validate, and it's kept in the lab like any other (8.3.1). This is how a contributor tests a package before submitting it (8.3.7).

**What a package may do is enforced by Roostack, not only by reviewers.** Registry packages (both tiers) are checked against a **package policy** in `pkgspec`:

- **Raw Quadlet lines are allowed, except a list of risky ones — Locked (2026-10-13).** Roostack writes each container's Quadlet file (the `.container` file systemd and Podman run it from) itself, from what the package declares: its image, its folders, its network, its secrets. The `quadlet:` passthrough lets a package add lines Roostack doesn't model: Forgejo's `UserNS=keep-id…` (whose user owns its files) and Immich's database `ShmSize` (shared memory) are today's uses. The Owner wants wide support from the start (2026-10-13): any line is allowed and reviewed when the package is added, **except a deny-list of lines that could reach beyond the service and have a Roostack way to do the same thing**. The list (agreed 2026-10-13): `Volume=`/`Mount=` with a host path (use `storage:`), `PodmanArgs=` (anything at all), `AddCapability=`, `SecurityLabelDisable=`, `Network=`/`Pod=` (Roostack's per-service network), `PublishPort=` (use `ports:`), `AddDevice=` (use `devices:`), `User=0`/`root`, `UIDMap=`/`GIDMap=`/`UserNS=host`, and the `[Service]` and `[Unit]` lines that run commands (`ExecStart…`, `ExecStop…`). A line that turns up in several reviews becomes a modelled field. Considered: an allow-list (safer by default, but every new app would wait for a Roostack change: rejected as too restrictive to start with).
- Images pinned by digest in the package: an error, not a warning; a multi-architecture index digest when the project publishes one. (A lab may still follow upstream tags for a service when its Owner opts in: 8.3.8.)
- Storage only through `storage:` (Roostack's folders); devices only through the abstract `devices:` requests.
- Nothing public by default (already true: §6.11), `public:` with `unsafe`, `private_paths` and `login_paths` filled in where they apply.

Local packages may break the policy, with the Owner's confirmation and the list of what breaks it shown.

**The policy — as built (2026-10-14).** `Package.Policy` in `pkgspec` (separate from `Validate`, so a local package can break it) returns every problem, each a sentence naming the field or Quadlet line and what to use instead:

- **Quadlet lines**, in containers' and databases' `quadlet:`, matched whatever their case: the agreed list above, read this way: `Volume=` is refused with any source, a named volume as well as a host path (named volumes are shared by every service of the `roostack` user and aren't backed up; storage only through `storage:`), so only an anonymous `Volume=/path` passes; `Mount=` only as `type=tmpfs`; `User=` when the user part is `0` or `root`; `UserNS=host` only, so Forgejo's `UserNS=keep-id:…` passes; `ExecStart…`, `ExecStop…` and every other `Exec…` key in `[Service]` and `[Unit]` (the `[Container]` section's `Exec=` is the container's own command, and allowed).
- **Added by the Owner on 2026-10-14**, because the generator appends a package's lines after its own, so they would override what Roostack writes: `Image=` (would replace the pinned image), `Secret=` (could name another service's Podman secret), `EnvironmentFile=` and `Rootfs=` (read host paths), `GlobalArgs=` (like `PodmanArgs=`), `ContainerName=` and `Label=io.roostack.…` (how Roostack finds a service's containers).
- **Images:** a container's `image`, and a database's when it sets one, must end in `@sha256:` and 64 hex digits; the multi-architecture check is the registry CI's (8.3.7). `Warnings()`, which only reported this, is gone.
- **Storage and devices:** the format already allows nothing else (mounts name a `storage:` entry; `devices:` takes only `gpu: intel`), so the Quadlet rules above are what enforce it.
- **Public access:** routes and ports must default to `exposure: private`; every route names at least one `login_paths` entry, or says why it shouldn't be public at all (`unsafe`). Decided by the Owner (2026-10-14) as what "where they apply" can mean mechanically; whether the private paths are right stays with review. A route without a login page (e.g. an API with tokens) marks itself unsafe. Considered: only checking the defaults (leaves the public fields to review alone); a new "no login" field (a format change for a rare case).
- **Where it runs today:** `roostack validate` fails on a problem (`-local` reports them as warnings, for a package of your own); `roostack render` prints them on stderr and still renders; the catalog loader logs each one as an error and still offers the package, since the bundled catalog is official packages and a problem there is a release bug, caught first by `TestExamplesParse`. Installing doesn't check it yet: that comes with fetching the registry (8.3.3) and "Add your own", where a local package's problems are shown for the Owner to confirm.

**What the UI shows before installing** (every tier): a short summary generated from the definition: what it stores and whether that's backed up, the addresses and ports it asks for, devices, how much memory it expects (a new package field), and links to the definition file and the files Roostack would generate (`roostack render`, in "Details").

**What review checks** (a checklist in the registry repository, the same for both tiers):

- Images come from the project's own published location, pinned by digest; the version matches `version`.
- Backups are right: databases declared (not just files), `critical` for what can't be remade, `replaceable` for caches, thumbnails and the like, transient stores `backup: false`.
- Secrets generated, never default values; `install_only` for admin passwords.
- Hooks are safe to run again and take user input only as environment variables (§8.1).
- Exposure defaults and public-access fields as above.
- Facts about the project (licence, source, website; 8.3.6) are present and correct.
- The author's test evidence (8.3.7) is attached.

**What review can't promise:** a container image is the upstream project's code; review checks the definition and where the image comes from, not the code inside it. The tier text says so ("Roostack checked how this is set up; the app itself is made by …").

**Pulling a bad package — Locked (2026-10-13), levels to detail.** The index can **withdraw** a version or a whole package, with a reason and a level. The Owner asked for levels, up to stopping a service, with an opt-out and a clear explanation:

- **Notice:** "Needs attention" says what's wrong and what to do (usually: update to the fixed version).
- **Warning:** the same, and the version can't be installed any more; updating is offered first on the service page.
- **Stop:** for a package found to be malicious, or an app being actively exploited with no fix: Roostack stops the service (its containers and its addresses), keeps all its data, and says on the service page and in "Needs attention" why, who said so (the registry, with a link), and what to do. The Owner can start it again, with a confirmation that names the risk.
- **The opt-out:** Settings → Updates, "Let Roostack stop a service the registry says is dangerous", on by default, explained in a sentence there. Off, a Stop is shown as a Warning.
- **Never:** removing a service or deleting data. A stop is the most the registry can do, so a stolen signing key (8.3.3) could at worst stop services until the Owner starts them again.

A lab that doesn't fetch learns of withdrawals from the next Roostack release. Published versions are never edited, only withdrawn and superseded. Considered: never stopping anything (the earlier leaning; leaves a known-malicious service running in labs whose Owner doesn't look); removing (data loss is never the registry's call).

- **Considered (tiers and policy):** one tier only, everything reviewed and tested by the project (doesn't scale to community contributions); no enforced policy, trusting review alone (one missed `Volume=` would expose a whole lab, and local packages would have nothing checking them); an allow-list of Quadlet lines (above); stricter rules for community than official (two rule sets to keep; official packages need nothing community ones shouldn't have, and needing an exception is a signal to review).

#### 8.3.5 Versioning and compatibility — Locked (2026-10-13)

- **A package version stays `<upstream version>-roostack.<revision>`** (§8.1). The upstream part says which release of the app runs; the revision counts changes to Roostack's definition for that release.
- **Updates (§7)** compare the upstream part: `patch` and `minor` policies need it to look like semantic versioning, otherwise the service only notifies. A revision-only change (a better definition, the same app) follows the `patch` policy. A service following upstream tags (8.3.8) uses the same policy names.
- **Each version declares its schema and the oldest Roostack it needs** (a new `requires: { roostack: "0.6" }` field). A lab only offers versions it can read and run; the catalog says "Needs a newer Roostack" for the rest.
- **The format is pre-1.0.** The registry keeps each version in the schema it was written in. Roostack reads the current schema and, during the alpha, the one before; when the schema changes, a converter rewrites the registry's current versions and the lab's own copies (8.3.1) on upgrade. At 1.0, only additive changes within `v1`.
- **No downgrades** through the UI: a newer app has usually migrated its database. Going back is a restore (§6.9).
- **Upgrade notes and migration steps** (§8.1 Future) become fields of a version, shown before updating.
- **Considered:** versioning packages independently of upstream (hides which app version runs); following upstream tags automatically (no review of what changed).

#### 8.3.6 How it appears publicly — Locked (2026-10-13): one index, read by the website and the lab

- **Facts about the project move into the package**, in a new `about:` block: maker, website, source, licence (SPDX), support/donation link, icon, category, keywords. Today these live in `services.ts`; with the registry they're reviewed with the package (8.3.4) and the same everywhere.
- **The website** (roostack.cloud, Astro, in the roostack-cloud repository) builds a browsable registry from the index at build time: a page per package with what it is, credit to its project, its tier and maintainer, what Roostack sets up (generated from the definition: storage and backups, address, ports, memory), its versions, and the definition file itself. Search and categories across all packages. **It lives under `/services`** (decided 2026-10-13: "services" is the word people use, in the lab's UI too; "package" is for authors): the hand-ordered hero services and their own wording stay at the top of `/services`, with every package below and a page each at `/services/<name>`. The website needs nothing from Cloud. Considered: `/packages` beside a curated Services page (two places for the same things).
- **The lab's catalog page** reads the same index (or the bundled snapshot): search, categories, tier badges, "Add your own" for local packages, and the install summary above. Details shows the definition and what it would generate.
- **Considered:** the website reading Roostack's repository directly (couples the website to Roostack's layout); hand-written pages per package (doesn't scale, and drifts from the definitions).

#### 8.3.7 Contributing a package — Locked (2026-10-13)

1. **Write:** start from a template (`roostack package new <name>`, or copy an example) and the format reference on the help site, extended with a "Write a package" guide.
2. **Check:** `roostack validate` (already renders every template with default and flipped settings), plus the package policy (8.3.4); `roostack render` shows the generated files.
3. **Try it on a real lab:** add it as a local package on a dev VM (`scripts/dev-vm.sh`) or one's own lab, and go through install, a backup, a restore onto a fresh VM, an update from the previous version, and removal. The guide gives the steps and what to paste as evidence.
4. **Submit:** a pull request to the registry repository, with a checklist template. CI validates, applies the policy, renders golden files with default settings, checks each image digest resolves (and which architectures it has), and checks the `about:` fields. Later, CI could run the install test on a VM.
5. **Review and publish:** a maintainer goes through the checklist; on merge, the index is rebuilt and signed. The author is the package's maintainer; a community package whose maintainer doesn't keep up with upstream security releases is marked unmaintained, then withdrawn if it becomes unsafe.

#### 8.3.8 Updates without waiting for a new definition — Locked (2026-10-13): both ways

The Owner wants (2026-10-13) services to pick up an app's patch releases (security fixes, mostly) without waiting for new definitions, and an opt-in to follow upstream at patch or minor level without the registry's digest. With the registry in its own repository and fetched by labs (8.3.2, 8.3.3), nothing waits for a Roostack release any more. **Decided: both of these.**

**1. An update bot in the registry (the default path).** A job in the registry's CI checks each package's upstream for new releases every hour, writes the new version (tag, digest, `version`) and opens a pull request. CI validates and renders it, and **runs it**: installs the package with its default settings in rootless Podman on the CI runner, waits for its health checks, and, for packages with databases, takes a backup and restores it into a fresh copy. Patch releases of official packages merge themselves when that passes; others wait for a person (community packages: their maintainer). Labs fetch the new index within hours, and each service's update policy (§7) applies it in the maintenance window (§3.2).

- **What "tested" means here:** CI shows the new version starts, answers its health checks and survives a backup and restore with this definition. It doesn't click through the app; a person reviewing a minor or major release can. Without the CI run, a bot update would only be checked on paper, which is the Owner's point.

**2. "Follow upstream" per service (opt-in).** On a service's update settings, the Owner can choose to follow the app's own releases at **patch** or **minor** level, ignoring the registry's digest:

- The package says which tags count as releases (a new `updates:` field, e.g. a tag pattern), so it only works for apps whose tags look like semantic versions; others don't offer it.
- The controller looks up the newest matching tag (on its update schedule), pulls it on the service's server, and **records the digest it got in the lab's state**, so restores stay exact (principle 1) and the Owner can see exactly what runs.
- **After each update the lab checks the service's health and goes back to the previous image if it fails** (Podman keeps the old image until the new one is healthy), with the reason under "Needs attention". It never rolls back a database, so a failed update after the app migrated its data is shown, not undone (the backup taken before updating, §6.9, is the way back).
- The choice is explained where it's made: the app's newest releases arrive sooner, but Roostack hasn't checked them with this package, and a release that needs a new definition can break the service until one arrives.
- The definition itself (folders, settings, backups) still comes only from the registry; a new definition for a newer upstream version is offered as a normal update.
- Withdrawals (8.3.4) can name image digests as well as package versions, so a bad upstream image is caught for services following upstream too.

**What the digest still gives, and doesn't (2026-10-13).** The Owner asked what pinning is worth if the bot updates it anyway. It gives: every lab runs exactly the bytes CI ran; a tag that upstream (or someone who took over upstream's account) re-points to a different image doesn't reach labs until a new commit, which a person or CI sees; and a bad image can be withdrawn by its digest. It doesn't give: any review of the app's code, and on its own it doesn't test anything (hence the CI run). Following upstream gives up the first two in exchange for speed, which is why it's an opt-in.

- **Considered:** only the bot (the earlier leaning; the Owner wants the choice); only following upstream (every lab would run untested images by default, and each lab would query image registries, which rate-limit: Docker Hub's anonymous limits); bot updates merged without running them (only checked on paper).
- **To agree later:** whether CI's run also covers ARM, once Roostack runs there (§3).

#### Decided in the second round (2026-10-13)

- Signing: an offline root key held by the Owner, with the project's other keys, and a signing key in CI (8.3.3).
- The registry repository's licence: **Apache-2.0**, the same as Roostack (§2.1): one licence across the project, contributions come under it explicitly, and Cloud can use the definitions like Roostack's code. Considered: MIT-0 or CC0 (copying snippets without credit; a second licence to explain).
- Review: anyone with merge access to the registry repository may review and merge a community package; one approval.
- The registry repository: `github.com/roostack/services`, created by the Owner (2026-10-13).

## 10. Multiple Servers — Locked (2026-09-27)

One lab can span several servers: extra boxes at home, VPSes in the cloud, and later Roostack Cloud. This section is the design to build towards; nothing here is built yet except where marked. It replaces "master/worker" elsewhere in this document.

### 10.1 Roles

**Naming (2026-09-28):** the computers in a lab are **servers** everywhere: the UI ("My Servers", Settings → Servers, "Move to another server"), this document and the code (earlier drafts said "machine"; the database was migrated). A **node** is a server's role when it isn't the controller, and `node.Node` is the code's handle on any server.

**Servers in the UI (2026-09-28):** Home shows **My Servers** beside My Services (status, backups, updates, services, a link to each server's settings). Settings that differ per server (updates and restarts, time zone, remote access, backups) are grouped under "Each server": the overview summarises every server, and each area's page opens on a summary row per server that also switches between them. Each server has its own page (`/settings/servers/<id>`) with its card and its settings. Service cards say which server a service runs on and when it was last backed up, with details (containers and images, web routes, ports, data folders and size); Roostack's own services (Roostack and its agent, Caddy, backup stores, network links) are shown per server behind a toggle, so nothing is hidden from a technical user.

- **Node:** any server running Roostack. Every node runs its own services (Quadlets, reconciler), its own Caddy and certificates, its own backups, OS updates, firewall and agent, exactly as a single-server lab does today.
- **Controller:** one node also holds the lab's desired state (§1.2: services, placement, settings), users and sessions, and serves the UI. It decides placement; nodes do the work.
- **The controller can move to any node** (chosen, not automatic), e.g. from a home NUC to a VPS:
  - Every node keeps a **replica of the lab's state** (desired state and the Roostack database), pulled with its assignments. The controller encrypts it with the **recovery key** (§6.9) before sending it; nodes store it but can't read it, because the recovery key is never stored on a node other than the controller.
  - **Planned move:** the controller hands over (freezes changes, sends the latest state, the new controller takes the address and certificate authority) and becomes a plain node.
  - **Disaster:** the Owner promotes a node from its replica by entering the recovery key (they have it written down for exactly this). At worst it misses changes since its last pull. Two controllers must never both be active: promotion revokes the old one's authority (a new epoch number that nodes follow).
- The first server installed is the controller; a lab with one server is a lab with one node that is also the controller. Single-server labs stay exactly as simple as today.

### 10.2 Private network: Roostack-managed WireGuard

- Roostack runs a **WireGuard** network between its nodes (WireGuard is in Debian's kernel; `roostack-agent` manages the interface and keys). Every node gets an overlay address (e.g. `100.96.0.x`).
- **No inbound ports at home:** home nodes dial out to reachable nodes (a VPS with a public IP), so a home controller needs no port forwarding. Nodes that can reach each other directly do; others go via a reachable node (hub and spoke first, a mesh later).
- All controller ↔ node traffic runs inside WireGuard **and** uses mutual TLS, so a leaked WireGuard key alone isn't enough.
- **Joining:** the Owner creates a one-time join code in the UI (short-lived, single use) and runs `roostack node join <code>` on the new server (or picks "Join an existing lab" in its setup wizard). The code carries the controller's address and a CA fingerprint; the node gets its WireGuard peer config and a client certificate from the controller's CA.
- "Private" (home network only, §6.10) widens to **home network or Roostack's WireGuard network**. The same network is the base for remote access for people later (a phone joining over WireGuard).

### 10.3 Controller ↔ node protocol

- **Nodes pull.** Every node periodically (and when nudged) fetches **its assignment**: the instances placed on it (package, version, settings, secrets it needs) plus lab settings it needs (domain, DNS provider, backup destinations). It generates and reconciles locally with the same code as today, then reports back **status**: service health, apply results, activity logs, backups, updates, restart needs.
- **Offline-tolerant:** if the controller is unreachable, a node keeps running its last assignment and queues its reports (§1.3 local-first). Assignments carry a version; nodes apply only newer ones.
- **Actions** (restart a service, run an action hook, restore, update now) are requests the node picks up on its next pull (or immediately when nudged), with results in the report. The same request types the in-process code uses today (e.g. the agent's JSON API) cross the network unchanged.
- **Secrets:** user-provided secrets travel only to the nodes that need them, over mTLS inside WireGuard; generated secrets are made on the node that uses them and never leave it (backups hold them, encrypted).
- **Backups per node:** each node backs up its own services to **its own repository** (or its own folder at the same destination) with **its own key**. The recovery key is added to every repository as a second key (restic supports several), so the Owner can restore anything with it, while a compromised node exposes only its own backups and its key can be revoked.
- **Packages:** the controller's catalog is the source of truth; nodes fetch package files they don't have (same version pinning).
- **Certificates (2026-09-28):** each server's certificate (from the controller's CA) lasts a year and renews automatically when 120 days are left: nodes ask the controller over the lab API with their current certificate; the controller signs its own. TLS picks up a renewed certificate without a restart. The controller records the certificate each server may use (its serial) and its lab API accepts only that one, plus the one it replaced until the new one is first used (in case the reply was lost). Removing a server therefore revokes its certificate as well as its WireGuard peer; a server rejoining gets a new one. Nodes accept requests only from the controller. Settings → Servers shows each certificate's expiry; one within 30 days of expiring (renewal failing) needs attention. The CA itself (20 years) isn't renewed yet.
- **Before the domain is set up**, Caddy waits for its DNS credentials and the rest of the lab (services, backup stores, storage for others) is applied without it.

### 10.4 Placement and moving services

- Every instance has a **`host`** (a node ID); default: the controller. The install form asks where to run it when the lab has more than one node, with hints (RAM, disk, GPU, home or cloud).
- **Moving** a service = back up on the old node, restore on the new one, switch its route, remove the old copy (existing per-service backup and restore, §6.9). Portability is the requirement from §4.

### 10.5 Public access through a cloud node ("edge")

For services hosted at home but public (e.g. Immich shared with family), without opening ports 80/443 at home:

- A cloud node can act as an **edge**. It forwards with Caddy's layer-4 plugin (`caddy-l4`, added to Roostack's Caddy image like the DNS plugins; ASSUMPTIONS to verify SNI routing and PROXY protocol). Public DNS records point to the edge's public IP; the edge forwards each connection **over WireGuard** to the home node that runs the service.
- **TLS passthrough by default:** the edge routes on the TLS SNI name and never decrypts; certificates and keys stay on the home node, so the cloud provider can't read the traffic (in line with "own your data", §4; unlike the Cloudflare proxy, §6.5.1). Visitors' IP addresses reach the home node via the PROXY protocol, so private checks, rate limiting and CrowdSec (§6.10) still see real visitors.
- Terminating TLS at the edge (caching, fewer hops) is an option per service later, clearly marked as letting the edge see the traffic.
- The home firewall stays closed to the internet; only WireGuard (outbound) is needed. The same mechanism is how a **Roostack Cloud relay** would work for people behind CGNAT (§6.5.1).
- Home devices keep reaching home services directly (local DNS records, §6.5.1), not via the edge.
- **As built (2026-10-11):** prototyped first (docs/ASSUMPTIONS.md Q1–Q11), then built and tried for real: VM3 (a controller at home, behind two NATs, no port forwarded) made Vaultwarden public through `roostack-test` (a Linode in Sydney, in the lab by the controller dialling it, §10.2), and a visit from the internet got Vaultwarden with VM3's own certificate, its admin path refused, plain HTTP redirected, Roostack's own pages not passed on, and VM3's log showing the visitor's real address.
  - **Choosing it:** Settings → Public access, **How people reach your public services**: port forwarding at home, or **through <a cloud server> in this lab** (any server but the controller with a public address: where the controller dials it, or where it connects from). Saved as `public.edge` (the server's ID) in `lab.yaml`, applied without a restart. A lab on the internet is reached directly and isn't offered it. The service's own public checklist then says there's nothing to change on the router.
  - **The edge server** gets Roostack's Caddy (servers other than the controller otherwise have none), built the same way with `caddy-l4` v0.1.2 added to the image, publishing TCP 80 and 443 only. Its config comes in its assignment: the lab's public names (and their old ones while those work) are passed through by the TLS name to the controller's 443 over WireGuard, with a PROXY v2 header; plain HTTP for them is redirected; anything else gets nothing. No certificates or DNS logins on it.
  - **The controller's Caddy** believes PROXY headers only from the edges' WireGuard addresses (`servers :443` with the `proxy_protocol` wrapper), on its normal port, and its private checks treat those addresses as outside ("not (private and not an edge)"), so a connection from the edge without a header (a bug, or a broken edge) reaches nothing private. **Changed from the design the same day:** a separate edge port (8443, WireGuard only, header required) was the plan; Caddy's options can't require a header from a trusted source anyway (Q4), and treating the edge as outside fails safe where a separate port wouldn't, with no second listener or duplicated sites.
  - **Public DNS records** point at the edge's public address while it's the way in (`public.Chosen`, asked each time), else the home's.
  - **TLS ends on the controller**, where every public name's certificate is (a service on another server is still proxied by the controller's Caddy, §10.9): so the edge passes to the controller, whichever server runs the service. A lab whose controller is in the cloud already serves public names itself and needs no edge; passing visitors through to a home server undecrypted there would need Caddy on that server (later).
  - **Through Roostack Cloud's relay — as built (2026-10-11), its first slice:** a third way in, for a lab linked to Cloud whose address is its roost.ac name (custom domains in Cloud's second slice). Choosing it asks Cloud first (`PUT /v1/lab/relay` in `cloudapi`: the relay WireGuard key and the public names; an account without the pilot grant is refused, and the page says so); the agent makes a separate interface, `roostack-relay`, keeping its key, which dials every edge Cloud names (addresses in 100.81.0.0/16, a keepalive). The controller's Caddy believes PROXY headers from the edges' relay addresses and treats them as outside, as for the lab's own edge; Cloud points the relayed names at its edges in DNS; the names follow the public ones after each apply. **The firewall accepts only TCP 443 from `roostack-relay`, before the home-network rules** its addresses (inside 100.64.0.0/10) would otherwise match: an edge reaches Caddy and nothing else. Tried over the internet (2026-10-11): VM3 through the test edge in Sydney, Vaultwarden with VM3's own certificate, its admin path refused, the visitor's real address in VM3's log.
    - **Visitors by country, and the lab's bans at the edges — as built (2026-10-11), the relay's second slice:** while relayed, Settings → Public access has "Visitors by country": anyone (the default), only visitors from chosen countries, or everyone except them, and "Let everyone in" for a day to a month (travel), after which the limit comes back by itself. Kept in `lab.yaml` (`public.countries`), sent with the relay request (`RelayRequest.Countries`, Cloud checks it; a refusal isn't saved), enforced at Cloud's edges before visitors reach the lab. No countries are kept out by default (Cloud's DESIGN §5, changed 2026-10-11: a refused visitor gets a bare connection error, with no page saying why). The controller sends CrowdSec's own bans (origin `crowdsec` or `cscli`, bans of an address or range; not the community's lists) every 5 minutes (`PUT /v1/lab/relay/bans`, at most 1,000, newest first); Cloud drops them an hour after the last. Countries apply only through the relay for now: port forwarding and the lab's own edge reach the lab's Caddy directly. Tried over the internet (2026-10-11) with VM3: only New Zealand refuses a visitor in Australia and only Australia lets them in, "Let everyone in" and ending it, a CrowdSec ban refused at the edge within a minute of being sent and let in again when lifted.
    - **The lab's own domain through the relay — as built (2026-10-12), the relay's third slice:** a lab whose address is its own domain (not a roost.ac name) can choose the relay too. The relay request names the domain (`RelayRequest.Domain`); Cloud answers with the lab's relay name (`r-….relay.roost.ac`, pointing at every edge) and the proof to add, a TXT record `_roostack.<domain>` with the lab's token (Cloud's DESIGN §5). With a supported provider and records managed, Roostack adds the TXT record and, once it's in place, asks Cloud to look at once; each public address becomes a **CNAME to the relay name** (Roostack's A record deleted first: a name with a CNAME can have no other record; someone else's A record is a conflict to clear by hand), the wildcard staying on the LAN address; relaying stopped, the CNAMEs and the TXT record go and A records come back. Kept by hand, Public access lists the TXT and CNAME records to add. Public access says where the proof stands (waiting, with what Cloud last saw and "Check now"; proven; gone, with relaying stopping a day later), and Needs attention warns while it's waiting and shows a problem when it's gone. The provider code for CNAME, TXT and deleting is tried against fakes only (ASSUMPTIONS M7). Changing the way in now re-syncs DNS at once.
    - **Visitors through the relay — as built (2026-10-12):** a card of Cloud's counts for the lab (`GET /v1/lab/relay/stats`; Cloud's DESIGN §5, "Statistics"): visitors (different addresses each day, in the lab's days: the relay request carries the lab's time zone), connections, data, connections turned away and why, a bar chart (visitors each hour today, each day for 7 or 30 days, each month for a year), and the top countries. Counts only, said on the card. Shown to Owners on Public access and to Admins on its own page, `/visitors`, linked from Services (Settings are Owners'); Members don't see it (agreed 2026-10-11). Loaded on its own (htmx), so a slow Cloud doesn't hold up the page; Cloud out of reach is said in the card. It says when its counts are from (the edges send them every 15 minutes), so a visit a minute ago missing isn't a surprise.
  - **One way in for the whole lab, for now (agreed 2026-10-11), built so each public address can choose its own later:** a route would gain its own `entry` (the lab's, port forwarding, or an edge), `publicHostsOf` would pick the edge's names by it, and DNS records would take each address's entry instead of the lab's. **Not yet:** HTTP/3 through the edge (Q7); the controller's Caddy still advertises it, and browsers fall back to HTTP/2; telling the Owner when the edge can't reach home beyond the Servers page's status and the "unreachable server" notice.

Failover is service-specific, so packages declare what they support:

- **none** (default): if the node is down, the service is down; the UI says so.
- **cold standby:** a second node keeps recent backups of the service; if the primary is unreachable for a set time, the Owner (or, when enabled, Roostack) restores the latest backup there and switches the route. Data since the last backup is lost; suits most home services.
- **replicated:** the service keeps a live copy on another node with its own replication (e.g. Postgres streaming, Vaultwarden via its database), declared per package. Much later.
- Automatic failover needs a way to tell "node down" from "network split" (at least a third node or the edge as a witness), so it comes after manual failover.

### 10.7 What to build now (no networking yet): seams

So single-server code doesn't paint us into a corner:

1. **`host` on every instance**, defaulting to the controller; loading services filters by host.
2. **Controller/node split in code:** the UI-facing manager (desired state, users, placement) talks to a **`Node` interface** for everything that touches a server (apply, status, hooks, actions, restores, activity, updates, restarts, firewall). Today: one in-process implementation. Later: a remote implementation speaking the same plain-data requests.
3. **Status, activity and restart state are per node**, and the UI's "This server" areas are per node (e.g. `/settings/servers/<id>/updates`) once there's more than one.
4. **Node identity:** every install gets a stable node ID and name at setup.

Then a **two-VM prototype**: a second dev VM joins the first over WireGuard and runs one service placed on it.

### 10.8 Decisions (2026-09-27)

- **Network layout:** hub and spoke (servers talk through a reachable node, usually a VPS). Direct links between two networks behind NAT (hole-punching, full mesh) only when a real case needs them.
- **Edge forwarding:** Caddy's `caddy-l4` plugin, not a forwarder of our own.
- **Keys:** the recovery key protects the state replicas and is added to every node's backup repository, but is stored only on the controller; each node has its own backup key (§10.3).
- **Roostack Cloud:** nodes run by Roostack Cloud are trusted like any hosting provider (a server running your services can see them; there's no real alternative). Roles that don't run services stay **zero-knowledge**: a relay or edge uses TLS passthrough, and a backup target only ever receives restic-encrypted data. Billing is out of scope until Roostack Cloud exists.

### 10.9 Prototype as built (2026-09-27)

What the two-VM prototype does, where it refines the design above:

- **Hub:** the controller is the WireGuard hub (`100.96.0.1`, UDP 51820; network `100.96.0.0/24`). A reachable hub other than the controller comes later.
- **Joining:** the Owner makes a code in Settings → Servers and runs `sudo roostack node join <code>` on the new server. The code carries a **one-time WireGuard key**, so only the hub's UDP port needs to be reachable (no public TLS endpoint).
- **The controller dials out — as built (2026-10-11):** when the controller can't be reached (at home, behind its router) and the new server can (a cloud server), the code is made with **None: this server connects to the new one instead** and the new server's public address. The code then says *listen*, without an endpoint: the new server listens on WireGuard's port (Roostack's firewall opened for the join by a fixed agent call, then kept open by its assignment), and the hub dials it at that address with a keepalive, before and after it joins (`servers.dial`). Everything else about joining is unchanged. The rule underneath is the one direct links use: whichever side can be reached is dialled. Both ways round now work: a controller in the cloud with servers at home (they dial it), and a controller at home with a server in the cloud (it dials the server); two servers both behind NAT still need a reachable hub (later). **Tried for real (2026-10-11):** VM3 (a controller behind two NATs: QEMU's and the home router's) joined a Linode in Sydney, with nothing forwarded at home. **Not yet:** if the cloud server's address changes, the hub keeps dialling the old one (re-join it, for now). Over WireGuard, the server checks the controller's CA against the code's fingerprint, sends its own WireGuard key and a CSR, and gets its certificate; the hub then replaces the one-time key with the server's own. Codes work once and expire after an hour.
- **Protocol:** every server serves a lab API on its overlay address (port 8471), mutual TLS with the lab's CA. The controller **sends** assignments and makes requests directly (status, service states, activity, hooks, actions, secrets, backups, restores, updates, restarts, settings); a node also **pulls** its assignment when it starts and every 15 minutes, and keeps its last one (without secrets) to run while the controller is away. Assignments carry a version; older ones are ignored. The controller works out every server's assignment on every change, but **sends only what changed**: a server that already has the same assignment, and applied it without error, isn't sent it again (it would only look busy, e.g. "Applying changes on vps" while a service installs elsewhere); one whose last apply failed is sent it again, as its retry. Typed-in secrets travel once and are never stored on disk.
- **Web routes of a service on another server:** the server publishes them on its overlay address (firewall: WireGuard interface only) and the controller's Caddy forwards to it (TLS ends on the controller for now; passthrough is §10.5's edge).
- **Nodes** run no UI, Caddy or DNS. Per-server pages live under `/settings/servers/<id>/…`.

### 10.10 Backups across servers, and moving services — Locked (2026-09-27)

Builds on §6.9 (restic, recovery key, 3-2-1) and §10.3 (each server backs up its own services to its own repository with its own key).

**Destinations are chosen per server, from providers the lab knows.**
- A **provider** is a place backups can go: a cloud account (B2, S3, …), an SFTP server, **a server's own disk**, or **another server offering storage** (below). A provider is set up once (its credentials) and any server can use it; the Backups page of each server picks one (and later extra copies, for 3-2-1).
- Every server's repository goes in **its own folder**, always, even if only one server uses the provider: `<provider path>/roostack/<lab id>/<server id>/`. Moving a lab or adding servers never reshuffles folders. On a rest-server store the server's own area comes first instead (`/<server id>/<lab id>`), because private repositories are named after the user; at another lab's store it is `/<guest user>/<server id>` (the user is the lab's own, and rest-server allows at most two levels).
- **The controller creates each repository** (decided 2026-09-27): it runs `restic init` at the destination with the recovery key, adds a new key for the server, and gives the server only that key. The recovery key never leaves the controller. So the controller must reach every destination, which the next point guarantees.

**Disks are offered over Roostack's network (restic's rest-server).**
- A server's own disk is used through a small **rest-server** on that server, listening only on Roostack's network. The controller creates repositories through it like any other destination, and the server backs up to itself through it too. One mechanism covers "local disk", "the NAS at home" and "a friend's server".
- rest-server runs **append-only** for backup clients, so a compromised server can add backups but not delete old ones (ransomware protection, §6.9). Pruning is done by a key that can delete, held by the controller (see open question 2).

**A server can be a backup target for other labs (friends and family).**
- The Owner of the storage server creates a **storage invite** (like a join code) with a **quota**; the other lab's Owner adds it as a provider. Each invited lab gets its **own rest-server repository area with its own size limit**, reached over a WireGuard link that allows **only** that port (it isn't a server in the host's lab and can reach nothing else).
- The host only ever sees encrypted data and sizes (zero-knowledge, like §10.8's backup targets).
- **Invite form — as built (2026-10-03):** the address guests connect to is filled in when Roostack knows it (on a lab on the internet, the server's public address; at home, the home's public address once DNS records know it), with "Use a different address" to change it; otherwise it's typed. The form says how much more the server can offer (free space, less what other labs have been given but not used yet, less 10% headroom), starts at 50 GB or that much if it's less, and says, as the number changes, how much free space that leaves for the lab's own services and backups. The page opens with the offering server's disk (the same block as Settings → Servers: free and total, a bar with the unused promised space, what uses it, warnings) and how much more other labs can be given. A new invite is shown in place of the form, with a Copy button, until "Make another invite". On a lab on the internet the help is about the provider's firewall rather than port forwarding.
- **Storage management:** the host sets and can change each guest's quota; Roostack keeps free-space headroom on the disk and refuses quotas that don't fit (new invites and quota changes); both sides see usage (the guest: "8.2 of 50 GB used at Mum's"); warnings at 80% and when a backup fails for lack of space; the host can remove a guest (their data is deleted after a grace period, with notice).

**Restoring across the lab — Locked (2026-10-04)**

Until now each server's backups could only be restored onto that server, and a full-lab restore brought back only the controller: moving two servers onto one new server, or rebuilding after losing a node, had no path. Decided:

- **A repository per server stays.** Considered: one repository for the whole lab. Rejected: a restic key opens a whole repository, so every server would hold a key that decrypts every other server's data; servers would contend for its lock; and the per-server append-only credentials (ransomware protection) would go. It would only gain deduplication across servers, which matters little (services rarely share data).
- **One snapshot per service.** Each backup makes the server's own snapshot (`roostack`, `server`: Roostack's state and the Podman secrets store) and then one per service (`roostack`, `service=<name>`: its data folders and its secrets, saved to `backup-secrets/<name>.json` in the state folder for the upload and removed after). So "which backups have Photos" is a tag query in any repository, and a service's backup carries what it needs to run on any server, even after its own server is gone. Retention groups by tags (`--group-by host,tags`), so each service keeps its own 7 daily, 4 weekly and 6 monthly backups: a service that's no longer backed up keeps its last ones rather than losing them to others' newer backups. Considered: one snapshot per server, finding a service by its paths (fewer snapshots, but restore stays tied to the folder layout).
- **One restore page per service, for the whole lab.** "Restore Photos" lists its backups from every server's repository and every copy, through the controller (which opens them all with the recovery key). The newest is chosen for you and said in one line ("Last night's backup, 03:00 (read from USB drive BACKUP)"); the others are under "Choose a different backup", for when the newest is already broken. It goes onto the server the service runs on, or another one chosen there. Restoring onto another server reuses moving through a backup.
  - **The Backups page is the lab's (2026-10-04):** with several servers, "Each server's backups" (the server switcher, one line per server showing how its backups are doing, then that server's status, latest run and plan) and "Your whole lab" (restoring every service, by the server it runs on; storage at other labs; the recovery key), the same whichever server is chosen. Until then the whole page was one server's: a service could only be restored from its own server's page, once that server had backups, and the recovery key showed only on the controller's.
  - **Moments, not places (2026-10-04):** every backup is in several places (the main backup and each copy), so the list shows each backup moment once, grouped as the clean-up thins them out (this week, this month, older: about 17 at most), and the place to read it from is chosen for you (the main backup, usually at home and quickest), with "Read it from" listing only the places that have that moment, for when the main one can't be read. Every snapshot of one run is tagged `run=<time>` so copies group exactly; older untagged ones group by server, within an hour. Considered: a flat list of every snapshot (about 50 rows with two copies, the same night three times), and filters (unneeded for a list this short).
- **Restoring a whole lab onto fewer servers.** After the controller is restored, services that were on servers that aren't there show as a plan: tick which come back onto this server (all, when they fit in its free space; otherwise none), with sizes. Servers still running reconnect by themselves, so nothing is assumed lost until the Owner says so. Services not chosen stay **waiting to be restored** ("Waiting to be restored, from nas", with its latest backup's size), each restorable later onto any server (one added later included) with the normal restore. Considered: placing them automatically (simple, but may fill a disk or put things where the Owner doesn't want them).
- **Backups of services waiting to be restored are kept.** Retention never ages them out (above). "Needs attention" says how many are waiting (information, not a problem: not in the problems email). Only "Remove and delete its backups…" on the service's page deletes them. Once no service from a lost server is waiting, the server leaves the lab; its backups stay (the recovery key still reads them).
- **Gone for good? — as built (2026-10-11):** the controller records when it first sees a server not answering (kept across restarts, forgotten when it answers). Settings → Servers says "Not connected since …", and a server without services offers "Remove it from the lab". After three days unreached, "Needs attention" stops saying only "can't reach" and says plainly "Roostack hasn't reached *server* since …. If it's gone for good (reinstalled, or switched off for good), remove it from the lab", or, if it had services, that they can come back from their backups on another server (the page below). Found with a reinstalled test VM that stayed in a lab for days. Considered: WireGuard's last handshake as the date (lost when the controller restarts).
- **As built (2026-10-04):** Settings → Servers shows a server that can't be reached as "Not connected" and offers "*server* is gone: restore its services…" (for any server that can't be reached, not only after a full restore: a node dying in a running lab is the same case). That page lists its services with the newest backup that can still be read and its size (from the snapshot's summary), all ticked when they fit in 90% of the chosen server's free space (otherwise none), one server for the whole batch; confirming "*server* isn't coming back" marks every one of its services `waiting` (their `host` still names it, so its backup records stay and it's in no assignment, even if it comes back), then the controller restores the ticked ones one after another (the restore through the controller above). Restoring the last waiting service, or removing it, takes the server out of the lab; removing it by hand is refused while services wait on its backups. "Remove *service* and delete its backups…" lists every repository first and deletes nothing if one can't be read (its backups there would stay unseen), then forgets every snapshot tagged with the service.

**Moving a service between servers: two ways, the UI suggests one.**
- **Copy directly** (quick, for smaller data or servers on the same network): copy the data to the new server over Roostack's network *while the service keeps running*, then stop it, copy what changed, start it on the new server and switch its web address. Downtime is only the final pass. The old copy is kept until the Owner confirms.
- **Through a backup** (large data, slow or unreliable links, or servers far apart): back up on the old server, then restore on the new one from the old server's repository. The controller adds a temporary key to that repository for the new server and removes it afterwards. Resumable, and reuses restore (§6.9).
- The move page shows the data size and suggests a way (through a backup above 10 GB, when the old server's backups are set up through Roostack).
- As built (2026-09-28): data travels **through the controller** in both ways (it is the hub every server already connects through); in the backup way the controller reads the old server's repository itself with the recovery key (`restic dump`), so no repository keys or store passwords are shared between servers. The service's Podman secrets are copied from the old server. Data already on the new server is kept aside (`<dir>.before-move-<time>`), and the old server's copy is renamed (`<dir>.moved-to-<server>-<time>`), both kept until the Owner deletes them.

**Decisions (2026-09-27)**
1. ~~Provider credentials~~ **Decided (2026-09-27): scoped where cheap and stable, shared elsewhere.** rest-server gets a user per server (`--private-repos`); B2 gets an application key per server limited to its folder (plain HTTP API, deleted when the server is removed). Other providers use the shared credentials, and the server's Backups page says so ("these credentials can reach the whole bucket"). More providers get scoped keys one at a time when there's a need.
2. ~~Pruning~~ **Decided (2026-09-27):** the controller runs `restic forget/prune` weekly with the recovery key, over a separate non-append-only credential. For friends' storage, the guest lab's controller does it.
3. ~~rest-server as a dependency~~ **Decided (2026-09-27):** run it as a pinned container (`docker.io/restic/rest-server`), like Caddy: containers where possible make other distributions easier to support later.
4. ~~Guest link~~ **Decided (2026-09-27): a separate WireGuard interface for guests** (`roostack-guests`, its own address range, e.g. `100.97.0.0/24`, and its own UDP port, default 51821). The firewall drops everything arriving on it except the rest-server port; the lab API and web routes are never reachable from it. Turning "storage for others" off takes the interface down.
   - **Protecting the WireGuard ports — Locked (2026-10-03):** UDP 51820 and 51821 are open only while used (a lab network with other servers; storage for others). WireGuard answers nothing without a key (a scan can't tell the port is open), lets in only the peers' keys Roostack added (join codes and invites add a one-time key, useless without their expiring token), has nothing to guess, and has cookies against handshake floods. On top, Roostack's firewall drops a source's new handshakes beyond 5 a second (burst 20); peers whose handshake was answered pass through conntrack first. Checked on VM1: 500 fake handshakes in a second, 25 reached WireGuard, and VM2's link from the same address kept working. Not CrowdSec: WireGuard logs no failed attempts for it to read, and blocking shared addresses (CGNAT, mobile) could silently cut off a friend's backups; a host-wide firewall bouncer was considered and not chosen.
   - **Joining from the first-run page — as built (2026-10-03):** a fresh server's first-run page asks for the setup code first (remembered for that browser for 30 minutes, and checked again at the end), then "What's this server for?" with nothing chosen: a new lab, add it to a lab you already have, or restore a lab from its backups. Joining takes the join code and a name (the hostname by default), does what `roostack node join` does from inside Roostack (the agent sets up WireGuard), and Roostack restarts as part of the lab; the page says where to manage it (join codes now carry the lab's name and `roost.<domain>`). A failure says why and is undone (the link and anything saved for the lab), so it can be retried. Joining gives up after 20 seconds without a WireGuard handshake, as storage for others does. The lab's "Add a server" shows the code to paste first, and the command under it. A server that's part of a lab has no UI of its own, so its address now serves one page: which lab it belongs to, and a link to manage it there (the lab's name and address are kept from the join code). Tried end to end on 2026-10-03 (a fresh VM joining VM1's lab from its page): a wrong setup code, a code to nowhere (refused after 20 seconds and undone), then a real join; it showed that Roostack didn't restart afterwards (restarts wait for the setup wizard, which a joining server never finishes), now fixed. Considered: keeping joining on the command line only (the one step that needed a terminal), and preselecting "A new lab" (most installs, but too easy to click past).
   - **The address — as built (2026-10-03):** the join code and the storage invite carry the address the other side connects to, chosen each time (it depends on where the other side is) from what Roostack knows: this server's home-network addresses (joining only; one per real network interface), a name from the domain (`link.<domain>`), the public address (the home's, or the server's on a lab on the internet), or another address (a VPN, a router forwarding another outside port, another dynamic DNS name, a test VM behind QEMU's NAT). The last one used is suggested; otherwise the home-network address for joining at home, else the name. **`link.<domain>`:** at home Roostack keeps it pointing at the home's public address (it changes), but only once someone first chooses it, so a lab that never needs it doesn't publish its home's address; it doesn't wait for CrowdSec (it isn't a website); on a lab on the internet the wildcard covers it. `link` is reserved: no service can use it. Considered: a lab-wide setting (but the right address depends on where each new server or lab is), and keeping a free-text field (error-prone, kept as "another address").
   - **Direct links between servers — as built (2026-10-04):** servers dial only the controller, so a server backing up to another server's disk went through it (and before this, couldn't at all: the hub didn't forward). Now, where one of the two can reach the other, they get a WireGuard link of their own, carrying only their traffic: the controller hands each its links in its assignment (peers marked `# roostack link` in its interface file, so its link to the controller is never touched; a server dialled directly listens on UDP 51820, opened in its firewall). Where a server is reached: an address the Owner typed on Settings → Servers ("Direct links", host:port), else its home-network address when both are at home (never one the other has too: VMs behind one NAT), else the address it connects to the controller from when it's somewhere else (a server on the internet). A link with no WireGuard handshake within 3 minutes is dropped for a day (a new address retries at once), and their backups go through the controller: it forwards only the backup store port between servers (its interface alone forwards; every server's forward chain drops anything else to, from or within Roostack's network). The backup plan says which path a backup to another server's disk takes. Considered: always through the controller (simple, but twice the controller's traffic, and its upload at home); a full mesh with hole punching (only when a real case needs it, as before).
   - **UDP and port forwarding:** a guest must be able to reach the host's port from the internet. Roostack opens the UDP port in its own firewall, then **explains port forwarding** on the storage page: which port (UDP, not TCP), to which server (its home-network address), a short how-to with common router names, and a **reachability check** (the guest's first connection, or a check from Roostack Cloud later) so the Owner knows it worked. As built (2026-10-03): the guest gives up after 20 seconds without a WireGuard handshake (the port can't be reached; waiting longer doesn't help) and says so, naming the provider's firewall and the router; a link that's up but unanswered is reported separately. The button shows "Connecting…" meanwhile. The same applies to the servers port (51820) when a server outside the home joins; the join page gets the same explanation. A Roostack Cloud relay can later remove the need for port forwarding (§10.5).

- **Storage for others on any server (2026-09-28):** the Owner chooses which server offers it (e.g. one with a big disk; the controller by default), only while no other lab stores anything. That server runs the guests' WireGuard link (`roostack-guests`, UDP 51821), their stores, and holds their data; the controller keeps the records and answers guests' requests (joining, usage), which that server forwards to it over Roostack's network (only from the server offering storage). Usage, free space and deleting a guest's data are asked of that server. A removed guest lab keeps its link for 30 days, hears about the removal (its Backups page and "needs attention" show when its backups there are deleted), and its data is then deleted (hourly check), or sooner if the host chooses.
