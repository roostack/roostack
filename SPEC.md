# Roostack Specification

This document records decisions (locked and pending) and the reasoning behind them. See PLAN.md for the project brief and TASKS.md for progress.

Status legend: **Locked** = agreed, **Pending** = under discussion, **Open** = not yet discussed.

**Name (2026-09-28):** the project is **Roostack**, pronounced "Roost Stack" (`roostack` in code, packages, paths and the Linux user). Its domain is **roostack.cloud** (the Go module path is `roostack.cloud/roostack`); **roost.ac** is for subdomains Roostack hosts for people's labs (§6.5). Earlier drafts called it MyLab; there was no release, so nothing migrates from that name.

---

## 1. Guiding Principles — Locked

1. **Recoverable by default.** A user can rebuild their entire lab on new hardware from a single backup. This is the main test for design decisions.
2. **Declarative state.** Roostack stores the *desired* state (services, domains, settings) as files; podman is reconciled to match. This simplifies backups, workers, and debugging.
3. **Local-first.** Everything works without Roostack Cloud or internet access, except public TLS issuance and image pulls.
4. **Transparent output.** Generated artifacts (container definitions, proxy config) are human-readable and inspectable. A comfortable homelabber can always find where things live and what Roostack did.
5. **Simplicity.** Small codebase, minimal dependencies, each chosen collaboratively for maintainability.
6. **Secure by default.** Rootless where possible, nothing public unless explicitly opted in.

## 2. Target Users — Locked

- **Primary:** less technical users who manage a lab after someone else has installed it (e.g. a NUC set up by a family member). Day-to-day management, including installing new services, must be possible entirely from the web UI.
- **Secondary:** comfortable homelabbers, who must be able to inspect and understand everything on disk.
- **Rationale:** Installing Linux and Roostack is an acceptable technical barrier; managing the lab afterwards must not be.

## 3. Deployment Targets — Locked

- **v1:** a dedicated, freshly installed server. Roostack assumes it owns the host.
- **Reference hardware:** x86_64 Intel NUC-style device.
- **ARM64 — as built (2026-10-13):** the same package for arm64 (`roostack_<version>_arm64.deb`), for ARM mini PCs and ARM cloud servers running Debian's own Debian 13 (§3.1). Every pinned image must have amd64 and arm64 builds (`make check-images`); a service whose image has none for a server's processor fails with a sentence saying so. Plan and progress: ARM64-PLAN.md.
- **Next:** Raspberry Pi 4 and 5 on Raspberry Pi OS (ARM64-PLAN.md, Phases 2–4). Older Pis (3, Zero 2 W) unsupported for now; reconsidered once Roostack's own memory use is measured (2026-10-13).
- **Rationale:** A dedicated host avoids conflicts with existing software (ports, podman config, firewall) and greatly reduces the support burden.

### 2.1 Licence — Locked (2026-10-18)

- **Apache-2.0** (the project's Owner; assumed from 2026-10-13, confirmed 2026-10-18). Roostack is open source: `LICENSE`, with `NOTICE`, and the package's copyright file says the same.
- **Why:** permissive like MIT, plus an explicit patent grant and a statement that contributions come under the same licence, which suits infrastructure others build on. Roostack Cloud imports Roostack's public packages (`cloudapi`, `authkit`), so a permissive licence lets it use contributors' code without a contributor agreement.
- **Considered:** MIT (the simplest, but no patent clause; the Owner's first thought); AGPL-3.0 (would stop a closed hosted fork, but Cloud's use of contributed code would then need contributors to sign over rights, and it puts some contributors off).
- Packaged services keep their own licences; the website shows each one.

### 3.1 Supported Distros — Locked

| Tier | Distros | Meaning |
|---|---|---|
| **Fully supported** | Debian 13 on x86_64; Debian 13 on arm64, from Debian's own installer or cloud image, on a machine that boots it with UEFI | Tested; installer supported; full host OS management (§3.2) |
| **Planned** | Ubuntu 26.04 LTS | Add when practical; avoid Debian-only assumptions that would make it hard |
| **Unsupported** | Anything else with Podman 5+, including ARM boards that need a vendor's image or kernel (e.g. Armbian) | May work; no host OS management, no support |

- **Rationale:** Debian 13 ships Podman 5.4, has a ~5-year support cycle, rarely changes, and has built-in unattended security updates, which makes it well suited to servers nobody logs into. Supporting a single distro keeps the installer, testing and docs simple.
- **Rejected:** Fedora Server (a major upgrade every ~13 months doesn't suit unattended servers); Ubuntu 24.04 (Podman 4.9 has no `.pod` Quadlets); Fedora CoreOS (unfamiliar and harder to troubleshoot).
- Distro-specific logic (package management, update tooling) should sit behind a small internal interface so Ubuntu can be added cleanly.
- **ARM64 (2026-10-13):** a UEFI arm64 machine on Debian 13 runs Debian's own kernel and updates, so to Roostack it's no different from the NUC. Boards that need a vendor's kernel get their kernel and updates from elsewhere, so §3.2 can't promise anything for them. Raspberry Pi OS will be the one vendor OS supported (ARM64-PLAN.md). Considered: Armbian (many boards, each with its own kernel and quirks; later, if people ask).

### 3.2 Host OS Management — Locked

- **Look — Locked (2026-09-27):** a design system with built-in colour themes (docs/DESIGN.md). The default is Teal and violet; each user can choose another (Ocean and magenta, or themes from popular open-source palettes: Catppuccin, Gruvbox, Nord, Solarized, Everforest, Rosé Pine, Tokyo Night) and light, dark or follow the device. Every theme must pass WCAG contrast checks in both modes (a test enforces it).
- **Brand mark and wordmark — Locked (2026-10-01), as built:** chosen with the project's Owner from mock-ups. Files, colours and how to regenerate them: `assets/brand/README.md`.
  - **Marks:** **Perch** (a hen on two rack servers with green "online" lights) is the primary mark; **Nest and egg** (a cracked egg on three woven layers) is the alternate. Each has a Roostack Cloud version (the hen on a cloud server, the egg in a cloud). A simpler **small mark** (the hen on one server) is the favicon, the app's top-bar mark and the help site's logo, because the full mark's details blur below about 32px.
  - **Colours:** the default theme's own: text colour on a `--highlight-soft` tile, the comb, wattle and cloud in `--highlight`, the egg's crack and every other cut-out in the tile colour, and the online light in the status green that shows on a text-coloured shape (`--ok-on-fg`). In Roostack the mark follows the user's theme; the files in `assets/brand` use Teal and violet. Considered: the first draft's own palette (red comb, amber beak, blue cloud: red reads as "danger" in Roostack, and it ignored the themes), a violet bird, and gold or coral accents outside the themes; the Owner preferred the quieter tile.
  - **Wordmark:** lowercase "roostack" in Space Grotesk (OFL): "roo" medium and "stack" bold for Perch, all medium for Nest; Roostack Cloud adds "cloud" in the highlight. The text is converted to outlines, so nothing loads a web font (the UI and help keep the device's own fonts, §6.3.1).
  - **Taglines** (for the website, not the UI): Rule your own roost. · Bring your stack home to roost. · Every service, home to roost. · Hatch your own cloud. · Your whole lab, under one roost. · Free-range servers. Fenced-in security.
- **Feedback on host operations — Locked (2026-09-27):** anything that acts on the host (OS updates, backups, applying service changes, setup hooks, restores) shows a one-line status that updates live ("OS updates: Installing updates…", then "✓ … finished: Installed 3 updates"), with the full step-by-step log and command output under a collapsed **Details** for technical users. Pages refresh their results when the operation finishes. Logs are kept in memory (latest run of each kind); results that matter later are stored separately.

- On fully supported distros, Roostack manages the host OS: security/package updates, reboot handling, and eventually major version upgrades.
- Users must be told clearly (docs and UI) that major manual changes to the host OS may limit Roostack's ability to manage it.
- **Rationale:** The primary user (§2) cannot maintain a Linux host. An unpatched host undermines everything else.

#### Time zone — Locked (2026-09-26)

- Roostack shows and schedules everything (nightly backups, maintenance windows) in the **host's** time zone.
- The setup wizard's first step confirms it, pre-filled from the browser's zone; the Owner can change it in Settings. `roostack-agent` applies it with `timedatectl set-timezone`, then Roostack restarts, because Go reads the local zone once at startup.
- If the browser's UTC offset differs from the host's, every page shows a prominent banner saying times are the server's, with a link for the Owner to change it.
- **Rationale:** cloud images and VMs default to UTC, which silently moved the "02:00" backup to midday for a user in Melbourne.

#### Update & reboot policy — Locked

| What | Policy |
|---|---|
| Security updates | Automatic, daily (`unattended-upgrades`, managed by `roostack-agent`) |
| Other Debian stable updates | Automatic (stable only receives bug and security fixes) |
| Reboots | "Reboot pending" shown in the UI; automatic reboot in a maintenance window (default 04:00). The Owner can change the window or choose notify-only |
| After reboot | Services return through systemd; Roostack health-checks them and flags failures |
| Major upgrades (e.g. 13 → 14) | Never automatic. Owner-initiated, guided, only once Roostack supports the new release, and only after a fresh successful backup |
| Roostack itself | Patch releases automatic; minor/major releases notify and need approval (same as services, §7) |
| Unknown host changes | Basic detection (extra apt sources, held packages, a changed firewall) triggers a warning; more thorough checks later. As built (2026-09-28): per server, on its Updates page and in "needs attention"; the Owner can mark the current changes as made on purpose, and anything new warns again |

- `unattended-upgrades`' own automatic-reboot option is **disabled**; only Roostack decides when to reboot.
- **How it runs (2026-09-27):** Roostack ships `/etc/apt/apt.conf.d/52roostack-unattended-upgrades` (adds stable-updates, no automatic reboot, removes old kernels). Every night after the 02:00 backup, the coordinator runs an "OS updates" job: `roostack-agent` runs `apt-get update && unattended-upgrade` in a transient unit (outside its own sandbox). The job is queued separately from the backup, so a failing backup doesn't hold back security fixes. Debian's own apt timers stay enabled as a fallback. `/run/reboot-required` (written by the kernel's postinst hook) is checked after each run and every 30 minutes; the coordinator then reboots in the window through the agent.
- The Owner sees the last run, any pending restart and why it waits, and can **check for updates now**, **restart now** (refused while a maintenance job runs), and choose automatic restarts at a chosen hour or notify-only (`lab.yaml`: `maintenance.restart`, `maintenance.restart_hour`).
- **Rationale for automatic reboots:** otherwise the primary user may run an unpatched kernel indefinitely. A brief overnight interruption is the better trade-off.

#### Maintenance coordinator — Locked

A single coordinator in `roostack` sequences every disruptive operation (backups, prunes, restores, service updates, package upgrades, reboots) so that conflicting operations never overlap.

- **Nightly order:** backup → automatic service updates → reboot if needed. This means there's always a fresh backup just before any automatic change.
- **Reboots wait** for running backups, restores and updates, then happen once they finish, within the window.
- **Never interrupted:** restores, major OS upgrades, and a backup's prepare step (services stopped or database dumps being written).
- **Resumable long jobs** (e.g. a multi-day first off-site upload) may be paused for a reboot that has been pending for longer than a deadline (default 24h, configurable), and they resume automatically afterwards. restic's repository stays consistent when interrupted.
- The UI explains why a reboot is waiting (e.g. "waiting for backup to finish, 62%").
- **Rationale:** fixed time windows can't handle jobs of unpredictable length. Delaying kernel security fixes for days is worse than pausing a resumable upload.

## 4. Roostack Cloud — Locked (scope), Open (design)

- A future paid hosting service for: resilience (critical services away from home internet), off-site backup targets, and users without their own hardware who still want to own their data.
- **Out of scope for v1**, but worker communication and backup formats must not preclude it.
- Implication: data portability is essential. A user must be able to move services and backups between home, VPS, and Cloud freely.

## 5. Users & Access — Locked

- **Roostack accounts are separate from service accounts in v1.** Roostack manages who can log in to Roostack; each service (Immich, Vaultwarden, …) manages its own users. Unifying them is part of the deferred SSO decision, and the design should allow Roostack to become the identity source later.
- **Fixed roles (not customisable in v1):**

| Role | Permissions |
|---|---|
| **Owner** | Everything: host settings, OS updates, backups and restore, recovery key, user management. At least one Owner must exist. |
| **Admin** | Install, configure, update and remove services; run backups; view logs. No host-level settings, no user management. |
| **Member** | View the dashboard (service links, status) only. |

  - Rationale: the person who sets up the lab (Owner) keeps control of risky host settings, while the day-to-day user (Admin) can still manage services freely.
- **Authentication:** local accounts, passwords hashed with argon2id. **TOTP 2FA** in v1, required for Owners and for any public admin UI. Passkeys later.
  - **Who must use two-factor — as built (2026-10-16):** Owners always; Admins while Roostack's own pages are public (a lab on the internet whose UI isn't kept to an SSH tunnel, §6.12), since an Admin can reveal service secrets, run actions and change services. Until they turn it on, every page sends them to Two-factor, which says why. Members never have to (they only see the dashboard). Making the UI public later asks existing Admins to enrol at their next page. Found by the security review of 2026-10-16 (M16): only Owners were asked. Considered, and chosen against by the project's Owner: requiring it of Admins on every lab (simpler, but a home lab's Admins reach the UI only from home).
- **Shared with Roostack Cloud — as built (2026-10-07):** the password, token and two-factor code is a public package, `authkit`, which Cloud's repository imports: one implementation. Both use the same argon2id settings (a lab has far fewer logins than Cloud, so it can always afford at least as much). Cloud, holding many accounts, also turns on a **pepper** (a key outside the database mixed into passwords) and **sealed two-factor secrets** (encrypted with a key outside the database), so a stolen database alone gives neither; a lab's database and keys are on one machine, where they wouldn't help. Fuzz tests try random input against it: the first runs found that a stored hash with out-of-range settings made argon2 panic (now refused, with limits on memory and rounds), and that base64 accepted several spellings of one value (now strict). Considered: two independent implementations, against a bug shared by both (twice the security-sensitive code to keep right).
- **Password recovery:** host command line only (`sudo roostack user reset-password <name>`, `reset-2fa <name>` for a lost phone). No email reset (it would need mail setup and adds attack surface), and no recovery codes: the command line is simpler for a home lab.
- **People page (2026-09-27):** the Owner adds people (a temporary password is shown once and must be changed at first login), changes roles, gives someone a new temporary password, turns off someone's two-factor, and removes people. Not on their own account (use Account), and the last Owner can't be demoted or removed. An Owner who forgot their own password uses the command line.
- **Signing out after inactivity — Locked (2026-10-03):** a session ends after a while without activity, 30 minutes by default; the Owner chooses 15 or 30 minutes, 1 or 4 hours, or never (Settings → People → Signing in). Activity is opening a page or sending a form; parts of pages refreshing themselves (htmx requests) aren't, so an open tab doesn't keep a session alive, and once it has ended they take the page to the login page, which says why. Without "keep me signed in" the cookie also ends when the browser closes. **"Keep me signed in"** on the login page (offered unless the Owner turns it off) keeps that browser signed in for 30 days with no idle limit, for someone's own device; it carries through the two-factor step and a password change. Sessions record when they were last used (saved at most every 30 seconds); the hourly session clean-up also deletes those past the idle limit, so relaxing the limit later doesn't bring old ones back. Considered: counting refreshes as activity (a tab left open would never sign out), and a countdown warning before signing out (more code and noise; the page simply goes to the login page).
- **Audit log:** records who did what and when, to support remote help and troubleshooting. *Since 2026-10-16* it also records failed logins (naming the account only when one has that name, so a password typed into the username box isn't kept, in the journal either), a person's change to their own notification address, new public-access check links, cancelling or dismissing Roostack Cloud's link notes, and risks accepted for the Owner's own packages on install and update (security review of 2026-10-16).

### 5.1 Roostack Data Storage — Locked

- **Desired state:** readable YAML files in `/var/lib/roostack/` (Principles 2 and 4).
- **Runtime data** (users, sessions, audit log, job history): a **SQLite** database in `/var/lib/roostack/`. A single file, no server, easy to back up. The backup prepare step must take a consistent copy (SQLite online backup / `VACUUM INTO`), not a raw copy of the file.

## 6. Container Runtime — Locked (principle)

- Podman, **rootless where possible**; rootful only where a service genuinely requires it (e.g. low ports, host networking, device access), and this is visible to the user.
- **Rationale:** security is a priority; rootless limits the blast radius of a compromised container.

### 6.1 Roostack Process Architecture — Locked

Roostack runs **directly on the host** (not in a container), as two processes shipped in one `.deb` package:

| Component | Runs as | Responsibilities |
|---|---|---|
| `roostack` | Unprivileged `roostack` user, strict systemd sandboxing | Web UI, API, desired state, rootless service management (Quadlets, status, logs) |
| `roostack-agent` | root, in a systemd sandbox | A small fixed set of privileged operations only: OS updates, reboots, the firewall, WireGuard, backup drives (listing, mounting, preparing blank disks) and folders, the host time zone, SSH's keys-only setting (§6.10). Listens on a local socket that only root and `roostack` may use, from the host's own user namespace. (Rootful Quadlets were planned here; nothing needs them yet.) |

- Nodes in a multi-server lab run the same package (§10).
- Roostack updates itself through apt, alongside host OS updates (§3.2), from its own apt repository (§7.2).
- **Installing it — as built (2026-10-18):** one command, `curl -fsSL https://dl.roostack.cloud/install.sh | sudo sh` (`scripts/install.sh`, addresses confirmed by the project's Owner on 2026-10-18; the key's hash and the suite are filled in at the first release). The script is short so it can be read first, downloads nothing but the release key, and does exactly the help's manual steps: checks Debian 13 on amd64 or arm64; fetches the key and checks the **SHA-256 of the whole key file** against one written into the script before installing it as `/usr/share/keyrings/roostack-archive-keyring.gpg`; writes `/etc/apt/sources.list.d/roostack.sources` (deb822, `Signed-By` that keyring only, the current minor series' suite); `apt-get update` and `apt-get install -y --no-install-recommends roostack` (Podman's recommended extras left out, about 300 MB: Roostack depends on the ones it uses, `aardvark-dns` and `ca-certificates` included, since 2026-10-18). The package ships the same two files and keeps them up to date from then on. Everything runs from a function called on the last line, so `curl | sh` can't run half a script, and apt can't swallow its rest from standard input. `ROOSTACK_REPO`, `ROOSTACK_SUITE` and `ROOSTACK_KEY_SHA256` point it at a test repository (plain HTTP allowed only then). **Why the file's SHA-256, not the OpenPGP fingerprint:** a fresh Debian 13 has no `gpg` to print one (apt checks signatures with `sqv`), and pinning the whole file also refuses a second key added to it; the help's manual steps show the fingerprint for people with `gpg`. A re-exported key (a new expiry) means a new `install.sh`, published with it. Considered: the key inside the script (no download at all; kept as a separate file so the manual steps and the script fetch the same thing).
- `roostack` is hardened with systemd sandboxing (`ProtectSystem`, `ProtectHome`, `NoNewPrivileges`, `PrivateTmp`, system call filtering, limited writable paths) to get most of a container's isolation.
- **`roostack` never runs `podman` directly — Locked (2026-09-26).** Rootless Podman needs the setuid `newuidmap`/`newgidmap` helpers, which `NoNewPrivileges` disables. So `roostack` only talks to the `roostack` user's systemd manager (`systemctl --user`, `systemd-run --user`), which runs Podman outside the sandbox. One-off commands (creating secrets, database dumps, `podman unshare` for backups) go through `systemd-run --user`.
- **Rationale:**
  - Keeps root code small and easy to review; privileged operations are explicit, not implied by broad socket access.
  - Podman/Quadlets rely on host systemd for lifecycle, so a containerised manager would need root-equivalent host access anyway.
  - Two components, a standard Debian install and update path, and no "container updating itself" problem.
- **Considered:**
  - *Container + many host mounts (Portainer/Komodo style):* those tools rely on the Docker daemon socket, which is root-equivalent. Under Podman they would also need the Quadlet directory, systemd D-Bus access, and a root agent regardless.
  - *Container web UI + host agent (A′):* a valid design that isolates the web-facing part. Rejected for now: it means either much more root code or three components, and the gain is limited because the agent API must allow arbitrary service deployment. The roostack↔agent API boundary leaves this option open later.
  - *Single root process:* rejected; the web UI would run as root.
- This deviates from PLAN.md's original "roostack orchestration container" wording. Services still run in containers; Roostack itself does not.
- **Root never works in the roostack user's folders — as built (2026-10-16).** `/var/lib/roostack` and `/srv/roostack` belong to the `roostack` user, so anything running as it (the service, or something that broke out of a container) can put a symlink there, and root following it would write wherever it points (`fs.protected_symlinks` only guards world-writable sticky folders like `/tmp`). Found in the security review of 2026-10-16 (H6). So:
  - **Commands that work on Roostack's files run as the `roostack` user, even with `sudo`.** `roostack user`, `roostack backup` and `roostack apply` started as root run themselves again as `roostack` (its UID, groups and systemd session) before reading anything. `roostack node join` does the join as `roostack` (its files and the agent calls; the agent accepts `roostack`) and keeps only the restart of the service as root. The process run as `roostack` gets no terminal: it runs in a session of its own and its output comes back through pipes with control characters removed, since another `roostack` process could take it over and type into root's terminal (TIOCSTI, which Debian 13's kernel turns off anyway) or send it escape sequences. A side effect: `sudo roostack backup snapshots` now works without `sudo -u roostack XDG_RUNTIME_DIR=…`. *Considered:* `runuser`/`setpriv` (the same, through another program; Go's `os/exec` sets the user itself), and opening every file with `O_NOFOLLOW` as root (every path in the code, easy to miss one).
  - **The database refuses symlinks.** SQLite follows a symlink for the database file itself, and the modernc driver can't pass `SQLITE_OPEN_NOFOLLOW`; it opens `-wal` and `-shm` without following (docs/ASSUMPTIONS.md S1). `store.Open` refuses any of the three that isn't a plain file.
  - **Drives (review M17, M18):** what `lsblk` says about a drive comes from the drive, so a crafted USB stick chooses its label, model and UUID, and lsblk's JSON brings back a newline in a label (docs/ASSUMPTIONS.md S5). The agent drops control characters from names, accepts only UUIDs shaped like one (8-4-4-4-12 hex, XXXX-XXXX or 16 hex digits), and refuses an fstab line with a field holding whitespace, a control character or `#`. It erases only a disk with no filesystem backups could use, nothing mounted and nothing in `/etc/fstab` (by UUID, PARTUUID, label or device): an idle backup drive is only automounted, so "not mounted now" let the roostack user erase it. So "Erase it and start afresh" for a drive Roostack could use is gone (the Owner's choice, 2026-10-16); erase it elsewhere first. *Considered:* also allowing drives with a filesystem that aren't in fstab (the roostack user could still erase any other drive plugged in), and the Owner's confirmation passed to the agent (the agent can't tell it from a request the roostack user makes up).
  - **The agent's inputs (review Lows):** WireGuard keys must be exactly what base64 writes for 32 bytes (Go's decoder skips newlines, which would then reach a wg-quick file inside a key). A typed backup folder must exist already: the agent makes only the `roostack` folder inside it (it used to make any missing folders on the way, owned by `roostack`), in a handle on the folder opened through an `os.Root`, opens it with `O_NOFOLLOW` and changes its owner through that handle (`fchown`), so a symlink swapped in midway is never followed.
  - **The agent's sandbox:** `roostack-agent.service` lets it write only to `/etc/fstab`, `/etc/sysctl.d`, `/etc/wireguard`, `/etc/roostack`, `/etc/ssh/sshd_config.d` (added 2026-10-17, §6.10 item 3), `/mnt`, `/media` and `/srv` (`ProtectSystem=strict`), with Unix and netlink sockets only, a capability bounding set of what its jobs use (`CAP_NET_ADMIN`, `CAP_SYS_ADMIN` for partition tables, `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, `CAP_DAC_READ_SEARCH`) and `@system-service` system calls. OS updates and reboots run in transient units outside it. Its socket moved to `/run/roostack-agent/agent.sock`, its runtime directory, since `/run` is read-only to it. Every job was checked on a VM (docs/ASSUMPTIONS.md S7).
  - **Only callers from the host's own user namespace:** `SO_PEERCRED` can't tell a rootless container's root (the `roostack` UID to the kernel) from the service, so a container given the socket in a bind mount (a package of the Owner's own can mount one; the registry's policy refuses it) could call the agent (docs/ASSUMPTIONS.md S6). The agent now refuses callers whose user namespace isn't the host's: their `uid_map` must map every UID to itself, read through a pidfd so a reused PID can't pass. Agreed with the Owner (2026-10-16). *Considered:* documenting it and relying on the package policy (H2 showed it can be bypassed).
  - **The installer:** `postinst` makes the folders inside `/var/lib/roostack` and `/srv/roostack` only when nothing is there (on every upgrade, `install -d` would have followed a symlink there and given its target to `roostack`, docs/ASSUMPTIONS.md S2), and the install message reads the setup code as `roostack`, keeping only the characters a code has.

### 6.2 Language: Go — Locked

- Both `roostack` and `roostack-agent` are written in Go, in a single codebase.
- **Rationale:** Builds a single static binary, which makes `.deb` packaging trivial. Low memory use suits NUC-class hardware. Podman is written in Go and there are mature systemd/D-Bus libraries. The language is small, readable and widely known, which fits the simplicity principle. The maintainer wants to learn it.
- **Considered:** Rust (steeper learning curve, slower to build with); Python (easiest to write, but harder to package and ship as a host service).

### 6.2.1 Releases: signed and reproducible — as built (2026-10-18)

Part of "encryption anyone can check" (TASKS): what a lab runs should be checkable against the published source, not taken on trust. Details and the key's ceremony: docs/RELEASING.md.

- **A release is a tag** `vMAJOR.MINOR.PATCH` on `main`. Pushing it runs `.github/workflows/release.yml`, which builds both packages (amd64, arm64), the plain `roostack` binaries (for the registry's Publish workflow, §8.3.3) and `SHA256SUMS`, signs `SHA256SUMS`, and hands the files to `apt-publish.yml`, which publishes them at `dl.roostack.cloud/releases/<version>/` and in the apt repository. Not GitHub's releases: the repository is private.
- **Reproducible:** the same tag builds the same bytes anywhere. `scripts/build-release.sh` (`make release`) pins the Go release (the go tool fetches it), uses `-trimpath` and an empty build ID, ignores the builder's go settings, and builds the help site with the Zensical in `uv.lock`; `build-deb.sh` dates every file with the commit's time, sorts, and compresses on one thread. The workflow builds in a Debian 13 image pinned by digest, twice (two runners, two folders), and stops unless both builds are identical. Considered: comparing only the binaries (the .deb is what servers install, so it must match too); Ubuntu's own tools on the runner (they change with the runner image, so a later rebuild might not match).
- **Signed with one OpenPGP key** (Ed25519): the primary key certifies only and stays offline; a signing subkey, without a passphrase, is the secret of a GitHub environment `release` that waits for a reviewer. The same key signs the apt repository, and the package installs its public half as apt's keyring, so updates to the key reach labs with Roostack's updates. Considered: a passphrase on the CI copy (it would sit beside the key in the same environment, protecting nothing more); the primary key in CI (a leak would mean replacing the key on every lab); Ed25519 signatures with the registry's tooling (apt checks OpenPGP).
- **Guards:** no release without the registry's real root key (§8.3.3) or with a development build, from a changed checkout, from a tag `git describe` doesn't give, from a commit not on `main`, or while the committed public key is the placeholder.

### 6.3 Web UI: Go templates + htmx + Alpine.js — Locked

- Server-rendered HTML, embedded in the `roostack` binary. No JavaScript build step.
- Step-up approach for interactivity. Use the lowest level that works:
  1. **htmx** for server interactions (default)
  2. **Alpine.js** for small in-browser behaviour (toggles, show/hide, simple validation)
  3. **Standalone JS libraries** for heavy widgets (e.g. xterm.js for a terminal, a chart library)
  4. **A separately built component** only when a feature genuinely needs it, decided case by case
- **Architecture rule:** business logic lives in core Go packages. HTTP handlers are a thin layer on top. This keeps the UI replaceable and supports the master/worker API and a possible CLI.
- **Rationale:** Roostack's UI is mostly forms, lists, status and logs, with state held on the server, which is htmx's strength. Validation lives in one place (Go). A small toolchain suits the simplicity principle and a maintainer learning Go.
- **Rejected:** React islands. They bring back a Node build toolchain and a second UI paradigm for limited gain.
- **Known limits:** UIs with a lot of browser-side state (drag-and-drop dashboards, visual editors) would need step 4.
- **Live updates — as built (2026-09-29):** parts of pages that show changing state (the home page, Services, the Backups status card, the drive list) poll with htmx, and are kept cheap: they poll **only while the tab is visible** (and refresh once when it becomes visible again); each poll sends a fingerprint of what the part shows, and the server answers **204 No Content** when it's unchanged, so htmx leaves the page alone (nothing to download or redraw; open panels, selection and scroll stay put); the controller **shares its reads of other servers** for 10 seconds, so several open tabs cost one round of calls (any change forgets them); and responses are **gzip-compressed** (a page is about a third of its size). Activity logs poll every 2 seconds only while something runs. **Later:** push instead of poll, once Roostack moves to htmx 4, with its WebSocket support (`hx-ws`); see TASKS.
- **Sizes — Locked (2026-09-28):** shown in decimal units everywhere (1 GB = 1,000,000,000 bytes; kB, MB, GB, TB), as drive makers, macOS and most people count them, so an "8 GB" USB drive reads 8.0 GB. One formatter (`internal/units`) serves the UI, logs and the CLI, and sizes people type (e.g. a storage quota in GB) use the same units. Binary units (GiB) were considered: exact, but unfamiliar to most people, and a drive would read smaller than its label.

### 6.3.2 Reaching the UI — Locked (2026-09-30), first run from the home network (2026-10-18)

- **The UI listens on `127.0.0.1:8480` only** (apart from the setup pages during first-run setup, below). With a roost.ac name, it is served at the name itself (`https://smiths.roost.ac`, §6.6); with an own domain, at `https://roost.<domain>` (named `roostack.<domain>` until 2026-10-01; shortened by the project's Owner) through Caddy, to the home network only (private). Without one, it's reached over an SSH tunnel (`ssh -L 8480:127.0.0.1:8480 …`), which works the same on Windows 10/11 (PowerShell), macOS and Linux, but is a hard first step for people who don't use a terminal, hence the setup pages on the home network below. The installer shows the command with the server's address filled in; on a server joining an existing lab, it points to `sudo roostack node join <code>` first, which needs no setup page.
- **First-run setup from the home network — Decided (2026-10-18), as built:** until setup is finished, Roostack also serves its setup pages, and only those, over **HTTPS on port 8443 to the home network**, with a **self-signed certificate** made at its first start (`/var/lib/roostack/setup-tls.crt` and `setup-tls.key`, 0600). The installer's message and the log (`journalctl -u roostack`) show the address by IP (`https://192.168.1.20:8443`), the certificate's **SHA-256 fingerprint** to compare with the browser's warning, and the setup code. The SSH tunnel still works, and the installer shows it as the other way. **Why:** the tunnel needs a terminal, which the people Roostack is for often don't use; a phone or laptop on the same network is what they have. **Rejected:** plain HTTP (considered 2026-09-30): the setup code and the Owner's password would cross the network readable by anyone on it; listening publicly; a real certificate (no name exists yet; Let's Encrypt's IP certificates need the server reachable from the internet).
  - **How long — decided (2026-10-18) in the security review of this work, confirmed by the project's Owner the same day:** until the wizard is finished (its last step, or setup finished over a tunnel, checked every 30 s), not only until the Owner exists, so the Owner isn't left mid-wizard needing the tunnel after all; and **never more than 24 hours after the Owner was made**, finished or not. The 24 hours count from the account's `created_at` in the database, so a restart doesn't start them again. Considered: stopping at the Owner (the rest of the wizard over the tunnel). The wizard's last step shows **Setup is finished** on the listener with where Roostack is from now on (the lab's address, or the tunnel); past the 24 hours, a page asked before the listener notices (within half a minute) shows **This setup page has closed** with the tunnel command (setup carries on there where it was left); after that the port is simply closed, and the help says why. Then the listener stops, the port closes, the certificate is deleted and everything signed in on it is signed out; from then on it's `127.0.0.1:8480` and Caddy as before. A server joining a lab, or a restored lab, never opens it again (its certificate and sessions are deleted at the next start).
  - **What it serves, and to whom** (`internal/web/firstrun.go`): only the first-run routes, even to the Owner: the first-run pages and wizard, logging in, two-factor set-up, and what the wizard's pages load or post to (its address step's Cloud link and network choice, the backup step's live log, a backup destination's location), the help and static files; everything else is 404. Before the Owner exists, the setup code guards them. **Once the Owner exists, every route needs the Owner signed in on the listener**, and only two-factor set-up until it's on; anyone else gets the login page (and its static files), and the setup code no longer works there.
  - **Its sessions and cookies work only on it:** a session records where it was signed in (`sessions.origin`: `setup` on the listener, empty on Roostack's own pages), and each is refused on the other, so a cookie the browser also sends elsewhere (cookies are per host, not per port) gets nothing there, and one from Roostack's own pages gets nothing on the listener. The same holds for the setup code's 30-minute pass, a login waiting for its two-factor code and a lab restore's search (kept in memory, tagged with where they were made); the listener sets no "known device" cookie and offers no "keep me signed in". When the listener stops, all of them are revoked (and again at Roostack's next start, if it stopped with Roostack).
  - **A lab restore started on the listener (as built, 2026-10-18):** the restore ends with Roostack restarting as the restored lab, which closes the listener (the restored lab's Owner is older than 24 hours, or its wizard is done), so the progress page can't follow it to the login page as it does over the tunnel. Instead, on the listener, the finished restore says that this setup page closes, and where to go: the lab's address from its restored settings, if it has one that opens from home, and the SSH tunnel with the server's address filled in. The same words are in the page from the start, hidden, and show if the page stops getting answers before it saw the end (the restart came first). *Considered:* keeping the listener open for a while after a restore (it would serve the restored lab's login to the home network, which the 24-hour rule is there to stop).
  - **Linking to Roostack Cloud from the listener** (the address step's roost.ac name): the lab asks Cloud to send the browser back to the form's `Origin`, here `https://<home address>:8443/setup/address/linked`. Acceptable: the address carries no secret (Cloud shows the place it's sending the browser to first), Cloud learns only a private address it can't reach, the page there needs the Owner's session on the listener (a top-level navigation, so the `SameSite=Lax` cookie goes with it), and if the listener has closed meanwhile the browser just can't load it: linking finishes by itself on the lab's side either way, and the Owner carries on over the tunnel.
  - **The firewall:** roostack-agent opens 8443 to the home network (`trust.HomeRanges`, the `lan4`/`lan6` sets) only while setup lasts (`Firewall.SetupPort`). Before the Owner has chosen the firewall (the wizard's SSH step), Roostack used to leave it alone entirely; now its table is there during setup with only that rule (`Firewall.Unchosen`: 8443 from the home network accepted, from anywhere else dropped, everything else accepted as before), and goes when setup is finished. The listener also closes connections that aren't from a home address to a home address before TLS, in case the firewall hasn't been applied yet. So a cloud server with only a public address never serves it: its installer message shows the tunnel.
  - **Someone else on the network setting it up first:** they'd need the setup code, which is only on the server (the installer's message, the log, a 0600 file). Its checks are unchanged: compared in constant time, half a second's wait after a wrong one, a 30-minute cookie once right, and checked again when the account is made.
  - **Someone in the middle** (ARP or DHCP spoofing) could show their own certificate: browsers warn about a self-signed certificate either way, so the installer and the help ask people to compare the fingerprint before going on. Someone who skips that check is no worse off than over plain HTTP, and Roostack can't do better without a name.
  - **DNS rebinding:** a page on another site whose name now points at the server can't complete a TLS handshake (the certificate isn't for its name, and scripts can't click through a warning), and the setup listener answers only requests whose `Host` is an IP address, never a name (421 otherwise). It doesn't require the server's own address: a port forward or a VM's network changes it on the way (found on the dev VM), and a page can only make a browser send an address it was itself opened at, which then goes to that address.
  - **Cross-site forms (CSRF):** as on the rest of the UI, a form must carry an `Origin` matching the `Host` (so it came from the setup page itself), and the setup code's cookie is `SameSite=Strict`. Nothing the setup listener receives is trusted as coming from a proxy (`X-Forwarded-*` are dropped).
- **Considered (2026-09-30), replaced by the above (2026-10-18):** serving the setup page to the home network over plain HTTP, only on a server with no public address. Rejected then and now: an option to listen publicly.
- **Open, for later: HTTPS by IP address.** Let's Encrypt issues certificates for bare IP addresses (short-lived ones), which could give a cloud server's setup page `https://<its address>` with a real certificate and no domain. Check whether Caddy can get one and how it renews, once public access has settled.
- **On a lab on the internet, the UI is public — Decided (2026-09-30) by the project's Owner, as built:** at `roost.<domain>`, as a public route: CrowdSec's bouncer (CrowdSec runs whenever the UI is public), 1000 requests per 10 s per visitor, and 10 a minute on `/login` and `/backups/recovery-key` (not `/setup`: the setup code can't be guessed, and the wizard's pages are under it). 2FA is required for Owners, and for Admins while the UI is public (§5). The Owner can keep it to an SSH tunnel instead (`public.ui_tunnel_only`), in the wizard's first step or Settings. Considered: tunnel only (safest, but the Owner of a cloud lab would need a terminal for everything).
- **Open: serving the UI through the domain as an explicit choice (at home).** At home, a domain automatically serves the UI at `roost.<domain>` (home network only). Proposed by the project's Owner (2026-09-30): make that something the Owner turns on once a domain is set. Questions: what is the UI reached by if it's off (the tunnel only?); does the wizard offer it at the domain step. (On the internet it's the choice above.)

### 6.3.3 Installing, step by step — Locked (2026-09-30); retries and restarts as built (2026-10-18)

- **Why:** a first install can take minutes (downloads, and on a brand-new server Caddy's image build), and the UI showed "stopped" with an **Open** link, or nothing at all, so people couldn't tell whether it had hung. Agreed with the project's Owner from a mock-up (2026-09-30).
- **As built (2026-09-30):** a new service (all its containers new) shows **installing** until its last step is done. Its page lists each step (done, in progress with "for …", or to do): *Downloading* and *Starting* each container ("the database (Postgres)", "the cache (Valkey)", or the service), *Making it reachable at its web address* (or *Waiting for Roostack's web proxy to finish building* while Caddy's image builds; left out while Caddy waits for the domain step), and *Finishing setup* if the package has install hooks. The log is under **Details** (the apply's, then the setup's). The Services list and Home show "Step 3 of 5: …" and no **Open** link; the address is shown greyed until it's running. Before its apply begins (e.g. waiting for another change), it shows one step, *Waiting for other changes to finish*. After 5 minutes on one step, the notice says it's taking longer than usual and when its log last changed. When it finishes, the page reloads to show it running.
- **How:** the node tracks installs in memory (`node.InstallProgress`, part of `ServiceDetail`, so other servers' installs show too), fed by the reconciler's progress events. Each new container's image is pulled first as its own step (`podman pull` through `systemd-run --user`, output in the apply log), so the download isn't hidden inside the unit's start (and its 5-minute pull timeout under systemd doesn't apply). New services start before a new Caddy, whose first start waits for its image build, so downloads run while it builds.
- **A failed install, and a restart halfway (as built, 2026-10-18):** a failed download or start shows **Try again** (Admins) beside the error, which applies again at once (`RetryInstall`, the same route as a failed setup's); the next apply or restart also tries again. The installs are kept in the server's settings (`installs`), not only in memory, so one cut off by a restart of Roostack still shows its steps afterwards. In both cases the containers' Quadlet files are already written, so a plain apply would only start them, with no download step; instead the node tells the reconciler which containers' first start didn't finish (`Reconciler.Unfinished`: every container of an install with a download or start step not done), and they're started as new ones again: downloaded first (quick if the image is there: `podman image exists`) and started one at a time, step by step. An install whose service has left the server is forgotten.
- **Not done:** download progress in MB. Without a terminal, `podman pull` prints a line per layer ("Copying blob …") and no progress (checked again on Podman 5.4, 2026-10-18); its progress comes only through Podman's API socket (a service Roostack doesn't run), or by watching the size of its temporary files, which the sandboxed daemon can't see. Left until there's a reason to run Podman's API.

People couldn't tell whether the lab was broken, the service was stopped, or the link was wrong.

The picture is a *scene*: the small mark's hen and server (or, for Roostack Cloud, the hen on a cloud), without its rounded tile, on a soft wash that fades out, with a few props (a nightcap for a stopped service, an egg hatching for one starting). Considered: the tile kept as a frame (felt like an icon, not a scene); plain icons without the mark (less recognisably Roostack).
- **As built (2026-10-13):**

### 6.4 Service Execution: Podman Quadlets — Locked

- Roostack generates **Quadlet** files (`.container`, `.volume`, `.network`, etc.) and systemd runs them. Rootless units go in `~/.config/containers/systemd/`.
- Users never write Quadlets directly. They are generated from Roostack's own service definitions (see §8).
- **Rationale:**
  - Official Podman feature (4.4+), maintained by the Podman project, and an open, well-supported format.
  - systemd provides start-at-boot, restart-on-failure, dependency ordering, and logging (`journalctl`) with nothing extra to build.
  - Designed for rootless operation (§6).
  - The generated files are plain text a homelabber can inspect (Principle 4), and they are declarative (Principle 2).
- **Rejected:** podman-compose. It is community-maintained, supports only part of the Compose spec, and needs extra pieces for boot and restart handling. Also rejected: running docker-compose against the Podman API socket, which brings back a daemon-style model with the same lifecycle gaps.
- Rootless services need `loginctl enable-linger` for the service user so they start at boot without anyone logging in.

### 6.5 Reverse Proxy & TLS — Locked

- **Proxy: Caddy**, run as a rootless container from a Roostack-built image that includes the DNS provider plugins.
- **DNS providers — Locked (2026-09-26):** Cloudflare, Amazon Route 53, Porkbun, Gandi, GoDaddy, Namecheap and Spaceship, defined in one registry (`internal/dns`). Each provider's credentials are stored as Podman secrets and passed to Caddy as environment variables, so they never appear in the Caddyfile. Before saving, the wizard checks credentials by **creating and deleting a temporary TXT record** through the provider's public HTTP API (Namecheap: a read-only check, since its API can only rewrite whole zones). That tests what certificate issuance needs.
- **Dependencies for provider APIs:** prefer plain HTTP calls or small generic libraries; avoid large vendor SDKs (e.g. the AWS SDK). Roostack's checks use the standard library only (including AWS SigV4 signing for Route 53).
- Roostack generates a readable Caddyfile from desired state and reloads Caddy (same pattern as Quadlet generation).
- **Not user-selectable.** One proxy keeps testing and config generation manageable. Users can add custom Caddy snippets, globally and per service.
- **Rootless on 80/443:** `roostack-agent` lowers `net.ipv4.ip_unprivileged_port_start` so the proxy needs no root.
- **Proxy networking (Option C) — Locked (2026-09-26):**
  - Caddy runs in its **own pasta network namespace** (`Network=pasta:--map-host-loopback,169.254.1.3`), publishing 80/443. Pasta keeps each visitor's **real IP**, which the private-route check and CrowdSec rely on.
  - Each routed container stays on its service's private network and is **published on `127.0.0.1:<port>`** only. Caddy reaches it at `169.254.1.3:<port>`, which pasta maps to the host's loopback. The Roostack UI listens on `127.0.0.1:8480` and is reached the same way.
  - Ports come from a central range (20000–29999), are allocated once, and are stored in the instance file (`routes.<name>.port`) so they never change.
  - **Why:** on the Debian 13 VM, rootless bridge networks replaced client IPs with `10.89.0.x` (Podman's `rootlessport`), which Caddy would treat as private, exposing "private" services to the internet. Rootless Podman can't put one container on both pasta/host networking and a bridge network, and the host side can't reach bridge addresses.
  - **Rejected:** Caddy on host networking (works, but shares the host's network namespace); a host-network forwarder using the PROXY protocol in front of a bridge-network Caddy (two proxies, no HTTP/3).
- **TLS: Let's Encrypt via DNS-01.** This is required so that private (LAN/VPN-only) services get valid certificates without being reachable from the internet.
- **Wildcard certificate by default** (e.g. `*.lab.example.com`), with services on subdomains sharing it. Rationale:
  - One issuance and renewal instead of one per service, so fewer rate-limit issues.
  - Subdomain names don't appear in public Certificate Transparency logs, so the list of services you run isn't published.
  - DNS-01 is already required, so there's no extra setup.
  - Trade-off: one certificate covers all services. That's acceptable on a single-owner host.
- **Rationale for Caddy:** best automatic HTTPS, readable config, easy custom snippets. **Considered:** Traefik (many DNS providers built in, but verbose config tied to container labels); Nginx + certbot (familiar, but TLS is a separate tool and config is verbose).

### 6.5.1 DNS Records & Local Access — Locked (2026-09-26)

Roostack manages the DNS records its services need, through the same DNS provider credentials used for certificates.

- **Private services (default):** one **wildcard record** (`*.<domain>`) pointing at the lab's **LAN IP**, in public DNS. Devices at home reach services without local DNS. Anyone can look the record up, but only the home network can reach the address, and service names stay out of public DNS (like the wildcard certificate).
- **Router DNS rebinding protection:** some routers drop DNS answers containing private IPs. Roostack **detects** this by comparing the home network's resolver with a public resolver, and shows instructions (allow the domain in the router, or use local DNS).
- **Local DNS** (e.g. Pi-hole) is optional, for later. Getting every device to use it means changing the router's DHCP DNS setting (router-specific, sometimes impossible). Roostack running DHCP itself was **rejected**: if the lab dies, the home network stops working.
- **Public services (stage 2):** explicit records pointing at the **public IP**; explicit records override the wildcard. Devices at home reach them via the router's NAT loopback (Roostack can test this).
- **Dynamic public IPs (stage 2):** Roostack updates the records itself (§6.11, 2026-09-30; ddns-updater was the earlier plan).
- **Cloudflare proxy (stage 3):** offered per public service, **off by default**, with advantages and disadvantages listed in the UI:
  - For: hides the home IP; DDoS protection; works around some ISP port blocking.
  - Against: Cloudflare decrypts the traffic (at odds with "own your data"); free plan upload limit of 100 MB per request; Cloudflare's terms restrict large media streaming on the free plan.
  - When proxied, Caddy trusts `CF-Connecting-IP` **only from Cloudflare's published IP ranges**, so the private check and CrowdSec still see real visitors.
  - Packages declare proxy warnings, e.g. large uploads (Immich, until its chunked uploads land) or media streaming (Plex, Jellyfin, stricter). The format is to be designed.
- **Ownership:** Roostack only changes records it created (tracked in its state, plus a comment where the provider supports it). An existing record with the same name that Roostack didn't create is never overwritten automatically; the UI explains the conflict. A record that already has the right value is adopted.
- **Taking over a record:** the Owner can explicitly take over a conflicting record from the dashboard. A confirmation page shows the current and new values, warns that anything relying on the current value stops working, and needs an "I understand" tick. The takeover is recorded in the audit log.
- **Switching management on or off** is done from the dashboard's "Home network access" card (Owner only), with the Namecheap risk opt-in where relevant, and applies without a restart. Turning it off leaves records in place.
- **Namecheap:** its API can only replace a domain's whole record set, so record management there is **off unless the Owner ticks an opt-in** with a clear warning, and strongly recommends another provider (e.g. Cloudflare).
- **No usable public IP (CGNAT):** public exposure needs a relay. Future options: Cloudflare Tunnel, or a Roostack Cloud relay (§4).
- **Stages:** 1) wildcard to LAN IP + rebinding check; 2) public records + dynamic DNS (with public exposure, firewall, CrowdSec); 3) Cloudflare proxy.

### 6.6 A lab's address (domains) — Locked, changed 2026-10-06

- **Before (2026-09-26 to 2026-10-06):** v1 required a user-owned domain, set up once at install, with `roost.ac` names planned for later. Built that way: the package installs a placeholder domain, and until a domain is set up nothing gets an HTTPS certificate. Untangling this is a task (TASKS, "Domain optional").
- **Certificates for an own domain — Locked (2026-10-06):** Roostack picks the best way available, automatically:
  1. **A supported DNS provider:** DNS-01 through the provider's API, one wildcard certificate (as today).
  2. **Benched (user, 2026-10-10): an unsupported provider.** Options 2 and 3 below were locked on 2026-10-06 and are kept as the design, but aren't being built now. The people they serve are few: they must be able to add CNAME records by hand, yet be unable to use any of the seven supported providers, when moving a domain's DNS hosting to one (Cloudflare is free) keeps the domain where it's registered. Meanwhile the help page says to do that. When this is built, both come together, and **reaching the lab on port 443 is a first-class choice** in the address step, not a hidden fallback.
     - **Through Roostack Cloud (lab linked):** DNS-01 by challenge delegation. Let's Encrypt wants a TXT record with a new value at every renewal (every 60 days, sooner as certificates get shorter), which nobody can keep up by hand; a CNAME added once (`_acme-challenge.<domain>` → a name Cloud gives the lab) moves that record to where the lab can write it, the mechanism a roost.ac name already uses. Still one wildcard; Cloud only touches that challenge name and never holds the certificate or its key. **Refined (2026-10-10):** the addresses should be a CNAME too (`*.<domain>` → a name under Cloud the lab keeps pointed at the right address, as for a roost.ac name), so the owner adds two records once and never touches DNS again, even when the server's or the home's address changes; otherwise they'd also keep A records up to date by hand. Needs a provider that allows a wildcard CNAME (nearly all); the bare domain can't be one, and isn't needed (Roostack is at `roost.<domain>`). A side benefit: Roostack holds no key to the domain at all, where most providers' API keys can rewrite the whole domain or account.

Let's Encrypt only issues wildcards after a DNS check, so each service gets its own certificate, and the names appear in public certificate logs (a wildcard hides them). Services only on the home network can't get a certificate this way.
- **Three states — Locked (2026-10-06), agreed from a mock-up:**

  - **A roost.ac name:** services at `photos.smiths.roost.ac`; **Roostack itself at the name** (`smiths.roost.ac`), not `roost.smiths.roost.ac`.
  - **An own domain:** as before, Roostack at `roost.<domain>`.
- **Choosing it — Locked (2026-10-06):** the wizard's step 3 is **"Your lab's address"** (was "Your domain"), and Settings → Domain and certificates becomes **Your lab's address**. ### 6.7 Storage Layout — Locked (defaults may change before launch)

Default paths:

```
/var/lib/roostack/                 # Roostack's own state: desired state, secrets, users
/srv/roostack/services/<service>/  # per-service data (bind mounts)
    data/
    db/
/srv/roostack/media/               # large shared media; can be a separate disk
```

- **Paths are configurable**, and all defaults are defined in **one central place** in the code so they can be changed easily. No migration support is needed before launch; the defaults will be locked before release.
- **Bind mounts, not Podman named volumes.** Data sits in a visible, predictable location (Principle 4), and it's easy to back up and move (Principle 1).
- The media location can be configured separately, e.g. a small system SSD plus a large data drive.
- **Open / to prototype early:** rootless user ID mapping. Files owned by UIDs inside containers appear as mapped IDs (e.g. 100000+) on the host. We need to settle how this affects browsing, backups, and media shared between services (e.g. Jellyfin and Immich), and where Podman's `keep-id` option helps.
- **Disk space — as built (2026-09-28):** each server reports the disk holding its Roostack data (`statfs` of `/srv/roostack`: total, used, free to the roostack user, and what the filesystem keeps back), with what Roostack's parts take: its services' data, the backups it keeps for the lab's servers, and those it keeps for other labs. Free and used space come from `statfs` alone (instant); only the breakdown is counted, with `du -s -B1` (space on the disk, as `df` counts it) at the lowest CPU and disk priority (`nice -n 19 ionice -c3`). `du` reads every file's metadata: quick on an SSD (300,000 files: under a second), but a large photo library on a spinning disk can take a minute or more and fills the kernel's metadata cache. So sizes are counted **once a day, right after the nightly backup**, while restic's reads of the same metadata are still cached, and otherwise only when a size is missing or over a day old (no backups set up, a new service); pages show the last count and when it was made, and never wait for one; while a count runs, the disk block says "counting…" and refreshes itself until it's done (2026-10-03: it said "not counted yet" until the page was reloaded). Settings → Servers shows it for each server, with a bar coloured by part (2026-10-03: services' data, the lab's backups, other labs' backups, the system; then the space promised to other labs and not used yet, striped; then free; and at the far end what the filesystem reserves for the system, striped grey), each part named with its size in a key underneath, and on the server storing other labs' backups, the space promised to them (their quotas) and how much of it they don't use yet. **Low space** is a warning below 5 GB or 10% free, and a problem below 2 GB or 5% (since 2026-10-17, on a disk under 20 GB the 5 GB and 2 GB become a quarter and a tenth of the disk: a 2 GB USB drive with 1.9 GB free was "running out of disk space"), shown on the home page and on Servers; so is having promised other labs more space than is free, and (2026-10-03) earlier, a warning once the space they could still add reaches into the 10% of the disk kept free for the lab's own services and backups. The backup plan shows the free space where each backup is (this server's drives, or another server's disk) and warns when it's nearly full. **Every disk — as built (2026-10-03):** each server reports every disk holding a folder Roostack uses: the system's (`/`), a separate disk for services' data or the backup store, a separate media disk, and each backup drive (the repository folder on it). Folders on the same disk (same device) count once; a disk is named by the most important folder on it (System disk, Data disk, Media disk, or a backup drive's name as the backup plan gives it, such as USB drive BACKUP; until 2026-10-17 "Backup drive <name>", which read "backup drive USB drive BACKUP") and shows where it's mounted when a server has more than one. Each disk's parts are what's on it: services' data split by folder (a service's `services` and `media` folders can be on different disks), the backup store's two parts, and a drive's backups; on a drive the rest is "Everything else". Low space, and the space promised to other labs, are per disk (promised space on the disk holding the backup store), and warnings name the disk when there's more than one ("This server's USB drive BACKUP is running out of disk space"). An unplugged drive isn't listed. Considered: listing every mounted filesystem (most mean nothing to Roostack's user, such as /boot/efi).

### 6.8 Databases — Locked

- **One database container per service** (e.g. Immich gets its own Postgres), not a shared instance.
- Roostack **standardises the pattern**: every package uses the same Roostack-managed Postgres/Redis setup, with the same data location (`<service>/db/`), backup method, health checks and upgrade process.
- **Rationale:**
  - Each app runs the exact database version and extensions it's tested with (e.g. Immich needs specific Postgres versions and a vector extension).
  - Upgrades and failures are isolated to one service.
  - Each service is self-contained, so moving it to another host or Roostack Cloud means moving one folder plus its definition (§4 portability).
  - The cost, roughly 30–50 MB RAM per idle instance, is acceptable on NUC-class hardware.
- **Rejected:** a single shared Postgres. It saves RAM, but it couples versions and upgrades, makes it a single point of failure, and makes backing up or moving one service harder.

### 6.9 Backups — Locked

**Tool: restic**, called as a CLI (`--json` output) behind a small internal interface (backup, restore, list snapshots, prune, check), so the tool can be swapped later.

- **Rationale:**
  - A Go single binary; encrypted and deduplicated, with many backends (local, SFTP, S3, B2, rclone, REST server).
  - Users can recover independently with the plain `restic` CLI and the recovery key, even if Roostack is broken. There's a large community and many docs (Principles 1 and 4).
  - Roostack owns scheduling and retention as part of desired state, so there's no competing policy engine.
  - The append-only `rest-server` keeps old backups from being deleted or overwritten by a server that's taken over, and is a natural future Roostack Cloud target. It doesn't stop that server *adding* files restic can't read, which can stop the repository working until they're removed (§10.10, "Junk in a repository").
- **Considered: Kopia.** It's faster, uses less memory (≈4 MB average chunks vs ≈1 MB, plus a memory-mapped index) and has a richer server. It's a realistic fallback if restic's memory or performance becomes a problem with very large libraries; the interface keeps switching cheap.
- **Expected resources** (estimate, ~750 GB / 100k photos and videos): ~150–400 MB RAM for nightly backups, up to ~1 GB for prune/check. Mitigations: `GOGC=20`, infrequent pruning, a systemd memory limit on backup jobs, quiet-hours scheduling.

**Backup process:**
1. **Prepare:** per-package hooks create a consistent state (e.g. `pg_dump` to `<service>/db-dump/`, SQLite's backup command, or a brief stop if there's no safe live method).
2. **Snapshot:** `/var/lib/roostack` plus each service's folder. Since 2026-10-04, one snapshot per service (tagged `service=<name>`, with its secrets) and one for the server's own state (tagged `server`): see §10.10, "Restoring across the lab".
3. **Verify:** periodic `restic check` and occasional test restores.
4. **Restore — Locked (2026-09-27):** per service, by the Owner, from the Backups page: choose one of the backups that contain the service (newest first), confirm, and it runs as an uninterruptible coordinator job with a live log. The service stops, its current data is moved aside (`<dir>.before-restore-<time>`), the backup's files and database dump come back, and it starts again. If getting the files back fails, the current data is put back (a partial restore is kept as `<dir>.failed-restore-<time>`) and the service starts again; if the data can't be put back, the service stays stopped and the log says where the data is, rather than claiming it's back (2026-09-29: a failed put-back used to go unnoticed and the service stayed stopped either way). Kept copies are listed on the restore page and deleted only when the Owner chooses. Restoring a whole lab onto a new server comes with the installer.

**Restore:** per service, or the full lab onto a new server (install Roostack → point at the backup → enter the recovery key).

**Full-lab restore — as built (2026-09-28):** on a fresh install, the first-run page offers "Restore a lab from its backups" next to creating the Owner (both need the setup code). The Owner says where the backups are (an S3-compatible bucket, a disk mounted on the server, or any restic address) and enters the recovery key; Roostack looks for every server's repository there (`roostack/<lab>/<server>`, a few levels deep for a disk), opens each with the key and shows the lab, server and latest backup of those it opens. Only the controller's (or a single server's) backup can be restored: its files go back where they were (Roostack's state, Podman secrets, every service's data, owners included), the recovery key becomes the backup key, and Roostack restarts. At that start the backed-up copy of Roostack's database becomes the live one (same accounts, settings and server identity); once the first apply has set the services up again, each service with a database is stopped, loaded from its dump and started, while "needs attention" says so. Backups carry the servers' WireGuard keys (`wireguard-keys.json`, kept by Roostack like the CA key), and the agent reuses a saved key for an interface that has none, so a restored controller keeps the keys its nodes and friends' labs know; they reconnect if they can reach it the way they reached the old one. Backups then continue at the lab's configured destination. The recovery key typed on the restore pages is kept in `<state>/restore-key` while a restore is prepared; it's deleted when the restore finishes or the first Owner is created (an abandoned restore), and never backed up (2026-10-16). If a service's databases can't be loaded after its files are back (restoring one service), it stays stopped and says so, rather than starting half-restored. **A restore that fails part-way can be started again (2026-10-16):** a server counted as "not fresh" once it had instance files, which the server's own snapshot puts back first, so after a later failure the page said the server already ran services (review M25). Now `<state>/restore-started` marks a restore under way (removed when it finishes, or when the first Owner is created instead; never backed up); while it's there the server counts as fresh, and the restore page says the last restore didn't finish and offers starting again, which puts everything back again over what it restored. **What a restore trusts (2026-10-17, review M26):** a backup says which server made it and whether that's the controller (from the files in it), and every server holds the recovery key and may write its own folder, so a node could make a backup that says it's the controller: it was offered beside the real one, and restored any paths it listed. Now each backup found says whose folder it's in (each server's is named after its ID: `roostack/<lab>/<server>` on a disk or online storage, `labs/<lab>/<server>` in Roostack Cloud, `<server>/<lab>` on a lab's own backup store, where the first is the server allowed to write it); a controller's backup is offered only from that server's own folder, and otherwise shown as not offered, saying why (backups moved by hand go back in a folder named after the server); and a restore puts back only Roostack's state folder, the Podman secrets store and each service's own folders (`<services_dir>/<name>` and `<media_dir>/<name>`, as this server's lab.yaml sets them), refusing a backup that lists anything else before putting anything back. Still possible: a node's backup claiming to be the controller of a lab of its own (its own ID, in its own folder), shown with its server's name and folder for the person to tell apart. Considered: offering a controller only when there's one (a forged one would then hide the real one). Considered: restoring into a staging folder and renaming at the end (cleaner, but Roostack's state, the secrets store and each service's folders are on different paths, so there's no single rename). Not yet: restoring from storage at a friend's lab (its link is in the lost state), and restoring a node on its own (restore the controller, then move the node's services).

**Defaults & policy:**
- Nightly; keep 7 daily, 4 weekly and 6 monthly.
  - **Two copies of one lab — as built (2026-10-04):** a full-lab restore makes the new machine the same lab (IDs, keys, domain), so if the old one comes back (it was only offline), both would back up into the same repositories and update the same DNS records. Fencing: the lab has a generation (`lab-generation` in the state folder, backed up with it), which a full-lab restore raises; every snapshot is tagged `gen=<n>`; before uploading, a server lists its repository (if it can't, the backup fails and is tried again, rather than going ahead unchecked: since 2026-10-16), and a snapshot of a newer generation means this copy is out of date: it stands down (no backups anywhere, no DNS updates; a problem on Home and its Backups page, which explain). Its services aren't stopped: a false alarm mustn't take anything down. "This is the right copy → Keep this copy" (Owner) raises its generation past the other's, so the other stands down at its next backup (a test restore that fenced the real lab). The same mark serves a server the controller removed while it couldn't be reached (a gone server, once nothing waits on it): the controller adds a `fence=removed` snapshot to its repositories, and if it comes back it stands down and its own page says it was removed. Considered: a new ID for restored services (the clash is the lab's and its servers' identity, not a service's; and it would cut their backup history); stopping the old copy's services (a false alarm would take the lab down). Not covered: an old copy that can't reach its backups at all (it then can't harm them either; DNS is the remaining risk).
  - **When "nightly" isn't simple — as built (2026-10-04):** the time is the server's local 02:00. On the night clocks go forward it runs at 03:00 (02:00 doesn't exist), and on the night they go back at the second 02:00: once either way (checked with Australia/Sydney). The schedule looks at the clock every minute rather than waiting once, as Go's timers don't count time asleep: after a suspend (or a paused VM) the backup runs as the machine wakes, not hours late. A night the server was off is caught up: 10 minutes after Roostack starts, then hourly, a backup runs if none was tried for 26 hours (an attempt counts: failures have their own retries). The controller's weekly clean-up tries a repository that's locked (its server still backing up, e.g. a big first backup) again an hour later, up to three times. Considered and left: starting each server's backup a few minutes apart (they share a destination only sometimes), and waiting for the clock to sync at boot (a machine without a clock battery; not a NUC).
- Packages classify data as **critical** (backed up by default: photos, passwords, repos) or **replaceable** (not backed up by default: media libraries, caches).
- **Destinations:** local disk, remote (S3/B2/SFTP), and Roostack Cloud (below). **Local-only is allowed, with a persistent warning** recommending off-site.
  - **Roostack Cloud backup — as built (2026-10-13):** for a lab linked to Roostack Cloud, the chooser offers "Roostack Cloud: off-site, set up for you", with the lab's use of its space ("This lab uses 1.2 GB of 50 GB"). It is online storage in Australia that Cloud runs; each server gets its own folder there, and backups are encrypted with the recovery key before they leave, so Cloud can store them but not read them. Nothing to configure: no account, keys or address to type. How it works:
    - **Short-lived keys.** No server keeps a storage password. Before each backup a server asks for keys that last 12 hours and open only its own folder, and only to add backups (they can't delete). The controller asks Cloud over its link (§4); any other server asks the controller over the lab API (`POST /v1/storage-keys`, mutual TLS), so nodes never talk to Cloud themselves. Keys are kept 0600 in the state folder (`cloud-backup-keys.json`), renewed when under an hour is left, and used while more than 5 minutes are left if Cloud can't be reached meanwhile. They're left out of the lab's own backups (they expire, so a copy is no use).
    - **The lab prunes, Cloud never holds a restic key.** Like every destination, the controller prunes each server's repository weekly with the recovery key. For that it asks Cloud for the lab's prune keys (`cloud-prune-keys.json`), which may delete within the lab's folders only. Cloud keeps deleted and overwritten files for 90 days, so neither a compromised server nor a stolen prune key can destroy backups at once.
    - Considered: one long-lived storage key per server (a key leaked from a backup or a stolen disk would work until someone noticed), and Cloud pruning for the lab (Cloud would need a key that opens the backups, which breaks "Cloud can't read it"). restic exits 0 when a delete is refused, so tests check the snapshots, not the exit code.
    - Not yet: a second, archived copy kept by Cloud (see TASKS).
  - **Restoring from Roostack Cloud — as built (2026-10-13), the user agreed the design the same day:** after losing the controller (a fire, a dead disk), a fresh install's "Restore a lab" page offers "Roostack Cloud", which needs only the recovery key: no account login, address or keys. It rests on the lab's **recovery identity**, an Ed25519 key derived from the recovery key (HKDF-SHA256; the key is 256 random bits, so no slow password hashing is needed). The controller registers the public half with Cloud when it links, at each daily check-in if it changed, and as soon as a new recovery key replaces the old (the old key then stops working with Cloud too). **Since 2026-10-17 (review M10) the registration proves the key:** it carries a signature over the lab's ID with its own purpose ("register", beside "access" and "relink" below), and Cloud refuses one without it, so a lab that learned another's public key can't register it and have that lab's restores find its own backups instead. Signing the lab's ID rather than a challenge from Cloud saves a round trip and ties the signature to the one lab already; nothing was released, so there's no period that still accepts unsigned ones. To restore, Roostack asks Cloud for a challenge, signs it, and gets keys that read the lab's folders (12 hours, as a big restore takes hours; they may write only restic's locks) and the list of its servers' repositories; the usual search and restore follow. **Every lab with the key (2026-10-17, review M10):** a lab unlinked from Cloud and linked again is a new lab there with the same recovery key, and Cloud keeps the old one's backups for a while. Cloud gave only one lab (the linked one), so the older backups couldn't be reached; now it gives each lab with the key, the linked one first, then the latest unlinked, each with its own keys and repositories. The restore page shows each lab, with its name and when it was linked or unlinked, and its backups under it, and the person chooses. A lab restored from an unlinked lab's backups links again from its Settings (Cloud refuses its old link). Considered: Cloud choosing the newest lab's backups (the person restoring knows which moment they want; the newest may be a test install). The recovery key never leaves the server. Anyone with the recovery key can already decrypt every backup, so reading them gives nothing more away; Cloud still emails the account each time, with where from and what to do if it wasn't them (change the recovery key).
    - **Relinking:** the restored controller's backup holds its Cloud certificate, which usually still works (certificates last 90 days and renewing doesn't cancel the old one). When Cloud refuses it (expired while the lab was off, or a restore from an old backup), the daily check signs a challenge to get a new certificate instead of forgetting the link, at once rather than after a waiting period (the user's choice: someone restoring after a fire needs their address back now; the email lets the real owner react). It must be the same lab, and Cloud refuses it for a lab that was unlinked on purpose: that one links again as usual. Its backups can still be read while Cloud keeps them.
    - Signatures are for one purpose ("access", "relink" or "register" is part of what's signed), each challenge works once for 5 minutes, and proving is rate-limited in Cloud, per address and per lab (2026-10-13). A relink refused because Cloud is busy (rate limited, or failing) keeps the link and tries again at the next check; only a refusal forgets it.
    - Considered: logging into the Cloud account to restore (it needs no new cryptography, but the person restoring often isn't the account's owner, and account recovery may be the very thing lost; it may come later as a second way); Cloud holding a copy of the recovery key (it could then read the backups, which breaks "Cloud can't read it").
- **3-2-1 backups — Locked (requirement), Open (design), 2026-09-26:** Roostack should guide users towards 3-2-1 (3 copies of the data, on 2 different kinds of storage, 1 off-site), not just warn. That means:
  - **Suggestions in the UI** explaining what's missing and why, e.g. "Your backups are only on this server" → suggest a USB disk, then an off-site destination.
  - **Multiple backup destinations**, e.g. a local disk *and* an off-site repository. **As built (2026-09-28):** each server has a main destination (backup 1) and any number of **extra copies** elsewhere (backups 2, 3, …, in the plan below). The controller creates each copy's repository like the main one (recovery key plus a key of the server's own). Each copy is **its own backup** of the same files, made right after the main one (the database dumps are already fresh), rather than `restic copy`: restic reads both repositories' credentials from the same environment variables, so two S3 accounts or two backup stores couldn't be told apart, and separate backups keep each copy readable on its own. restic's file cache keeps the second run cheap. Copies still run when the main destination fails. Opening each repository is limited to 2 minutes (2026-10-03): restic keeps retrying storage it can't reach, such as another server that's switched off, which held up the whole run. **Destinations run one after another — Locked (2026-10-03):** one set of database dumps for all of them, and at the same time they'd compete for the same disk reads and (at home) upload bandwidth, so it wouldn't be quicker; one failing doesn't stop the rest, and a main destination whose drive isn't plugged in is skipped while the copies go ahead. **Trying again — Locked (2026-10-03):** only the destinations that failed are tried again, after 1 hour and then 3 hours, then they wait for the nightly backup (each retry makes fresh database dumps); failures that need someone (a wrong key, a full destination, no permission) aren't retried, and a destination whose drive isn't plugged in is backed up as soon as it is (checked every minute). The card says when ("Roostack tries again today 14:00."), and "needs attention" waits until the retries are over (at once for a missing drive, which needs someone). The plan is kept in memory: after a restart the nightly backup tries everything anyway. Considered: retrying the whole run (repeats what worked), and retrying everything indefinitely (hides failures that need someone). Each copy's result is recorded and shown; a failed or stale copy needs attention. Copies are pruned and checked with the main repository. Stopping a copy leaves the copies made so far.

Where a server's backups already go isn't offered again; this server's own disk counts once. A backup that fails to set up is forgotten again (the one before it is put back), and the failure stays shown on the plan for an hour. Under the plan, the **checks**: 3 copies (the data and at least two backups), 2 kinds of storage (the data is on a disk, so at least one backup that isn't a disk: disks count as one kind, whether this server's, plugged into it, a folder, or another server's), 1 away from home (online storage, a friend's lab, or another server that's somewhere else), and backed up lately. **Where each server is — Locked (2026-09-28):** Roostack can't tell whether a server is at home or somewhere else (a VPS, a relative's house), so the Owner says, once per server: asked on the plan's card when a backup goes to another server ("Where is vps? ### 6.10 Host Security — Locked

Layered defaults:

1. **Firewall:** default-deny inbound. Allow 80/443 plus ports that specific services need (e.g. WireGuard, Pi-hole DNS on the LAN). `roostack-agent` generates a readable **nftables** ruleset file and reloads it (nftables is Debian 13's default, so no extra dependency).
   - **SSH access — Locked (2026-09-27):** the Owner chooses in the setup wizard (step 2) and in Settings: home network only (recommended, default), anywhere, or nobody. The page lists current SSH connections (read from `/proc/net/tcp`) and a choice that would cut one off must be confirmed. Stored in `lab.yaml` (`firewall.ssh`).
   - Roostack applies the firewall after every apply, so enabled package ports are opened (home network only unless public). Until the SSH question is answered, Roostack leaves the firewall alone.
   - **Who counts as home — as built (2026-10-16, after the security review's H3, H4 and M23; the lab's servers taken out 2026-10-17):** "home network" (SSH "home only", private package ports, Caddy's private routes and the UI) is the private ranges (RFC 1918, ULA, link-local, loopback) and the CGNAT range 100.64.0.0/10 (Tailscale, people's devices on Roostack's network later), **except other labs' links (100.100.0.0/14), Roostack Cloud's relay (100.81.0.0/16) and the lab's own servers (100.96.0.0/17, §10.2)**, which are never home. A Tailscale device whose address falls in one of those ranges isn't home either (Tailscale picks addresses across 100.64.0.0/10, so roughly one device in twelve: mostly the other labs' /14, since 2026-10-16); Tailscale's admin console can change a device's address. The firewall's set and Caddy's list are both made from `trust.HomeRanges` (below). Interfaces are settled before any rule by source: from `roostack-relay` only Caddy's edge listener; from `roostack` (the lab's servers) only what's opened for servers (§10.2); from `roostack-guests` only the guest API and each guest lab's own store, from its own address; `roostack-st*` (this lab's links to other labs' storage) take nothing in; nothing is forwarded to or from any of them. Before this, a friend's lab reached SSH, home-only ports, the UI and private routes, since its addresses were inside the CGNAT block. Kept: the CGNAT range as home for Tailscale users (the Owner's choice, 2026-10-16); considered dropping it (safer where an ISP lets CGNAT subscribers reach each other, but it would cut off Tailscale).
   - **One place for trust classes — as built (2026-10-17, review §6):** H3, H4 and M23 had one root cause: who counts as what was a set of address ranges written out in four places (the agent's ruleset, `internal/firewall.Desired`, `node.Local`'s inline rules and Caddy's list). Now `internal/trust` defines the classes (anyone, home, the lab's servers, a server still joining, an edge, other labs, the relay, this lab's links to other labs' storage), how each is recognised (an interface first, then an address: WireGuard guarantees which peer an address on its interface is) and what each may reach. Every firewall rule names the class it's for (`Rule.For`: anyone, home, servers or guests; the agent renders each by its interface and addresses), `firewall.Desired` builds them all (the server's roles, such as a backup store or storage for other labs, come from `node.Local` as `firewall.Roles`), and Caddy's private list is made from the same home ranges. Tests keep them equal: one runs a source of every class through a small evaluator of the generated nftables rules and compares each port's verdict with `trust.May`; another checks every edge of every range against Caddy's list. *Considered:* the agent owning it (it knows its interfaces, as the review suggested), but Caddy's generator would then import the agent's server code; a small package beside it is read by both.
2. **Admin UI is LAN/VPN-only by default.** Public access requires explicit opt-in **and** mandatory 2FA. Rationale: the UI controls the whole host and is the highest-value target.
3. **SSH hardening — Locked, as built (2026-10-17):** key-only authentication, no password login, no root login. The user can opt out, but **the UI shows a persistent warning** while SSH takes passwords. Found promised but missing in the security review of 2026-10-16 (M19); built the next day, with the Owner choosing each point below from a mock-up (2026-10-17).
   - **Where it's asked:** with who can log in (item 1), in setup step 2 and in **Settings → Remote access**, for each server: "How do they log in?", **With an SSH key only** (recommended) or **With a key or a password**. Stored in `lab.yaml` (`firewall.ssh_login`: `key` or `password`). Not asked on a server with no SSH server (openssh-server not installed). It's the wizard, not the installer, that asks (this item first said the installer): apt runs the installer without anyone to answer, and it can't check a key.
   - **What keys only is:** one drop-in, `/etc/ssh/sshd_config.d/10-roostack.conf`, with `PasswordAuthentication no`, `KbdInteractiveAuthentication no` and `PermitRootLogin no`, written or removed by `roostack-agent` (`PUT /v1/ssh`, which takes only on or off; the content is the agent's own). Debian's `sshd_config` includes that folder at its top and sshd keeps the first value it reads, so `10-` wins over cloud images' `50-cloud-init.conf`. The agent checks every change with `sshd -t`; if sshd refuses it (another file is broken), the old file is put back and SSH isn't reloaded, so it keeps running as it was; otherwise `systemctl try-reload-or-restart ssh.service`. Logged-in sessions stay. Roostack doesn't write it again at start: removed by hand, the page says it's missing and the warning shows.
   - **No root at all (the Owner's choice):** `PermitRootLogin no`, not `prohibit-password` (Debian's default, root by key): a stolen key alone then doesn't give root where sudo asks a password. A cloud server that only has root (Hetzner, DigitalOcean) needs an account made first; the help shows the commands. *Considered:* root by key only (no extra account on cloud servers, but less than promised).
   - **How Roostack knows a key works (the Owner's choice):** keys only needs sshd's log to show a key login (`Accepted publickey`) by an account that still exists, isn't root, and is in the `sudo` group: proof that someone holds a working key and can still get root. Only journal lines from root running sshd's own program count (`_UID=0`, `_EXE=/usr/lib/openssh/sshd-session` or `/usr/sbin/sshd`), which journald fills in itself: any user can log a line that says it's sshd's (`logger -t sshd-session`). Until one is seen, the page says so, links to "Set up an SSH key" in the help and offers **check again**. *Considered:* an `authorized_keys` entry for a sudo account (doesn't prove anyone holds the private key or that sshd accepts the file's permissions, and the agent would need to read `/home`), a test connection (Roostack has no private key to test with), and the Owner ticking "my key works" (how people lock themselves out).
   - **"Nobody" (the Owner's choice):** keys only straight away, without the check: nothing reaches SSH, so nobody can be locked out, and a firewall mistake or opening SSH later finds passwords off. No warning. *Considered:* leaving sshd alone until SSH is opened.
   - **The default (the Owner's choice):** keys only when a key login has been seen (or it's already on); otherwise **With a key or a password**, and the wizard carries on, with the warning lasting until a key is set up. *Considered:* not letting the wizard go on with SSH open until a key works (safest, but it stops people who never use SSH unless they choose "Nobody").
   - **The lasting warning:** on the home page's Needs attention, for each server whose SSH takes passwords and can be reached: "SSH on this server still accepts passwords: anyone on your home network can try to guess one." (a warning), or "… accepts passwords from anywhere, so anyone who can reach it can try to guess one." (a problem), with **Turn passwords off**. Settings sums it up ("SSH from your home network only, passwords allowed"). It's worked out from what sshd really does (`sshd -T`, read through the agent and kept 30 seconds for pages that poll; the remote access page reads it fresh), so a file of the Owner's turning passwords back on is caught too, and a cloud image that already turned them off shows none.
   - **`Match` blocks — as built (2026-10-17):** a `Match` block overrides the global settings for the connections it matches, Roostack's file included (a drop-in can't hold a `Match` of its own: Debian includes the folder at the top of `sshd_config`, so everything after it would become part of the block). So the agent reads the `Match` lines of `sshd_config` and the files it includes and, when there are any, asks `sshd -T -C user=…,host=…,addr=…` about connections from an address in each home range, the lab's servers' range and the internet, and from each address and user the blocks name (a range's first address, a pattern's wildcards as 1, a group's members), to port 22 or a local address or port a block names, up to 256. Passwords for a home address (or a server's) count as "takes passwords"; for addresses outside home only, they matter once SSH is open to anyone. The page names the block ("SSH still takes passwords from some addresses: “Match Address 192.168.7.0/24” in its settings turns them back on…") when keys only is on, and the lasting warning counts it. *Not covered:* `Match Host` (it needs reverse DNS) and `RDomain`, and wildcard user names other than the one Roostack makes up. Checked on VM4 (docs/ASSUMPTIONS.md J5).
   - **Socket-activated SSH — checked (2026-10-17):** Debian 13's `ssh.socket` (`Accept=no`) starts the normal `ssh.service` on the first connection, so sshd reads its files when it starts, not per connection. Two things broke and were fixed: an sshd started by the socket can't reload (on SIGHUP it starts itself again and can't bind port 22, which systemd holds; the service fails and the agent reported an error, though the next connection then started it with the new files), so with `ssh.socket` active the agent restarts `ssh.service` instead (logged-in sessions stay); and while it waits for its first connection, `/run/sshd` (the service's `RuntimeDirectory`) is gone, so `sshd -t` and `sshd -T` fail, so the agent checks with `sshd -G` then (it reads the same files and refuses a broken one, without host keys or that folder) and reads the global settings with it, saying it couldn't check `Match` blocks (`sshd -G` takes no `-C`). docs/ASSUMPTIONS.md J4.
4. **Intrusion protection: CrowdSec**, enabled automatically once any service is public. It uses a Caddy module ("bouncer") to block at the proxy, and scenarios for Caddy and SSH logs. Not run on fully private labs (little benefit, saves resources).
   - **fail2ban is not run alongside it.** CrowdSec covers the same local log-parsing and banning, and running both would mean duplicate bans, two configs, and two tools changing the firewall.
   - **Signal sharing: on by default, opt-out.** Opting out is a **prominent choice when something first goes public** (changed 2026-09-30 from "during install", since CrowdSec only runs from then on; §6.11), and can be changed later in Settings. Only attack data is shared (attacker IPs, attack types, timestamps), nothing about the user's own users or data.
   - **If the user opts out:** local detection and banning keep working fully, like fail2ban but with better parsers and blocking at the proxy. They lose the community blocklist, i.e. pre-emptive blocking of IPs already seen attacking others. Rule and parser updates from the CrowdSec Hub are separate and still work.
   - **Web application firewall (WAF) — Locked (2026-10-06), not built yet:** adopted, not built from scratch. A WAF reads requests (paths, headers, bodies), so it runs where TLS ends: in the lab's own Caddy, in front of each public service. That protects every public lab, whether its traffic comes through port forwarding, its own VPS or an edge (an edge never decrypts, §10.5).
     - **First: CrowdSec's AppSec component, on by default for public services.** Its "virtual patching" rules block exploits of known vulnerabilities in popular apps (often before people update), with few false positives since they target specific exploits. It uses what's already running (CrowdSec and its Caddy bouncer, item 4); *to verify:* that the bouncer version we pin passes requests to AppSec.
     - **Later: generic rules (the OWASP Core Rule Set), per service:** broad protection (SQL injection, cross-site scripting and so on) but notorious false positives on modern apps (large uploads, JSON APIs, sync clients). Run in "detect only" first, and each catalog package ships the exclusions it needs (e.g. no body inspection on its upload path), tested with the package. That per-package knowledge (logins, uploads, exclusions) is Roostack's contribution, alongside the login paths it already rate-limits.
     - **Considered:** Coraza (the OWASP engine, with a Caddy module) running the Core Rule Set directly: a possible engine for the later step, but a new Caddy plugin (a dependency to agree). ModSecurity, BunkerWeb, open-appsec and SafeLine are built around other proxies (nginx, Apache, their own), a poor fit for Caddy.
5. **Baseline:** automatic security updates (§3.2), Caddy rate limiting on login pages, secrets in files readable only by Roostack (0600), and container images only from trusted registries, pinned to specific versions.
6. **Wrong two-factor codes — as built (2026-09-29):** limited per account, not per login, since someone with the password could otherwise log in again for more tries. Every fifth wrong code in a row locks the account's codes (even the right one) for 15 minutes, doubling each time up to a day; the right code resets the count. That leaves a guesser about five tries a day, while someone mistyping waits 15 minutes. The count is in the database (a restart doesn't clear it), covers the login and the recovery key page (§6.9), and each lock is audited; the password step says so when locked, telling people that wrong codes they didn't enter mean their password is known. Checks run one at a time, so parallel guesses can't slip past. `roostack user reset-2fa` ends a lock. Considered: a limit per login (what we had; it limited nothing), locking the whole account (the lock is only on codes, so it can't be used against an account whose password the attacker doesn't have), and relying on Caddy's rate limiting alone (per address, so it doesn't stop guesses from many addresses).

### 6.11 Public access — Locked (2026-09-30), details Open

Nothing is public unless the Owner makes it so (§1 principle 6). The Owner makes one of a service's addresses public from the service's page, or, on a lab on the internet, when installing it (§6.12); the Roostack UI itself stays private (§6.10 item 2).
- **Who — Locked (2026-10-16):** only an Owner, everywhere: from the service's page, when installing, and the CrowdSec sharing question (a lab-wide setting). An Admin installing on a lab on the internet sees no public choice and no sharing question; the service starts private, and the form says an Owner can make it public from its page. Each install's audit entry records the service, the server it runs on, whether it went public, and any risks the Owner accepted for a package of their own (§8.3.4). Found by the security review of 2026-10-16 (M15): the install form let an Admin make a service public and answer the sharing question, which this section and §6.12 disagreed about. Considered: letting Admins choose at install (Admins manage services, but exposing one to the internet is a host-level risk, like the rest of public access).

- **Ways in ("entries"), all to be supported:**
  1. **Port forwarding at home:** the router forwards TCP 80 and 443 (and UDP 443) to the server; public records point at the home's public address. Built first: it needs nothing beyond the home router.
  2. **Through a cloud server in the lab** (an "edge", §10.5): no router change, and the home's address stays hidden.
  3. **Through Roostack Cloud** (later, §4): the same edge mechanism, run by Roostack Cloud, for people without a cloud server of their own or behind CGNAT.

  A service that runs on a cloud server is reached at that server directly. The entry is a seam in the code from the start (where public records point, and how traffic reaches the service's server), so 2 and 3 slot in without reworking 1.
- **Changing it — as built (2026-10-01):** making an address public asks for confirmation (a dialog, like other hard-to-undo actions); making it private again uses a red confirm button. While it's public, the package's private parts can be opened or closed again ("Parts kept private"); links into the app that lead to a private part say who can open them. "Home only" became "Private", explained for each kind of lab.
- **What can be public:** packages mark addresses that aren't safe to make public (admin pages, APIs meant for home), with the reason. The Owner can still make one public, after a warning that gives the package's reason and a tick to confirm; the override is audited. Considered: never allowing it (too rigid for technical Owners who know what they're doing); allowing anything with no mark (non-technical Owners can't judge an admin page's risk).
- **Protection first:** CrowdSec and Caddy's rate limiting (§6.10) run before anything goes public, and the switch waits for them. Dependencies agreed (2026-09-30): the CrowdSec container, and two Caddy plugins, `caddy-crowdsec-bouncer` and `caddy-ratelimit`.
- **Checking it works from outside:** for now, the Owner checks from a phone on mobile data (on a lab on the internet, from any browser, §6.12). Roostack Cloud will check automatically later. Considered: port-checking websites (they learn the home's address and domain); checks from the lab's own cloud servers (maybe later).
- **DNS:** each public address gets its own record pointing at the entry's public address, overriding the private wildcard (§6.5.1 stage 2).
- **The home's public address — Locked (2026-09-30):** found with a DNS query (OpenDNS's `myip.opendns.com`, Cloudflare's `whoami.cloudflare` as a fallback), checked every few minutes, and public records updated by Roostack's own record code (§6.5.1), with the same ownership tracking. This replaces ddns-updater (§6.5.1 stage 2): one less container, and one owner for every record. Considered: ddns-updater (more providers, but a second writer to the same zone); HTTP "what's my IP" services (they see every check).
- **CrowdSec signal sharing — Locked (2026-09-30):** asked in the "Protection" step the first time something goes public (CrowdSec only runs from then on), not during install (§6.10 item 4 updated), and changeable later in Settings.
- **CrowdSec and SSH — Deferred (2026-09-30):** CrowdSec reads Caddy's logs only for now. The rootless container can't read the host's journal, and SSH is home-network-only by default. To revisit: the agent passing SSH log lines on, or blocking with nftables (TASKS.md 1.18).
- **Rate limits — Locked (2026-09-30):** every public address gets a generous limit per visitor address, and the login pages a package names get a strict one.
- **As built (2026-09-30):**
  - Packages: `routes.<r>.public` with `unsafe` (a reason), `private_paths` (each with a reason) and `login_paths`; the Owner's opened paths are the instance's `public_paths`.
  - Caddy, for a public address, in one `route` block: private paths refused to outside visitors, CrowdSec's bouncer, 1000 requests per 10 s per visitor and 10 a minute on login paths, then the service. The only path that reaches Roostack is the check link (a 32-digit token).
  - While anything is public, the lab runs CrowdSec (pinned image) reading Caddy's JSON access log; the bouncer's key is a generated Podman secret. The sharing opt-out travels in the assignment.
  - The entry is `internal/public.Entry`; port forwarding finds the home's address over DNS. `dnsrecords` sets each public address's record once CrowdSec's health check answers, re-syncing every 5 minutes (30 s while waiting), and points it home again when the address goes private: the providers' record APIs can't delete yet.
  - UI: "Reachable from" on the service page; a page per address (warning, reasons, private paths, the sharing question, then the checklist: protection, DNS record, the router, the phone check); Settings → Public access. Owner only, audited.

### 6.12 Where the lab is: at home, or on the internet — Locked (2026-09-30)

- **Why:** Roostack assumed every lab sits behind a home router. On a cloud server (a VPS) that's wrong everywhere: "home network only" meant the provider's private network (shared with other customers) or nobody; the public checklist asked about a router and a phone on mobile data; DNS talked about home. Found running a lab on a Linode (2026-09-30).
- **The setting:** `network` in `lab.yaml`: `home` (the default) or `internet`. It's about the controller, whose Caddy serves the lab's addresses: a cloud server that joins a home lab needs nothing, since the controller at home serves its services. Asked in the wizard's first step ("Where is this server?", with the time zone), changeable in Settings → Where it is and DNS (Roostack restarts).
- **Detected, then confirmed:** a public IPv4 address on one of the server's own interfaces suggests "on the internet" (IPv6 isn't counted: home servers often have public IPv6 addresses behind the router). A cloud server behind its provider's NAT (some AWS or Oracle setups) looks like home, so the Owner confirms. While nothing is saved and the server looks like a cloud server, Home and Settings say so.
- **On the internet — Decided (2026-09-30) by the project's Owner:**
  - **Private means only through an SSH tunnel**, and the UI says so plainly: a private service's page says "Only through an SSH tunnel (for technical users)", linking to the help's steps (tunnel to the server's port 443, a hosts-file line, open the address). Caddy's private addresses become "this server only": loopback, the server's own address (a tunnel's requests, to the host's 127.0.0.1, reach Caddy's pasta network from it) and pasta's host-loopback address (docs/ASSUMPTIONS.md P9). The provider's private network isn't allowed.
  - **Services start public** when an Owner installs them (the install form's "Anyone on the internet can reach it", ticked, with the CrowdSec sharing question the first time), except addresses their package marks unsafe, which start private. An Admin's install starts private: only an Owner makes anything public (§6.11, 2026-10-16). Rejected: private by default (unusable without a tunnel); waiting for a Roostack VPN for the Owner's devices (a bigger feature, later).
  - **The UI is public** at `roost.<domain>` unless kept to a tunnel (§6.3.2). So CrowdSec can start before anything has asked about sharing attack reports: it shares nothing until the Owner answers (on the first install form or public-access page), on any lab.
  - **DNS:** the wildcard `*.<domain>` points at the lab's public address (from the entry, so a provider's NAT doesn't matter) and covers public services: no per-service records, and nothing waits for CrowdSec. Messages talk about "this server", not home.
  - **Public access checklist:** protection, DNS, **your provider's firewall** (naming Linode, Hetzner, AWS, DigitalOcean and Oracle Cloud; TCP 80 and 443, UDP 443) instead of the router, and **a check from any browser** instead of a phone on mobile data.
  - **SSH** defaults to "from anywhere" (recommended there); "only from private networks" says it would need the provider's console to get back in.
- **Both kinds of lab:** when the check link doesn't open, the page lists what to look at, in order: Roostack's firewall (always open for web traffic), the router or provider firewall (Roostack can't see it), public DNS (checked), and at home whether the connection takes incoming connections at all (CGNAT).
- **Checking from outside — Locked (2026-10-06), not built yet:** a lab linked to Roostack Cloud can ask Cloud to check it from the internet, as a visitor would: public services work (public DNS, port 443, a valid certificate for the name, the right app answering); **private services are *not* reachable** (a mistaken port forward or a router's UPnP would otherwise go unnoticed: flagged as a problem at once); risky ports open on the home's public address (a short list: SSH, databases, remote desktop, router and NAS admin); later from each region. Checks run on demand ("Check from outside now", offered right after a service's public setting changes); scheduled checks are a Cloud plan feature. Roostack's side: "Reachable from outside: checked today 09:14" on each public service, problems in the attention list and by email. Cloud only checks names the lab has proven it controls and the address the lab connects from. **Without Cloud,** the manual check (a phone on mobile data) stays.
- **Later:** a warning when home DNS answers a public address with something else (the "overridden" check applied to public names). Package ports ("extra connections") on a lab on the internet: "home network" there means the provider's network.

### 6.13 Email and notifications — Locked (2026-10-03)

**Sending — as built (2026-10-03):** Settings → Email (Owners) sets the SMTP server: host, port, STARTTLS (587, the default) or TLS (465), username, password, and the sender address (suggested: `no_reply@<domain>`, once the domain is set up). The settings are in `lab.yaml` (`mail:`); the password is in its own file (`mail-password`, 0600), never shown again ("leave empty to keep it", or "forget the saved password"). The password is only sent over an encrypted connection: a server that doesn't offer STARTTLS is refused with a sentence suggesting TLS. Messages are plain text (UTF-8, quoted-printable) and marked `Auto-Submitted: auto-generated`. "Send a test email" sends one, to your own address by default, and says which step failed if it didn't (reaching the server, the login, the sender, a recipient). Each person sets their own address on their account page; empty means no email. Only the controller sends (it knows the whole lab). The standard library's SMTP client is used (no new dependency); it's frozen but complete for this. Checked against Fastmail from VM1. Considered: a relay service's API (another account and dependency), and sendmail on the host (needs a local MTA, more to secure).

**Notifications — Locked (2026-10-03), as proposed; as built the same day (below the table).** Baseline: **email when something needs a person, or when something important happened while they weren't looking; never for routine success.** Most of it already exists as "needs attention" on the Home page, so the proposal is to email those items, once, with a few security events added.

*What, and to whom by default:*

| Group | Events | Owner | Admin | Member |
|---|---|---|---|---|
| **Problems** | A backup failed after its retries ran out, or none finished for two days; an extra backup failing; a disk running low or other labs' promised space reaching into what's kept free; a server unreachable for 15 minutes; a service down or restarting in a loop for 15 minutes; OS updates failing; a certificate that can't be renewed; DNS records in conflict; storage at a friend's lab removed, or its backups there deleted | on | on (services, backups, disks) | off |

| **Weekly summary** | Backups made, space used and trend, updates installed, attacks blocked on public services, anything still needing attention | off | off | off |

*How:*
- **One email per problem**, when it has lasted a few minutes (so a blip that fixes itself sends nothing; retried backups only once the retries are over), then **a daily reminder** while it lasts, and **"It's fixed"** when it clears. Several problems at once go in one email.
- Each email says what happened, what Roostack already tried, and what to do, with a link to the page (the "needs attention" sentence, plus detail). Plain text; no tracking.
- Security emails go straight away, without waiting or grouping.
- Members never get lab problems: they can't act on them.

*Configurability (proposed):* each person chooses, on their account page, which **groups** they get (Problems, Waiting for you, Security, Weekly summary), with the defaults above; Security about their own account can't be turned off. Per-event switches considered and not proposed: too many choices for the people Roostack is for; groups cover "too much email". Owners can see who gets what on Settings → Email. Later: other channels (ntfy or similar push) as another way to receive the same notifications.

*As built (2026-10-03):* a notifier on the controller runs every minute. Problems and things waiting come from "needs attention" as each person would see it on Home (so roles filter them the same way), problems and warnings only; an item is the same problem while its link and its words are, numbers and times aside ("3.0 GB free" and "2.9 GB free" are one). Problems are emailed after 10 minutes, things waiting after a day; reminders daily; "Fixed" once an emailed item clears. "Needs attention" gained "<service> has stopped working" (systemd gave up restarting it). Security events come from the audit log (so command-line resets count too): password changed, two-factor turned on, a password or two-factor reset (to the person, and to Owners), codes locked after wrong tries (newly audited, at login and when checking it's you), a login from a new browser (a long-lived device cookie, `devices` table; not for someone's first login), a new Owner or Admin, a role changed to one, a server joining, another lab starting to store here (both newly audited). The first run starts from the newest audit entry: history isn't emailed. One email per person per run, subject "[Lab name] Security: …" / "Needs attention: …" / "Still needs attention: …" / "Fixed: …", with links to `roost.<domain>`. The weekly summary goes on Monday from 8 am: each server's last backup and disks, and anything still needing attention. Groups are chosen on the account's Email and notifications page; Members see only the line that their own account's security emails always come. Nothing is sent until Settings → Email is set up; problems start being followed once it is. The account became area pages with a sidebar like Settings (Your account, Two-factor, Email and notifications, Appearance), tabs on phones. Settings → Email lists who gets what (each person's address and groups). The weekly summary also says what CrowdSec saw on the public addresses that week (`cscli alerts list --since 168h` in its container: attacks, from how many addresses, how many blocked, the commonest kinds), when CrowdSec is running.

*Changed (2026-10-08), after a day of alternating "Needs attention" and "Fixed" emails about a server that had gone* (a test VM reinstalled as a lab of its own, still listed in another lab): **"Fixed" waits as long as a new problem does** (an emailed item must stay gone 10 minutes; the controller's retries showed the server as "applying" for a moment, which had counted as fixed); **items can carry their own key**, so an error whose words change between attempts stays one problem (a failed change is keyed by its server); and **a server that can't be reached has its own item**, "Roostack can't reach <server>. It may be switched off, or its network down.", linking to its server, instead of "the last change didn't finish" with whichever network error the last attempt got.

### 6.14 History — Locked (2026-10-03), as built the same day

Nothing Roostack does should look like magic, afterwards too. **Settings → History** (Owners) lists, newest first:
- **What Roostack did** on each server: every finished log of work in the background (applying changes, backups, updates, restores, moves, backup set-ups), with its full output ("Log"), how long it took, and whether it failed. Each server keeps its own in its database (`events`), and the controller asks each one (lab API `/v1/history`). Runs that changed nothing (most applies at start-up) are "routine": shown as the latest on Settings → Servers, not kept.
- **What people did**: the audit log (logins, installs, settings, account changes), kept on the controller.
- A filter by kind, and "Older" for paging back.

**Applying changes says why** it ran: the controller sends a reason with each assignment ("Installing forgejo", "Changing who can reach vaultwarden", "Roostack started (after a restart or an update)"), and the server's log starts with it, then what it did, or "Nothing to change". Settings → Servers shows each server's latest apply under its Changes, live while it runs, and Home's "Applying changes…" links there.

**Limits:** history is kept for 30 days, 90 (the default) or a year, the Owner's choice; older history is deleted every day on every server (the controller asks each), and at once when the choice shortens. Each server keeps at most 5,000 events, and each event its log's last 2,000 lines (at most 256 kB). "Delete all history" deletes everything on every server; the deletion is then audited, so there's a trace. Considered: a size limit in megabytes (harder to explain than days and a count), and keeping everything forever (the database grows without bound on a small server).

### 7.1 Updating a service — Locked (2026-10-14), as built (2026-10-14)

Proposed to the Owner with a mock-up and agreed on 2026-10-14 (the Owner: "agree"; the one change is the stopped-service rule below).

- **What can be updated to:** the version the registry offers (`Package.Offer`, the one the fetcher keeps, §8.3.3), when it's newer than the installed one (`pkgspec.CompareVersions`). Only a service whose package is the registry's counts: the index has the package, and the installed version is either the index's own (same SHA-256) or no longer listed (`registry.Index.Updates`), so a package of your own that shares a name isn't updated from the registry. No downgrades (§8.3.5). Considered: offering every newer version (the fetcher keeps one; a fix on an older line would need it to keep more: filed).
- **Services from the Owner's own packages (§8.3.4) — Locked and built (2026-10-15)**, proposed to and agreed by the Owner: such a service (`local: true`) updates to the version of that package the Owner added last, when it's newer, and never from the registry; a registry service never updates from the Owner's packages (`Manager.updateSource`). Everything else is as for the registry's: the same kinds, policy, notice, backup, check and going back, and `local` is kept. **What a newer version asks for that the installed one didn't** (`Package.Risks`, new lines only) is listed in the notice; only the Owner can update then, ticking "I've read what it asks for, and want to update anyway", as when installing, and such an update never applies by itself. Admins see the list and "Only the Owner can update it". After the Owner adds a newer version, the catalog's confirmation lists the services running an older one, each linking to its update. Removing the package from the list means nothing newer to offer. Considered: updating the Owner's own only by hand (simpler, but ignores the update choice made on the service).
- **Kinds** (`pkgspec.UpdateKind`), from the upstream part of the versions (§8.3.5): the same upstream is a **revision** (a better definition of the same app); one to three numbers, optionally after a `v`, compare as major.minor.patch; anything else, or going backwards, is **other**.
- **The update policy** (`updates:` in the instance, `instance.AllowsUpdate`): `notify` never updates by itself; `patch` takes revisions and patch releases; `minor` adds minor releases; `all` takes everything, majors and "other" included. Chosen on the service page under Settings → Updates (Admins), with a sentence for each. New installs stay on `notify`.
- **Automatic updates wait for a person** when the update has upgrade notes, when that version already failed on this lab, when the server's backups aren't set up through Roostack, or when the new version needs a setting the service never had (a new required setting without a default; Roostack can't ask yet, so it can't update at all and says so). Considered: applying updates with notes automatically (the notes would then only be read afterwards, which defeats them).
- **When:** each night after the server's backup (§3.2's order: backup, then automatic service updates, then a restart if one is needed): the controller waits, per server, for the nightly backup that started after 02:00 to finish well (up to 12 hours), then queues that server's automatic updates without a second backup. A failed backup means no automatic updates that night.
- **A service Roostack stopped** because the registry withdrew its version as dangerous (§8.3.4) updates **straight away**, with a backup first, when the offered fix fits its policy (the Owner, 2026-10-14: "yes, but not on notify"): it's down anyway, so it doesn't wait for the night. On `notify` the withdrawal's notice offers the update instead. Checked after every registry check (`Manager.UpdateStopped`, from `RegistryChanged`).
- **Where "Update" appears:** the service page's notice (the versions, the kind in words, the notes, what Roostack does, and why it does or doesn't update by itself, with "Change this"); inside the withdrawal's notice when the version is withdrawn, replacing "wait for a fixed version"; under "Needs attention", one information line for all services with an update waiting for a person (not repeated for a withdrawn one) and a problem, emailed, for an update that didn't work; an "Update available" badge on the Services list (Admins); and "<version> is available" next to "Installed" in the catalog, linking to the service page. Admins update; Members see nothing to act on. A confirmation asks first when there are notes to read or no backup to go back to.
- **Showing versions:** the app's own version ("1.36.1"); when only the package's revision changes, "1.34.3, package revision 2", so the two never read the same.
- **Upgrade notes** (§8.3.5): every note newer than the installed version up to the target, oldest first, in the notice and before the confirmation (`Package.NotesSince`).
- **How an update runs** (`manager/update.go`, `node/update.go`), one at a time in the lab, as an activity ("service-update") with steps on the service page:
  1. The service's server downloads the new version's images while the old one keeps running (`reconcile.Pull`), so a failed download changes nothing and the switch doesn't wait for it.
  2. It backs up (a manual update: a fresh backup of the server, only what changed is uploaded; an automatic one follows the nightly backup) and then **holds its maintenance queue** with a job named "Updating <service>", so no backup, restore, OS update or restart starts until the update is done. The hold ends when the controller says so, or by itself after 10 minutes without word from the controller.
  3. The controller keeps the new package file (`state.KeepPackage`), saves the instance with the new version (dropping routes, ports and settings the new package no longer has, and `started_anyway`, which only covers the version it names) and applies. The previous package file is kept until the update is over.
  4. **The check:** every unit active, every container check passing, and no restarts, for a minute, within five minutes. Container checks are `health.cmd` (run in the container) and `health.http` through the route's published port when a route leads to it (an answer below 500 works); this is the first use of HTTP checks (ASSUMPTIONS F1). It gives up early when systemd restarts a unit five times or gives up on it (failed) for 30 seconds.
  5. **If the check fails, Roostack goes back** to the previous package and image (Podman keeps the old image; nothing prunes images) and checks that version the same way. **Data isn't rolled back**: the app may already have changed it, so the notice links to restoring the backup from step 2 (Owners). A version Roostack stopped as dangerous stays stopped after going back.
- **What's recorded:** the last update of each service in the controller's settings (`service-update:<name>`: from, to, when, result, error, automatic, who, when the backup finished, which server): the "Updated … (by itself)" notice for a week, the failure notice and its "Needs attention" problem (while that version is still offered, or for a week once nothing newer is; a newer offer replaces it), not retrying a failed version automatically, and the restore link. The full log is in the history (§6.14).
- **Considered:** the update as one job on the service's server (the controller owns desired state, so the server can't switch versions by itself); a backup of only the updated service (backups are per server, with a snapshot per service, and an incremental one is quick); restoring the backup automatically after a failed update (it would undo anything written meanwhile, and most failures are the app not starting, which going back to the old image fixes); updating every service in parallel (two updates on one server would fight over its queue).
- **"What's new" (as built, 2026-10-18; asked for by the Owner on 2026-10-14):** a package may say where its project describes each version, `about.releases`: an https address with `{version}` where the app's version goes (`https://github.com/x/y/releases/tag/v{version}`), or one page for every version. The update notice links to **What's new in** *version* (the app's version, not for a revision, whose app is the same). In the package rather than the index, since the index carries each package's file anyway and the address is the project's, like `source`. A package using it needs a Roostack that knows the field (package files are parsed strictly), which its `requires.roostack` says. *Considered:* a link per version in the index (the registry's maintainers would have to keep it for every version); upgrade notes (§8.3.5), which stay for what must be read before updating.
- **Not built yet:** `upgrade` hooks and migration steps (§8.1 Future); asking for a setting a new version needs.

### 7.2 Roostack's own updates — Locked (2026-10-18), as built (2026-10-18)

The brief (TASKS 1.12, "apt repository and signing"): patch releases install themselves, a new minor release only notifies and the Owner accepts it (§3.2's table). Built in one round with the release pipeline (`release.yml`, which builds and signs the files) and the installer; the shared names are placeholders until the Owner confirms them.

- **Release series.** A release series is a version's major.minor (0.4.0, 0.4.1 and 0.4.2 are the 0.4 series). Patch releases only fix things; a new series can change how things work.
- **The repository.** `apt.roostack.cloud`, one apt suite per series (`dists/0.4`, `dists/0.5`), component `main`, amd64 and arm64, packages in `pool/main/r/roostack/`. Release files say `Origin: Roostack` and `Label: Roostack`. Only plain release versions go in (major.minor.patch): a pre-release in its series' suite would install itself everywhere, so betas would need a suite of their own (filed). The release files themselves (binaries, .debs, `SHA256SUMS` and its signature) are at `dl.roostack.cloud/releases/<version>/`. Both names are one Cloudflare R2 bucket (roostack-cloud's `ops/tofu/releases`), since GitHub's releases can't serve a private repository's files; each name serves the whole bucket, which is harmless.
- **Built by `scripts/build-apt-repo.sh` with apt-ftparchive** (apt-utils): part of apt itself, and what Debian's own archive tools build on. It writes the Packages files and the Release file; gpg signs it (`InRelease` and `Release.gpg`, SHA-512). *Considered:* reprepro (keeps its state in its own Berkeley DB, which would have to live in the bucket beside the repository), aptly (a larger Go tool with its own database), and a small Go program (reading a .deb needs xz, which Go's standard library lacks: a new dependency). In CI it runs in a Debian 13 image pinned by digest, with its packages from Debian's snapshot of the same day (`apt-get --snapshot`), so every run uses the same tools.
- **Rebuilt from what's published.** Each run downloads every suite's `dists/` (not the pool), checks each `InRelease` against the release key and each Packages file against it, then adds the new packages' stanzas to their suite's. So a run never drops an older version, and the bucket is the only state. A version already published can't be published again with different contents (the script refuses, and the bucket's lock refuses to overwrite or delete anything under `pool/` and `releases/`). After signing, the script checks the new `InRelease` against the committed public key, so a wrong signing key fails the run rather than the labs.
- **Caching.** Indexes are also published under `by-hash/` (`Acquire-By-Hash: yes`), so apt fetches indexes by their SHA-256 and never gets one that doesn't match the `InRelease` it has. The CDN caches `pool/`, `releases/` and `by-hash/` for a year (they never change) and doesn't cache the rest (`InRelease`, the plain indexes, the list of series): a new release reaches labs at once, and edge TTLs below two hours need a paid Cloudflare plan anyway.
- **No `Valid-Until`.** It would stop an old `InRelease` being replayed to hold back a fix, but the repository would then need re-signing every few days, through the release environment's required reviewer. HTTPS already makes a replay hard. *Considered and left:* a scheduled re-signing job.
- **Publishing** (`.github/workflows/apt-publish.yml`): a job `release.yml` calls (`workflow_call`) once the release's files are built. It checks `SHA256SUMS.asc` against the committed public key and every file against `SHA256SUMS` first, then uploads the release files (each only once; checksums last), then the repository in the order a client reads it backwards (packages, indexes, `Release`/`InRelease`, the series list), so a client mid-way still sees a complete older state. It runs in the GitHub `release` environment (a required reviewer), with the release key's signing subkey and an R2 token that can only read and write that bucket.
- **What each server has** (in the package): `/etc/apt/sources.list.d/roostack.sources` (deb822: `URIs: https://apt.roostack.cloud`, `Suites:` the package's own series, amd64 and arm64, `Signed-By:` the keyring) as a conffile, and `/usr/share/keyrings/roostack-archive-keyring.gpg`, the release key's public part (`packaging/keys/roostack-release.asc`, unarmoured by `build-deb.sh`). A development build's source says `Enabled: no`: its versions aren't the repository's. `52roostack-unattended-upgrades` adds the origin `origin=Roostack,label=Roostack`, so patch releases in the server's series install with each night's OS updates. Within a series the package's source doesn't change, so a source someone edited (a mirror) doesn't stop unattended-upgrades. Host checks (§3.2) don't count `roostack.sources` as software from outside Debian when it's signed by Roostack's keyring, whatever its address.
- **Updating itself during the OS updates job (found on VM1, 2026-10-17).** The package restarts both Roostack processes. The job's output used to reach the agent through a pipe (`systemd-run --pipe`), which broke when the agent restarted, and unattended-upgrade then failed (exit 120); anything it installed after Roostack could have been cut off. Now the job's unit writes to `/run/roostack-agent/os-updates.log` (kept across the agent's restarts, `RuntimeDirectoryPreserve=restart`), and the agent follows the file; the unit runs to the end whatever happens to the agent.
- **Recording that run (as built, 2026-10-18).** The unit's script writes its exit status to `/run/roostack-agent/os-updates.exit` when it ends, and the agent reports the latest run (`GET /v1/updates/last`: still running, the exit status and when, the log). When the agent stops sending a run's output (`agent.ErrUpdatesCut`), Roostack follows the run through that until it ends, then records it as usual, with "Roostack updated itself to <version> and restarted" when it did. Before each run Roostack keeps a mark in its settings (`os.updates.running`), cleared once the run is recorded; if Roostack itself restarted halfway (the package restarts it too), its next start finds the mark and does the same, as a maintenance job, so nothing else starts before the run is recorded. A run with no exit status (a restart of the server clears `/run`), or one older than the mark, is recorded as not finished. *Was:* the run was recorded as "updated itself" from the output so far, before the old process died, if it lived long enough.
- **A new release series.** `build-apt-repo.sh` also publishes `series`, a line per suite with its newest version. Each server's Roostack reads it from the address in its own source (so a mirror works), five minutes after starting and every six hours, and its **Updates** page then offers "Roostack 0.5.0 is available": a new series can change how things work, so it waits for the Owner. Once the Owner accepts it (Owners only), the server's next OS updates run (nightly after the backup, or **Check for updates now**) moves to it, if the server's last backup worked and finished within the last 26 hours (or the server isn't backed up through Roostack, which the offer says). Otherwise it waits and the page says why. Moving is done by the agent, in the updates' own unit: it changes the source's `Suites:` line (nothing else, so a mirror stays), runs `apt-get update` (which checks the new suite's signature; if that fails the source goes back as it was), then `apt-get install roostack` with `--force-confold` (unattended-upgrade would skip a package whose conffile changed), then the usual unattended-upgrade. The series is passed to the agent as a checked major.minor only. *Considered:* signing the series list and checking it in Roostack (Go's standard library has no OpenPGP, and apt checks the suite anyway: a forged list could only cause a failed move, put back); the source written by `postinst` instead of a conffile (a conffile keeps an admin's edits, and `--force-confold` deals with the one change a new series makes); one acceptance for the whole lab (each server has its own Updates page today; a lab-wide offer, and the order in which a controller and its nodes move, is filed).
- **Telling the Owner (as built, 2026-10-18):** besides the Updates page, a new series is an information line under "Needs attention" for Owners ("Roostack 0.5.0 is available. It starts a new series of releases, so it waits for you to say yes."; once accepted, when it installs, or why it's waiting), linking to the Updates page, and a line under its server in the weekly summary email (Owners only: only they can accept it). Information, not a problem: Roostack carries on working on the series it has, so it isn't emailed as needing attention.
- **"What's new" (as built, 2026-10-18):** the offer links to the series' section of the public help's What's new page (`https://help.roostack.cloud/whats-new/#roostack-0.5`, `help/docs/whats-new.md`), written before the series' first release (docs/RELEASING.md). The public help, not the one built into the server's Roostack, which can't know about a newer series. *Considered:* a third field in the `series` list with an address (the repository would then decide where notes live, but the script would have to be given one per series, and the help is where Roostack's own words are).
- **Not built yet (filed in TASKS):** one acceptance for every server in a lab; suites for pre-releases.

## 8. Service Definitions & Catalog — Locked (principle)

- The service definition format is user-facing from early on (custom services is a nice-to-have; the planned registry, §8.3, makes them its "local" tier).
- Breaking changes to the format are acceptable before 1.0.
- **Official packages are curated and opinionated.** Upstream `docker-compose.yml` files are a starting reference, not something we import directly. Each official package includes Roostack-specific configuration so it runs production-ready in the Roostack ecosystem:
  - automatic TLS / reverse proxy wiring
  - backup definitions (what data to back up, how to quiesce it)
  - use of Roostack-managed shared resources (e.g. common databases)
  - standard storage locations
- **Rationale:** Upstream compose files are rarely production-ready as a one-click install. Being opinionated is what makes one-click install and management reliable for less technical users.

### 8.1 Format — Locked (initial; may be revisited)

- **Two file kinds:**
  - **Package** (`<name>/<version>.yaml` in the registry, §8.3): authored by Roostack or the community. Describes how to run the app well: containers, settings, storage, databases, routes, health checks.
  - **Instance** (`/var/lib/roostack/services/<name>.yaml`): the user's choices (package version, subdomain, exposure, setting values, update policy). This is part of desired state.
- Roostack combines package + instance and **generates** Quadlets, Caddy site snippets, and backup jobs.
- **Our own YAML schema** (`schema: roostack/v1alpha1`) models what Roostack needs to understand, with a **raw Quadlet passthrough** for unusual needs.
  - Rejected: packages shipping Quadlet templates plus a manifest. Every package would do things differently, and Roostack couldn't reason about them as well.
- **Backups are declared, not scripted:** `databases` entries (`sqlite`, `postgres`, …) and `storage` classes (`critical` / `replaceable`) drive Roostack's standard backup methods.
- **Secrets** are declared (optionally `generate: true`) and delivered as Podman secrets, so they never appear in generated unit files.
- **Images are pinned** by tag + digest. Roostack's own images too (2026-09-29): rest-server by digest, and the Caddy image, built on each server, from base images pinned by digest and DNS plugins pinned by version (`build/caddy/Containerfile`). Digests are the multi-arch index, so the same pin works on ARM.
- **Templating:** Go templates (e.g. `{{ .Routes.web.Host }}`, `{{ .Settings.x }}`).
- **Versioning:** `<upstream version>-roostack.<package revision>`.
- **Additional schema features** (from the Immich stress test):
  - **`when:` conditions** on containers and devices, for optional components (e.g. Immich machine learning), so disabled features don't use RAM.
  - **`devices:`** as abstract requests (e.g. `gpu: intel`) that Roostack maps to device paths and groups (rootless `/dev/dri` needs `keep-groups`).
  - **`depends_on:`**, which becomes systemd ordering (`After=`/`Requires=`).
  - **Route options** at the Caddy level (e.g. `max_body_size`; more expected: timeouts, websockets).
  - **Storage `location:`** (e.g. `media` → the large data disk) and **per-directory storage classes**, so regenerable data (thumbnails, transcodes, caches) is excluded from backups.
  - **Database `image` override** for custom builds (e.g. Immich's Postgres), still following the standard database pattern; **`backup: false`** for transient stores (e.g. Redis job queues).
- **`ports:` — Locked (2026-09-26):** for protocols Caddy can't proxy (SSH, DNS, WireGuard), a package declares a container port with a title, a suggested host port (≥1024) and a protocol. Ports are **off unless the package enables them**; an Admin turns them on per service and can move them. Enabled ports are published on every host address (`PublishPort=<host>:<container>/<proto>`) and are **private** (home network only) via the firewall. Public ports come with the firewall and CrowdSec, like public routes. Roostack rejects clashes with other ports, the UI port and the web-service range (20000–29999). Templates see `{{ .Ports.<name>.Enabled }}` and `.HostPort` (e.g. for clone URLs).
- **`hooks:` — Locked (2026-09-27):** commands run inside a service's container.
  - `on: install` runs once after the first successful start (e.g. creating Forgejo's admin). It is retried while the app starts, so it must be safe to re-run; a failure shows under "Needs attention" with **Try again**.
  - `on: action` is a button on the service page for Admins (e.g. "Reset a password"), with optional `inputs` (string or secret).
  - User-provided values reach hooks **only as environment variables** (`env:` templates, `secrets:`), never templated into the command, so they can't change what a shell script does.
  - Settings can be `required`, have a `min_length`, and be `install_only`: asked at install, used only by install hooks. An `install_only` secret is **deleted once the install hooks succeed**, so Roostack doesn't keep a copy of e.g. the admin password.
  - Only `install` and `action` for now; `upgrade` hooks when a package needs them.
- **Service settings — Locked (2026-09-27):** most of an app's settings stay in the app. Packages list `links:` into its own admin pages (Forgejo's site administration, Vaultwarden's admin panel), shown first under Settings on the service page. Roostack's own settings (not secrets, not `install_only`) and the web address are editable there; saving regenerates and restarts the service. A secret marked `reveal: true` (e.g. Vaultwarden's admin token) can be shown to Admins on request, and each view is audited.
- **Future:** storage shared between services (e.g. Jellyfin reading Immich's library, read-only); migration steps for upstream breaking changes. (Upgrade notes are built: §8.3.5.)
- **Reference packages**, in the registry (§8.3.2): Vaultwarden (simple), Forgejo (Postgres, an optional SSH port), Immich (complex). Copies are this repository's test fixtures (`internal/testdata/packages`).

### 8.2 Several copies of a package — Locked, as built (2026-10-04)

Any package can be installed more than once (two Forgejos at different addresses, say), each copy treated as a separate service in everything.

- **Every installed service has an ID that never changes**, separate from the package it's an instance of: the instance file's `name` (the file is `<name>.yaml`); empty means the package's name, so the first copy is called after its package (`forgejo`) and nothing changes for it. Units, the Podman network, secrets, database names, data and media folders, Caddy's site file, backup tags (`service=<name>`), setup progress and the UI's URLs (`/services/<name>`) all use it. The package (`package:`) is what it runs.
- **People see a title**: the instance's `title`, or the package's. The ID is shown only where it matters (Details, folders).
- **Its name starts with its package's (decided 2026-10-04):** an ID is the package's name, or that, a dash and more (`forgejo`, `forgejo-work`; lowercase letters, digits and single dashes, up to 40 in all). So names say what they are in folders, containers and backups, and a package's own name is always free for its first copy. Considered: any name (a Vaultwarden called `immich` would take Immich's name).
- **Installing:** every install asks for a title (the package's by default) and the name's own part after `forgejo-` (empty for just `forgejo`), which follows the title as it's typed ("Forgejo (work)" gives `work`, the package's title taken out) until it's edited, and the web address follows the name (`git-work`) until that's edited. The catalog's "Add another…" on an installed package starts at "Forgejo (2)", `forgejo-2` and `git-2`. A name or address already used is a form error.
- **Renaming:** the service's page changes its title ("Rename"); its name is shown there and stays.
- **Considered:** renaming a service's ID later (it would mean renaming units, folders, secrets, databases and backup tags: rejected; the title changes instead); one set of data shared by copies (not what copies are for).

### 8.3 Service registry — Locked (2026-10-13), partly built

**What the Owner asked for (2026-10-13):** a proper registry of services: every package Roostack can install (not only the hero services on roostack.cloud/services), each with its definition file, and a way for the community to add their own. Planned the same day with options for each question; the Owner decided most of them (each subsection says which). The rest was decided in a second and third round the same day; the index's format was locked last (8.3.3). Nothing here is built, except where a section says so (8.3.1, 8.3.2, 8.3.3, 8.3.4's policy, install summary, your own packages and withdrawals, 8.3.5's compatibility, 8.3.6's facts and the catalog page).

**Where things stand (checked in the code, 2026-10-13).** These shape the plan:

- The catalog is `docs/examples/*.yaml`, copied into the `.deb` as `/usr/share/roostack/catalog/<name>/package.yaml`: **one version of each package per Roostack release**.
- An instance must name exactly its package's version (`instance.Validate`). So a release that bumps a package makes services already installed from it invalid, and §7's service updates aren't built yet.
- **The package isn't part of the lab's desired state.** Backups hold the instance files but not the packages they used, so restoring onto a Roostack with a newer catalog can't find the version the instance names. That breaks principle 1 (recoverable by default) as soon as packages change between releases.
- **Raw Quadlet passthrough accepts any key** in the `Unit`, `Container`, `Service` and `Install` sections. `Volume=` with a host path or `PodmanArgs=` could reach anything the `roostack` user can: every service's data, secrets and the lab's own files. Fine for packages the project writes; not for packages from strangers.
- An image not pinned by digest is only a warning.
- Packages carry no facts about the project itself (licence, website, source, maker, icon). The website's Services page keeps them by hand (`site/src/data/services.ts` in the roostack-cloud repository).
- Nodes already receive their services' package files from the controller over the lab API (`node/wire.go`), so only the controller needs to know where packages come from.

#### 8.3.1 The lab keeps the packages it uses — Locked (2026-10-13), as built (2026-10-14)

Whatever else is chosen: when a service is installed or updated, the controller **copies the exact package file into the lab's desired state** (e.g. `/var/lib/roostack/packages/<name>/<version>.yaml`), and generation reads that copy, not the catalog. It is backed up with the lab and replicated like the instance files.

- **Why:** a restore then needs nothing but the backup (principle 1); a newer catalog never changes a running service behind the Owner's back; local and community packages (below) work the same way as official ones; and the Owner can see exactly what is running (principle 4).
- The catalog becomes only *what can be installed*; the lab's copy is *what is installed*. Copies no service uses are deleted.
- **Considered:** keeping every past version in each release's catalog (grows forever, and still fails for packages that didn't come from a release).
- **As built (2026-10-14):** the copy is `/var/lib/roostack/packages/<name>/<version>.yaml` (`config.Paths.LabPackageFile`), the catalog's file byte for byte, 0644 (it isn't secret, and people can read what runs). `state.KeepPackage` writes it when a service is installed, before its instance file; whatever changes a service's version later (§7 updates, 8.3.8) must call it too. `state.LoadServices`, the manager's view of an installed service and the assignment sent to other servers all read the lab's copy; the catalog is read only to list and install packages. After each apply the controller deletes copies no service uses (`state.PrunePackages`), keeping those of services waiting to be restored. A package's `version` is now limited to letters, digits and `._+-` (up to 64), since it names a file.
  - **Backed up and replicated:** the copies are under the state folder, which the lab's backup already holds whole (`backup.LabPlan`), so they come back with a restore like the instance files; other servers get each package file inside their assignment, as before, now read from the lab's copy. Nothing else keeps instance files, so nothing else was needed.
  - **Labs from before:** a service whose version has no copy yet gets one from the catalog the first time it's loaded, if the catalog has that version; otherwise loading it fails with an error naming the missing file.

#### 8.3.2 Where definitions live — Locked (2026-10-13): their own Git repository, from the start

| Option | For | Against |
|---|---|---|
| **A. This repository** (`catalog/<name>/package.yaml`, out of `docs/examples`) | No new infrastructure; package and generator change together; golden tests next to the code | Every package fix waits for a Roostack release; community pull requests mix with Roostack's own; the repository's licence and review rules apply to packages |
| **B. A separate public Git repository** ("the registry repository": [`roostack/services`](https://github.com/roostack/services), created by the Owner 2026-10-13) | Transparent: every package and every change is a reviewable commit, forkable; packages can be fixed between releases; contributors don't need to touch Roostack's code; its CI builds the index (8.3.3) and the website reads it | A second repository to keep in step (its CI checks out a Roostack version to validate and render) |
| **C. A registry service on Roostack Cloud** (uploads, an API, a database) | Accounts, download counts, ratings | A lab would depend on Cloud to find packages, against principle 3 (local-first) and the rule that everything works without Cloud; server code to run and secure; less transparent than Git |

**Decided: B, right away** (the Owner, 2026-10-13). The packages move from `docs/examples` into the registry repository, not into a `catalog/` folder here first, so there's one move and package fixes never wait for a Roostack release. This repository keeps a few small packages as test fixtures for the generator's golden tests; labs fetch the registry (8.3.3). The registry is static files, so anyone can mirror it; Cloud may mirror it too, but is never needed.

- **Considered:** A first and splitting later (the earlier leaning: one place while the format moves fast, but two moves, and the split would come when it's busiest).
- **As built (2026-10-14): the registry's layout**, decided by the Owner the same day. `packages/<name>/` holds a file per version named after it (`1.34.3-roostack.1.yaml`), the logo as `icon.png`, and `registry.yaml`: the tier, the maintainers and any withdrawals, kept by the registry's maintainers rather than the package's author (a separate rule for it in the repository's code owners, later). Considered: a file each for tier, maintainers and withdrawals (finer ownership rules, three files per package for little gain). Plus a README, a CONTRIBUTING stub (8.3.7) and the Apache-2.0 licence; packages for Forgejo, Immich and Vaultwarden moved there from `docs/examples`. Here, copies of the three in the same layout are the tests' fixtures (`internal/testdata/packages`, found through `internal/pkgtest`); they change with the tests, not with the registry.

#### 8.3.3 How a lab finds and updates packages — Locked (2026-10-13); changed (2026-10-14): a signed index fetched from the registry, no bundled fallback

| Option | For | Against |
|---|---|---|
| **A. Bundled with each release only** (today) | Simple; works offline; packages are covered by the `.deb`'s own signature (once the apt repository is signed) | Package updates (security fixes, new upstream versions) wait for a Roostack release; community packages would all have to ship in every release |
| **B. Fetched from the registry only** | Packages update on their own schedule | A new lab without internet, or with the registry down, has no catalog |
| **C. Both** | The bundled snapshot is the offline baseline (principle 3); a newer index replaces it when the controller can fetch one | Two sources to reason about (the newer index wins) |

**Decided: C** (the Owner, 2026-10-13); **changed to B** (the Owner, 2026-10-14, below). The registry's CI publishes a static **index** (every package, every version, each file's SHA-256, its tier, schema, minimum Roostack version and architectures, and any withdrawals) plus the package files. The controller fetches it every few hours and when the catalog page is opened; nodes get packages from the controller as now.

- **Git is the source of truth; the index is generated from it — Locked (2026-10-13).** In the repository each package is a folder with a file per version, and its tier, maintainer and any withdrawals are files there too, so every change is a reviewed commit. After each merge, CI builds the index from the repository (like a lock file): one JSON file and its signature, beside the root key's statement naming the current signing key (below). The index holds a serial number and a date, then per package and version: the file's path and SHA-256, schema, minimum Roostack version, tier, the image architectures CI checked, and any withdrawal (level and reason). A lab downloads the index, checks its signature, and fetches only the package files it needs, checking each hash. That needs only Go's standard library (an HTTPS request and Ed25519), works from any mirror, and carries facts Git doesn't hold (the architectures CI found).
  - **Considered:** the lab reading Git directly (a clone or pull: a new dependency on every server, either the `git` package called from the sandboxed daemon or a large Go library, plus code to check commit signatures); GitHub's API to list files (ties labs to GitHub, no mirrors, and unauthenticated calls are limited to 60 an hour per address, which several labs behind one connection could reach).
- **Hosting — Locked (2026-10-13): GitHub** (the Owner's suggestion): the repository on GitHub, the index on GitHub Pages, reached through an address of ours (`registry.roostack.cloud`, as built below) so the host can change without a Roostack release. Considered: GitHub's raw file URLs (rate-limited, and the address is GitHub's); Cloudflare like the help site (§6.3.1; fine too, one more moving part).
- **The index is signed.** HTTPS proves a lab is talking to GitHub, not that the files are what the maintainers published: a leaked GitHub token, a bad workflow change, a mirror or a DNS hijack of our address could serve a changed package. A signature checked by the lab catches all of those, lets anyone mirror the files, and stops an old index being replayed (the index carries a serial number and a date, and a lab refuses one older than it has). Package files are trusted through their hashes in the index. Ed25519 is in Go's standard library, so no new dependency.
- **Two levels of key — Locked (2026-10-13).** A **root key** kept offline by the Owner, with the lab's other keys, whose public half is built into Roostack; it signs only a short statement naming the current **signing key**. The signing key lives in the registry's CI and signs every index, so publishing stays automatic (needed for 8.3.8). If the signing key leaks or CI is compromised, the Owner signs a new one with the root key and labs drop the old one, without a Roostack release. Losing the root key itself needs a Roostack release with a new one. Considered: one key, offline (every publish waits for a person); one key in CI (a leak means a Roostack release to replace it); the full TUF framework (the same idea with more roles and a dependency); minisign's file format (a known format, but it signs files, not key delegations; our own small JSON format is a few dozen lines).
- **Changed (2026-10-14): fetched only (B), no bundled snapshot as a fallback.** The Owner, when the packages moved: installing pulls images from the internet anyway, so an offline lab gains nothing from a bundled catalog, and a snapshot that's out of date never hears of withdrawals (8.3.4), so it could offer a vulnerable version with no warning. Restores don't need it either: they use the lab's own copies (8.3.1). What's given up: while the registry's address is down, nothing new can be installed or updated (mirrors can cover that later), and turning fetching off means no installs or updates from the registry.
- **The stopgap, gone (2026-10-14):** until fetching was built, each release shipped the registry at a pinned commit as `/usr/share/roostack/catalog` (`packaging/registry` named the commit; `scripts/fetch-catalog.sh` cloned it during `make build`). Removed with the as-built fetching below, the same day.
- **As built (2026-10-14): the formats, address and keys**, proposed and agreed with the Owner that day.
  - **Address: `https://registry.roostack.cloud/v1/`** (the Owner), a CNAME to GitHub Pages; `registry.url` in `lab.yaml` replaces it (a mirror). `v1` is the format: fields may be added within it (older Roostacks ignore them); a change older Roostacks would misread is a new format at `…/v2/`, beside this one. Considered: `services.roostack.cloud` (reads like the website's services page).
  - **Files:** `keys.json` and `index.json`, each with a `.sig` beside it, and `packages/<name>/<version>.yaml` and `icon.png` at the paths the index gives. A `.sig` is `{"signatures": [{"key": "ed25519:…", "sig": "…"}]}`: Ed25519 over the file's exact bytes, a list so a statement can carry an old and a new root key's signatures. A lab checks the signature first, then the file's `type`, so an index can't pass as a key statement.
  - **`keys.json`** (`roostack-registry-keys`): a serial, a date and the signing keys (`ed25519:` and base64). A lab remembers the highest serial it has seen and refuses a lower one, so once it has seen a statement naming a new key, an old statement naming a leaked key is useless. No expiry: the root key is offline, and an expiry would mean a ceremony on a timer.
  - **`index.json`** (`roostack-registry-index`, format 1): `serial` (the second CI signed it: always increasing with no counter to keep), `date`, the registry `commit`, and per package its title, description and categories (the newest version's, so the website and catalog can list packages without every file), tier, maintainers, icon (path, SHA-256, size), a whole-package withdrawal, and per version: path, SHA-256, size, schema, `requires_roostack`, the architectures CI found a build of every image for, and any withdrawal (level, reason, link). A lab refuses an index with a lower serial than it has, or the same serial with other contents.
  - **Stale: a warning, not a refusal** (the Owner). CI signs a fresh index every day even with no changes, so an index over 14 days old (`registry.StaleAfter`) means the lab can't reach the registry, CI is broken, or someone is holding back newer ones (a "freeze", which would hide withdrawals). The lab still installs from it, and says so in the catalog and under "Needs attention". Considered: an expiry after which nothing installs (a broken CI for two weeks would stop every lab installing); no warning (a freeze would go unnoticed).
  - **The key ceremony and rotations** are a process to follow when the Owner is ready: [docs/REGISTRY-KEYS.md](docs/REGISTRY-KEYS.md). Until then `rootKeys` is empty, a development build trusts a throwaway root key given with `make build REGISTRY_DEV_KEY=…`, and `build-deb.sh` refuses a release without a real root key or with a development one. **The guard covers every build (2026-10-16, security review M27):** it used to run only for a version of exactly `X.Y.Z`, so a `git describe` version such as `1.2.3-4-gabc` skipped it, and it searched `rootkeys.go` for `"ed25519:`, which a comment would satisfy. Now `make build` compiles `internal/registry/buildkeys` with the binaries' linker flags and writes what it reports (`root_keys=<n>`, `dev_key=<true|false>`, from `registry.Trusted`) to `bin/registry-keys`, failing on a malformed key; `build-deb.sh` refuses a package whose `bin/registry-keys` is missing, older than `bin/roostack`, has no root key or has a development key, unless it's told it's a development build (`ROOSTACK_DEV_BUILD=1`, which `dev-install.sh` sets). Considered: running `bin/roostack` to ask it (a Mac, or an amd64 machine building for ARM, can't run it).
- **As built (2026-10-14): building the index.** `roostack registry index` (`internal/registry.Build`) checks every package as `roostack validate` does (the package policy included), that each file is named after its version in a folder named after the package, each icon, and each `registry.yaml` (tier, maintainers, withdrawals of versions that exist); asks the image registries which processors every image has (`internal/imagecheck`, the code behind `make check-images`); checks `keys/keys.json` is signed by a root key and names the signing key; then writes the signed index and the files to publish. Any problem in any package fails the build: a broken package is fixed, not published without. `-check` does the same with no key and writes nothing, for pull requests. The registry repository's workflow (`.github/workflows/publish.yml`) runs it on pull requests (check only), on each merge to `main` and daily, and deploys to GitHub Pages; the signing key is in an environment only `main` can use. It downloads a Roostack release's `roostack` binary, pinned by its SHA-256 (`ROOSTACK_BINARY_URL`, `ROOSTACK_BINARY_SHA256`), so the registry's checks are a released Roostack's (the Owner, 2026-10-14: release binaries are coming; considered: checking out this repository, which is private, with a read token).
- **As built (2026-10-14): fetching.** The controller only (other servers get packages in their assignments, as before). `registry.Fetcher` gets `keys.json` and checks it with the root keys; gets `index.json` (with `If-None-Match`, so an unchanged index is one small request; unchanged, the copy on disk is checked again with the current signing keys) and checks it; then, for each package, picks the version this lab would install (`Package.Offer`: the newest not withdrawn at warning or stop, whose `requires_roostack` this Roostack meets, built for the controller's processor) and downloads it and the icon unless it already has a file with that SHA-256, checking size, hash, that it parses and names itself. Other versions, withdrawn ones and removed packages leave the folder; registry.yaml isn't kept (the index carries its facts). The index is written last, after its files. Limits keep a bad mirror from filling the disk (16 MB index, 1 MB a file). Everything lives in `/var/lib/roostack/catalog` (`config.Paths.CatalogDir`, now its default), left out of backups since it can be fetched again; `status.json` there records the last try, the last success, the error, the serials seen, the ETag and why any package isn't offered.
  - **When (the Owner asked whether the background check is needed; kept, 2026-10-14):** when Roostack starts, every 4 hours plus up to 30 random minutes so labs don't all ask at once (`registry.Updater`), and when the catalog page opens if the last try was over 15 minutes ago, waiting at most 10 seconds. The background check is what brings withdrawals (and, later, §8.3.8's updates) to a lab whose Owner doesn't open the catalog, and what makes the 14-day warning mean something.
  - **Settings → Updates** (the controller's page) has "Services you can install": when it last checked and whether that worked (the error under "What went wrong"), the list's date, size and registry commit (linked to GitHub), the address and folder, the packages not offered on this lab and why, "Check now", and "Check the service registry for services and fixes", on by default (`registry.disabled` in `lab.yaml`, named like `cloud.disabled`). Off, the catalog offers nothing and says why: the lab wouldn't hear of withdrawals, so an old list isn't offered either.
  - **Not built yet:** offering versions other than the newest; a lab whose servers have different processors (the index's architectures are checked against the controller's); mirrors as a fallback list. (The catalog's tier badges and search: 8.3.6, as built.)
- Settings → Updates shows when the catalog was last fetched and from where, and the Owner can turn fetching off (then nothing new can be installed from the registry). As built above.
- **Considered:** per-author signatures (e.g. sigstore): more infrastructure, harder for contributors, and the trust that matters is the review (8.3.4), which one registry key states; Git commit signatures alone (a lab would need Git, and the history, to check them).

#### 8.3.4 Trust and review — Locked (2026-10-13): three tiers; a package policy of risky lines; the policy, the install summary, your own packages and withdrawals as built (2026-10-14)

**Tiers**, shown as a badge on the catalog and the service page (as built 2026-10-15, below the tiers):

- **Official:** maintained by the Roostack project, reviewed, and tested on a real lab for each Roostack release (install, backup, restore, update, remove).
- **Community — a fast follow** (the Owner, 2026-10-13): opened soon after the registry starts with official packages, not before 1.0 is needed. In the registry, written and maintained by its author, reviewed against the checklist below before each version is published, but not tested by Roostack for each release. The UI says who maintains it and when it was last reviewed.
- **Your own (local):** a package file the Owner adds themselves ("custom services", §8). Never fetched or reviewed; installing one shows a plain warning that Roostack hasn't checked it. It still has to validate, and it's kept in the lab like any other (8.3.1). This is how a contributor tests a package before submitting it (8.3.7).

**Tier badges — as built (2026-10-15).** **Official**, **Community** or **Your own** beside a service's name on the catalog, the Services list and the service's page (the `tier-badge` component, one template for all three). For an installed service the registry's tier is read from the index the lab has now, by package name (a second copy too), so it follows the registry: a package that becomes Official shows as Official, and one the registry no longer lists shows none. Your own comes from the instance (`local: true`, above) and wins over a registry package of the same name. Considered: recording the tier at install, like `local` (stable, but stale once the registry changes it). Not built yet: who maintains a Community package and when it was last reviewed, and the tier text ("Roostack checked how this is set up; the app itself is made by …").

**What a package may do is enforced by Roostack, not only by reviewers.** Registry packages (both tiers) are checked against a **package policy** in `pkgspec`:

- **Raw Quadlet lines are allowed, except a list of risky ones — Locked (2026-10-13).** Roostack writes each container's Quadlet file (the `.container` file systemd and Podman run it from) itself, from what the package declares: its image, its folders, its network, its secrets. The `quadlet:` passthrough lets a package add lines Roostack doesn't model: Forgejo's `UserNS=keep-id…` (whose user owns its files) and Immich's database `ShmSize` (shared memory) are today's uses. The Owner wants wide support from the start (2026-10-13): any line is allowed and reviewed when the package is added, **except a deny-list of lines that could reach beyond the service and have a Roostack way to do the same thing**. The list (agreed 2026-10-13): `Volume=`/`Mount=` with a host path (use `storage:`), `PodmanArgs=` (anything at all), `AddCapability=`, `SecurityLabelDisable=`, `Network=`/`Pod=` (Roostack's per-service network), `PublishPort=` (use `ports:`), `AddDevice=` (use `devices:`), `User=0`/`root`, `UIDMap=`/`GIDMap=`/`UserNS=host`, and the `[Service]` and `[Unit]` lines that run commands (`ExecStart…`, `ExecStop…`). A line that turns up in several reviews becomes a modelled field. Considered: an allow-list (safer by default, but every new app would wait for a Roostack change: rejected as too restrictive to start with).
- Images pinned by digest in the package: an error, not a warning; a multi-architecture index digest when the project publishes one. (A lab may still follow upstream tags for a service when its Owner opts in: 8.3.8.)
- Storage only through `storage:` (Roostack's folders); devices only through the abstract `devices:` requests.
- Nothing public by default (already true: §6.11), `public:` with `unsafe`, `private_paths` and `login_paths` filled in where they apply.

Local packages may break the policy, with the Owner's confirmation and the list of what breaks it shown.

**The policy — as built (2026-10-14).** `Package.Policy` in `pkgspec` (separate from `Validate`, so a local package can break it) returns every problem, each a sentence naming the field or Quadlet line and what to use instead:

- **Quadlet lines**, in containers' and databases' `quadlet:`, matched whatever their case: the agreed list above, read this way: `Volume=` is refused with any source, a named volume as well as a host path (named volumes are shared by every service of the `roostack` user and aren't backed up; storage only through `storage:`), so only an anonymous `Volume=/path` passes; `Mount=` only as `type=tmpfs`; `User=` when the user part is `0` or `root`; `UserNS=host` only, so Forgejo's `UserNS=keep-id:…` passes; `ExecStart…`, `ExecStop…` and every other `Exec…` key in `[Service]` and `[Unit]` (the `[Container]` section's `Exec=` is the container's own command, and allowed).
- **Added by the Owner on 2026-10-14**, because the generator appends a package's lines after its own, so they would override what Roostack writes: `Image=` (would replace the pinned image), `Secret=` (could name another service's Podman secret), `EnvironmentFile=` and `Rootfs=` (read host paths), `GlobalArgs=` (like `PodmanArgs=`), `ContainerName=` and `Label=io.roostack.…` (how Roostack finds a service's containers).
- **Made a real boundary (2026-10-16), after the security review of that day (finding H2)** showed lines reaching beyond the service with no problem reported:
  - **Every line is read back as written.** systemd and Quadlet ignore spaces around a key, so `Volume =/var/lib/roostack:/lab` was a `Volume=` no rule saw; `=` or a line break in a key, or a line break in a value, made a line of its own; and a value ending in a backslash joins the next line to it (all checked on a dev VM: docs/ASSUMPTIONS.md A12). A key is letters and digits, starting with a letter, and a value has no line break and doesn't end in a backslash. `quadlet.CheckKey` and `CheckValue` say so, and three places use them: `pkgspec` validation (so `Parse` refuses such a package before the policy runs), the policy (in case a package reaches it unvalidated), and `quadlet.Unit.Validate`, which every unit Roostack writes goes through. Considered: trimming keys instead (the next oddity would be another bypass).
  - **Values are read the way Quadlet reads them.** `User=` and `Group=` are root as `root` or as any number that is 0 (`00`, `+0`); a `Label=` or `Mount=` line is several words, unquoted and unescaped, so each word is checked and a backslash refused; `Mount=` is a single `type=tmpfs` without a `source`; `UserNS=` is only `keep-id…`, `auto`, `nomap` or `private` (not `host`, `ns:<path>` or `container:<name>`).
  - **More keys refused**, matched whatever their case by name, prefix (`Exec…`) or part of a name (`…Path…`). In `[Container]`: those that read or write the server's files (`ContainersConfModule`, `EnvironmentHost`, `SeccompProfile`, a `LogOpt=` with a path, `HealthLogDestination=` a folder), change the image or the unit's name (`AutoUpdate`; `ServiceName`, which could name the unit after Caddy's), or loosen Podman's protections (`SecurityLabel…`, `Unmask`, `Annotation`, `GroupAdd=keep-groups`, `SubUIDMap`, `SubGIDMap`). In `[Service]`, the unit that runs Podman on the server: Podman's own environment (`Environment…`, `PassEnvironment`, `UnsetEnvironment`: `CONTAINERS_CONF_OVERRIDE` points it at another configuration), its input and output (`Standard…`, `TTY…`: `StandardOutput=append:<path>` writes to any file the `roostack` user can), its user and groups, any key naming a path, directory, credential or image (`…Path…`, `…Director…`, `…Credential…`, `…Image…`, `Root…`, `PIDFile`, `TemporaryFileSystem`), and how systemd runs it (`Type`, `NotifyAccess`, `Delegate`, `Slice`, `Sockets`, `BusName`, `LogNamespace`, security contexts). In `[Unit]`: every dependency and relationship (`Requires`, `Wants`, `BindsTo`, `PartOf`, `Upholds`, `Conflicts`, `Before`, `After`, `OnFailure`, `OnSuccess`, the `Propagates…` keys, `JoinsNamespaceOf`, `…MountsFor`), which Roostack writes itself from `depends_on:`, `SourcePath`, and the `…Action` keys (`FailureAction=exit` would stop every service of the `roostack` user). Everything in `[Install]`: Roostack writes `WantedBy=` itself, and `Alias=` could name the unit after another.
  - **Nodes check again.** A server other than the controller runs `Package.Risks` on every package in the assignment it's sent (`node.Decode`) and refuses the assignment if a registry package has any, naming the service and each problem, rather than trust that the controller checked. A package the Owner added themselves (`local: true` in its instance) may have risks, which the Owner accepted when installing it. The controller's own server applies its assignment in-process, after `CheckPolicy`.
  - **Still allowed:** Forgejo's `UserNS=keep-id…` and Immich's `ShmSize`. Every package in the registry still passes (`roostack validate`, 2026-10-16), and the generated files of the test fixtures are unchanged.
- **An allow-list of Quadlet keys — Locked (2026-10-16), the Owner, on the security review's recommendation; replaces "any line except the deny-list" (2026-10-13).** A deny-list over systemd's hundreds of `[Service]` and `[Unit]` keys kept having gaps, and every new Podman or systemd release could add more. Now a package may use only the keys Roostack has looked at and found to stay inside the service (`quadletAllowed` in `pkgspec`), and the deny-list stays as a second check that also says what to use instead:
  - **`[Container]`:** of the 81 keys Podman 5.4's Quadlet knows (Debian 13's; checked against `podman-systemd.unit(5)` on a dev VM), the 42 that stay inside the container (`Environment`, `Exec`, `Entrypoint`, `Tmpfs`, `ShmSize`, `Sysctl`, `Ulimit`, `ReadOnly`, `DropCapability`, `NoNewPrivileges`, `Mask`, DNS and host names, health checks, …), and 9 with their values checked as above (`Volume`, `Mount`, `User`, `Group`, `UserNS`, `Label`, `LogOpt`, `GroupAdd`, `HealthLogDestination`). Not allowed beyond the deny-list: `CgroupsMode` (where Podman puts the container's processes), `LogDriver` (Roostack shows the container's log), `StartWithPod` (no pods).
  - **`[Service]`:** when it's restarted or given up on (`Restart…`, `Timeout…`, `RuntimeMaxSec`, `WatchdogSec`, exit statuses) and how much of the server it may use (`CPUQuota`, `CPUWeight`, `IOWeight`, `MemoryHigh`, `MemoryMax`, `MemorySwapMax`, `TasksMax`, `LimitNOFILE`, `LimitNPROC`, `Nice`, `OOMPolicy`, `OOMScoreAdjust`). **`[Unit]`:** `Documentation` and the start limits (`StartLimitIntervalSec`, `StartLimitBurst`). **`[Install]`:** nothing.
  - **Exactly as written:** keys match by case here, as systemd and Quadlet read them (`shmsize` is refused with "write it as ShmSize"); the deny-list matches whatever the case.
  - **A key that isn't on the list** is refused with a sentence saying it hasn't been checked and that a package needing it asks for it. Adding one is a reviewed change to Roostack: say what it does, whether it reads or writes anything on the server or touches other units, and add a case to `TestPolicy`; `TestQuadletListsAgree` fails if a deny rule refuses every value of an allowed key. Considered: keeping the deny-list alone (the Owner's 2026-10-13 choice, for wide support; but the registry's packages need only two keys, and each review found more gaps); an allow-list for `[Service]`, `[Unit]` and `[Install]` only (`[Container]`'s keys are a known set, but a newer Podman adds keys nobody has looked at).
- **Images:** a container's `image`, and a database's when it sets one, must end in `@sha256:` and 64 hex digits; the multi-architecture check is the registry CI's (8.3.7). `Warnings()`, which only reported this, is gone.
- **Storage and devices:** the format already allows nothing else (mounts name a `storage:` entry; `devices:` takes only `gpu: intel`), so the Quadlet rules above are what enforce it.
- **Public access:** routes and ports must default to `exposure: private`; every route names at least one `login_paths` entry, or says why it shouldn't be public at all (`unsafe`). Decided by the Owner (2026-10-14) as what "where they apply" can mean mechanically; whether the private paths are right stays with review. A route without a login page (e.g. an API with tokens) marks itself unsafe. Considered: only checking the defaults (leaves the public fields to review alone); a new "no login" field (a format change for a rare case).
- **Facts and needs (added 2026-10-14):** the `about:` facts, `requires.roostack` and each container's `memory` are required (8.3.6 lists which), and a licence must say `-only` or `-or-later`.
- **Where it runs today:** `roostack validate` fails on a problem (`-local` reports them as warnings, for a package of your own); `roostack render` prints them on stderr and still renders; the catalog loader logs each one as an error and still offers the package, since a problem in a registry package is a registry bug (the registry's CI checks every change with `roostack registry index`, 8.3.3, and won't publish one that breaks it). `TestFixturesParse` holds the test fixtures to the policy too. **Installing checks it (2026-10-14):** `manager.Install` refuses a registry package with any problem (a FormError saying the registry should have caught it; the install page shows the list and no form, with a link to report it), and one of the Owner's own with risks unless the Owner accepted them (below).
- **Risks, apart from facts (2026-10-14):** `Policy` is now the missing facts (`about:`, `requires.roostack`, `memory`) followed by `Risks`: the unpinned images, Quadlet lines and public defaults, what could reach beyond the service or change unseen. A package of your own may leave the facts out (8.3.6), so only its `Risks` are shown and confirmed, and `roostack validate -local` warns about those alone.

**Your own packages — as built (2026-10-14).** From a mock-up; the Owner chose each of these from options the same day:

- **Adding:** "Add your own" is a card at the end of the catalog, for the Owner only, leading to **Add your own service** (`/catalog/add`): a package file and an optional logo, uploaded. The warning there, in the Owner's chosen words: "Nobody has reviewed this package. Services from the service registry are checked before they're offered; a package you add isn't. It decides which app runs and what it's given, so only add one you wrote or got from someone you trust." **What review checks** (a checklist in the registry repository, the same for both tiers):

**Pulling a bad package — Locked (2026-10-13), levels to detail.** The index can **withdraw** a version or a whole package, with a reason and a level. The Owner asked for levels, up to stopping a service, with an opt-out and a clear explanation:

- **Notice:** "Needs attention" says what's wrong and what to do (usually: update to the fixed version).
- **Warning:** the same, and the version can't be installed any more; updating is offered first on the service page.
- **Stop:** for a package found to be malicious, or an app being actively exploited with no fix: Roostack stops the service (its containers and its addresses), keeps all its data, and says on the service page and in "Needs attention" why, who said so (the registry, with a link), and what to do. The Owner can start it again, with a confirmation that names the risk.
- **The opt-out:** Settings → Updates, "Let Roostack stop a service the registry says is dangerous", on by default, explained in a sentence there. Off, a Stop is shown as a Warning.
- **Never:** removing a service or deleting data. A stop is the most the registry can do, so a stolen signing key (8.3.3) could at worst stop services until the Owner starts them again.

A lab that doesn't fetch doesn't hear of withdrawals, which is one reason there's no bundled fallback (8.3.3, changed 2026-10-14). As built (2026-10-14), the index carries withdrawals and the catalog no longer offers a version withdrawn at warning or stop. Published versions are never edited, only withdrawn and superseded. Considered: never stopping anything (the earlier leaning; leaves a known-malicious service running in labs whose Owner doesn't look); removing (data loss is never the registry's call).

**Withdrawals for installed services — as built (2026-10-14).** Wording and placement agreed with the Owner from a mock-up, and the questions below decided by the Owner, the same day:

- **Which services:** the controller compares each installed service's version with the newest index it has (`registry.Index.Withdrawn`), counting the version's withdrawal or the whole package's, whichever is more severe. It only counts when the lab's copy of the package file (8.3.1) has the SHA-256 the index names, so a package of your own that shares a registry package's name and version isn't the registry's to withdraw. A service waiting to be restored (§10.10) is left out.
- **Where the stop is kept: nowhere; it's worked out each time** (the Owner). Every assignment works it out again from the index, the opt-out and the service's `started_anyway` (`manager.markStops`). So a stop the registry lifts (published by mistake, or with a stolen key) lets the service start again by itself, and a restored lab works it out afresh. The only things saved are the Owner's choices: `started_anyway: <version>` in the instance file (desired state, backed up), and `registry.no_stops` in `lab.yaml`. The controller's settings (`registry-stop:<service>`) also note when Roostack first stopped a service, for the page and the last backup below. After each check of the registry (`Fetcher.Fetched`), the manager applies again if what's stopped changed. Considered: a `stopped:` field in the instance file (the service stays stopped after the registry lifts the stop); the store (not backed up, so a restored lab would stop again services the Owner had chosen to run).
- **What stopping does:** `generate.Stop` trims the service's generated files. Its containers and Caddy site go, and with them its addresses and ports. Its folders, secrets and network stay, and its names and ports stay reserved, so nothing else takes them meanwhile. The reconciler removes only unit and site files, so no data is touched. Other servers get the stop in their assignment (`WireService.Stop`).
- **Databases and backups** (the Owner: split by image). Only Postgres needs its container running to be backed up (`pg_dump`); SQLite and Redis are backed up from their files. A database on Roostack's own image (the package names none) keeps running, so backups carry on as before. One on an image the package sets could be the dangerous part, so it runs only until a backup of the server that started after the stop has finished. Roostack starts that backup straight away and checks every minute. Then the database stops too, its dump step is dropped, and later backups keep that last dump, which nothing changes while the service is stopped. A server with no backups set up has nothing to wait for. Considered: always keeping databases running (a malicious image keeps running, with outbound internet); always backing up first, then stopping everything (delays every stop by a backup).
- **What the pages say:** on the service page, a notice for each level, with the registry's reason in quotes, a link to its notice in a new window, "Said by the service registry; stopped <when>", and **What to do**: "wait for a fixed version, then update it, or remove it" (the Owner: offer removing too). Once the registry offers a newer version, it says "update it to <version>, which the service registry offers instead", with the Update button (§7.1, 2026-10-14). A stop is an error notice saying Roostack stopped it to protect the lab, that its data and backups are kept and its addresses are off. The status pill reads "stopped by Roostack" (`registry-stop`). Under "Needs attention": a stop is a problem (emailed like the others); started anyway, a warning, and a stop with stops off, a warning that says so; a notice is information. Admins see them; only the Owner can start a stopped service.
- **Start it anyway:** a collapsed "Start <app> anyway…" with **Make it private first**, shown and ticked when an address or port is public (the Owner: it keeps out whoever is attacking that version). It makes every route and package port private. The confirmation names the risk and says Roostack won't stop this version again. It's recorded in the audit log, and updating to another version ends it.
- **The opt-out** in Settings → Updates, under "Check the service registry", as agreed: "Let Roostack stop a service the registry says is dangerous", on by default, with the explanation in a sentence. Off, a stop shows as a warning, and services Roostack stopped start again.
- **`roostack backup run` on the command line** reads the instance files, which don't hold the stop (the nightly backup uses the assignment). So the dump step itself checks (2026-10-14): a Postgres database whose Quadlet file is gone, with a dump from an earlier backup, keeps that dump, and the backup's log says so (`backup.ErrDumpKept`). A database that crashed keeps its file, so its dump still fails and the backup says so. Considered: asking the controller for the stops (the command line would need the manager, or the lab API, for one case); checking whether the container is running (a crashed database would quietly keep an old dump).
- **Known gaps:** public DNS records and the relay keep a stopped service's names (nothing answers there, so they're simply unreachable); starting again needs no DNS change.

- **Considered (tiers and policy):** one tier only, everything reviewed and tested by the project (doesn't scale to community contributions); no enforced policy, trusting review alone (one missed `Volume=` would expose a whole lab, and local packages would have nothing checking them); an allow-list of Quadlet lines (rejected 2026-10-13, then adopted 2026-10-16: above); stricter rules for community than official (two rule sets to keep; official packages need nothing community ones shouldn't have, and needing an exception is a signal to review).

#### 8.3.5 Versioning and compatibility — Locked (2026-10-13)

- **A package version stays `<upstream version>-roostack.<revision>`** (§8.1). The upstream part says which release of the app runs; the revision counts changes to Roostack's definition for that release.
- **Updates (§7)** compare the upstream part: `patch` and `minor` policies need it to look like semantic versioning, otherwise the service only notifies. A revision-only change (a better definition, the same app) follows the `patch` policy. A service following upstream tags (8.3.8) uses the same policy names.
- **Each version declares its schema and the oldest Roostack it needs** (a new `requires: { roostack: "0.6" }` field). A lab only offers versions it can read and run; the catalog says "Needs a newer Roostack" for the rest.
- **The format is pre-1.0.** The registry keeps each version in the schema it was written in. Roostack reads the current schema and, during the alpha, the one before; when the schema changes, a converter rewrites the registry's current versions and the lab's own copies (8.3.1) on upgrade. At 1.0, only additive changes within `v1`.
- **No downgrades** through the UI: a newer app has usually migrated its database. Going back is a restore (§6.9).
- **Upgrade notes and migration steps** (§8.1 Future) become fields of a version, shown before updating.
- **As built (2026-10-14): `requires` and `upgrade_notes`** (in `pkgspec`, `about.go`; the format reference on the help site has the details).
  - `requires: { roostack: "0.6" }` names the oldest release, as `major.minor` or `major.minor.patch`. `Package.RunsOn(version)` compares it with the running Roostack's version (the `-X main.version` the build was given, from `git describe`), number by number, so `0.10` is newer than `0.9`. **Chosen (2026-10-14):** only the release the running version starts with counts, and what follows it is ignored, so `v0.6.0-3-gabc1234` (a build after the 0.6.0 tag) and `v0.6.0-rc.1` both count as 0.6.0; a version that doesn't start with a release (`dev`, a bare commit before the first tag) is a development build and runs everything. Considered: full semantic-version ordering with pre-releases before their release (a release candidate couldn't install packages written for its own release, and nothing is released yet); refusing everything on a development build (no package would install on a dev VM). The fetcher uses it (as `pkgspec.RunsOn`, on the index's `requires_roostack`) to keep only versions this Roostack can run (8.3.3, as built 2026-10-14); the catalog doesn't yet say "Needs a newer Roostack" (Settings → Updates lists such packages).
  - `upgrade_notes:` is a list of `{ version, note }`, **each note tied to the package version it arrived in** (decided by the Owner, 2026-10-14). A package keeps the notes it still needs from earlier versions, so the lab shows every note newer than the installed version, and updating from 1.9 to 2.1 still shows 2.0's warning while reading only the new file. Considered: free text for this version only (updating past several versions would show only the last note, unless the lab fetched every file in between). Shown before updating since 2026-10-14 (§7.1); an update with notes never applies automatically.
- **Considered:** versioning packages independently of upstream (hides which app version runs); following upstream tags automatically (no review of what changed).

#### 8.3.7 Contributing a package — Locked (2026-10-13)

1. **Write:** start from a template (`roostack package new <name>`, or copy an example) and the format reference on the help site, extended with a "Write a package" guide.
2. **Check:** `roostack validate` (already renders every template with default and flipped settings), plus the package policy (8.3.4); `roostack render` shows the generated files.
3. **Try it on a real lab:** add it as a local package on a dev VM (`scripts/dev-vm.sh`) or one's own lab, and go through install, a backup, a restore onto a fresh VM, an update from the previous version, and removal. The guide gives the steps and what to paste as evidence.
4. **Submit:** a pull request to the registry repository, with a checklist template. CI validates, applies the policy, renders golden files with default settings, checks each image digest resolves (and which architectures it has), and checks the `about:` fields. Later, CI could run the install test on a VM.
5. **Review and publish:** a maintainer goes through the checklist; on merge, the index is rebuilt and signed. The author is the package's maintainer; a community package whose maintainer doesn't keep up with upstream security releases is marked unmaintained, then withdrawn if it becomes unsafe.

**The guide — as built (2026-10-14).** The help site has a section of its own, **Make your own service** (the Owner chose it over a page in the technical reference, leaving room for more): an overview (a package just for your lab, or for everyone), **Write a package** (start from the registry package closest to the app; each part in the order it's needed; finding an image's multi-architecture digest with `skopeo inspect --raw … | sha256sum` or `docker buildx imagetools inspect`, as `podman image inspect` gives only the local processor's; `validate`, and `render` with a minimal `service.yaml`), **Try it on a lab** (install and use it, measure memory with `podman stats` as the roostack user, back up, restore the whole lab onto a fresh server, remove; the update step waits for service updates, §7) and **Submit it to the registry** (community packages aren't open yet, and the page says so). Evidence is a **checklist in the registry's pull-request template** (the Owner, 2026-10-14; considered: a free-form write-up): Roostack version and processor, `validate`'s line, install and what was added, public access, memory per container, the service's backup line and the restore onto a fresh server, removal. The registry's CONTRIBUTING.md points to the guide. `roostack package new` isn't built; the guide starts from a copy.

**The registry's pull-request checks — as built (2026-10-14).** Besides `roostack registry index -check` (validation, the policy, the `about:` facts, each image's processors), the Publish workflow renders every package a pull request adds or changes and puts the files in the run's summary, with a diff against the previous version of the same package (`.github/render-changes.sh` in the registry). **Not committed** (the Owner, 2026-10-14; considered: golden files beside each package, which every contributor would regenerate on Linux with the pinned binary, and every Roostack update would rewrite). For this, `roostack render -package FILE` needs no lab or service file: it renders the package's defaults in an example lab (`generate.ExampleLab`, `lab.example.com`, and `ExampleInstance`); the guide's "Check it" uses it too. **Code owners:** a GitHub team, `@roostack/registry-maintainers`, owns everything (`.github/CODEOWNERS`), every `registry.yaml` included; community packages' folders gain their maintainers when they open (the Owner, 2026-10-14; considered: the Owner's account alone, or nothing until then). It takes effect once the team exists and `main` requires code owners' reviews.

#### 8.3.8 Updates without waiting for a new definition — Locked (2026-10-13): both ways

The Owner wants (2026-10-13) services to pick up an app's patch releases (security fixes, mostly) without waiting for new definitions, and an opt-in to follow upstream at patch or minor level without the registry's digest. With the registry in its own repository and fetched by labs (8.3.2, 8.3.3), nothing waits for a Roostack release any more. **Decided: both of these.**

**1. An update bot in the registry (the default path).** A job in the registry's CI checks each package's upstream for new releases every hour, writes the new version (tag, digest, `version`) and opens a pull request. CI validates and renders it, and **runs it**: installs the package with its default settings in rootless Podman on the CI runner, waits for its health checks, and, for packages with databases, takes a backup and restores it into a fresh copy. Patch releases of official packages merge themselves when that passes; others wait for a person (community packages: their maintainer). Labs fetch the new index within hours, and each service's update policy (§7) applies it in the maintenance window (§3.2).

- **What "tested" means here:** CI shows the new version starts, answers its health checks and survives a backup and restore with this definition. It doesn't click through the app; a person reviewing a minor or major release can. Without the CI run, a bot update would only be checked on paper, which is the Owner's point.

**2. "Follow upstream" per service (opt-in).** On a service's update settings, the Owner can choose to follow the app's own releases at **patch** or **minor** level, ignoring the registry's digest:

- The package says which tags count as releases (a new `updates:` field, e.g. a tag pattern), so it only works for apps whose tags look like semantic versions; others don't offer it.
- The controller looks up the newest matching tag (on its update schedule), pulls it on the service's server, and **records the digest it got in the lab's state**, so restores stay exact (principle 1) and the Owner can see exactly what runs.
- **After each update the lab checks the service's health and goes back to the previous image if it fails** (Podman keeps the old image until the new one is healthy), with the reason under "Needs attention". It never rolls back a database, so a failed update after the app migrated its data is shown, not undone (the backup taken before updating, §6.9, is the way back).
- The choice is explained where it's made: the app's newest releases arrive sooner, but Roostack hasn't checked them with this package, and a release that needs a new definition can break the service until one arrives.
- The definition itself (folders, settings, backups) still comes only from the registry; a new definition for a newer upstream version is offered as a normal update.
- Withdrawals (8.3.4) can name image digests as well as package versions, so a bad upstream image is caught for services following upstream too.

**What the digest still gives, and doesn't (2026-10-13).** The Owner asked what pinning is worth if the bot updates it anyway. It gives: every lab runs exactly the bytes CI ran; a tag that upstream (or someone who took over upstream's account) re-points to a different image doesn't reach labs until a new commit, which a person or CI sees; and a bad image can be withdrawn by its digest. It doesn't give: any review of the app's code, and on its own it doesn't test anything (hence the CI run). Following upstream gives up the first two in exchange for speed, which is why it's an opt-in.

- **Considered:** only the bot (the earlier leaning; the Owner wants the choice); only following upstream (every lab would run untested images by default, and each lab would query image registries, which rate-limit: Docker Hub's anonymous limits); bot updates merged without running them (only checked on paper).
- **To agree later:** whether CI's run also covers ARM, once Roostack runs there (§3).

#### Decided in the second round (2026-10-13)

- Signing: an offline root key held by the Owner, with the project's other keys, and a signing key in CI (8.3.3).
- The registry repository's licence: **Apache-2.0**, the same as Roostack (§2.1): one licence across the project, contributions come under it explicitly, and Cloud can use the definitions like Roostack's code. Considered: MIT-0 or CC0 (copying snippets without credit; a second licence to explain).
- Review: anyone with merge access to the registry repository may review and merge a community package; one approval.
- The registry repository: `github.com/roostack/services`, created by the Owner (2026-10-13).

## 10. Multiple Servers — Locked (2026-09-27)

One lab can span several servers: extra boxes at home, VPSes in the cloud, and later Roostack Cloud. This section is the design to build towards; nothing here is built yet except where marked. It replaces "master/worker" elsewhere in this document.

### 10.1 Roles

**Naming (2026-09-28):** the computers in a lab are **servers** everywhere: the UI ("My Servers", Settings → Servers, "Move to another server"), this document and the code (earlier drafts said "machine"; the database was migrated). A **node** is a server's role when it isn't the controller, and `node.Node` is the code's handle on any server.

**Servers in the UI (2026-09-28):** Home shows **My Servers** beside My Services (status, backups, updates, services, a link to each server's settings). Settings that differ per server (updates and restarts, time zone, remote access, backups) are grouped under "Each server": the overview summarises every server, and each area's page opens on a summary row per server that also switches between them. Each server has its own page (`/settings/servers/<id>`) with its card and its settings. Service cards say which server a service runs on and when it was last backed up, with details (containers and images, web routes, ports, data folders and size); Roostack's own services (Roostack and its agent, Caddy, backup stores, network links) are shown per server behind a toggle, so nothing is hidden from a technical user.
  **Revised (2026-10-15, Console glass, docs/DESIGN.md "Layout"):** Servers is a main area in the sidebar (`/servers`), Home shows services and servers as tables under a strip of figures, and a service's details (containers and images, routes, ports, data folders and size) moved from the Services list to the Technical side of its page.

- **Node:** any server running Roostack. Every node runs its own services (Quadlets, reconciler), its own Caddy and certificates, its own backups, OS updates, firewall and agent, exactly as a single-server lab does today.
- **Controller:** one node also holds the lab's desired state (§1.2: services, placement, settings), users and sessions, and serves the UI. It decides placement; nodes do the work.
- **The controller can move to any node** (chosen, not automatic), e.g. from a home NUC to a VPS:
  - Every node keeps a **replica of the lab's state** (desired state and the Roostack database), pulled with its assignments. The controller encrypts it with the **recovery key** (§6.9) before sending it; nodes store it but can't read it, because the recovery key is never stored on a node other than the controller.
  - **Planned move:** the controller hands over (freezes changes, sends the latest state, the new controller takes the address and certificate authority) and becomes a plain node.
  - **Disaster:** the Owner promotes a node from its replica by entering the recovery key (they have it written down for exactly this). At worst it misses changes since its last pull. Two controllers must never both be active: promotion revokes the old one's authority (a new epoch number that nodes follow).
- The first server installed is the controller; a lab with one server is a lab with one node that is also the controller. Single-server labs stay exactly as simple as today.

### 10.2 Private network: Roostack-managed WireGuard

- Roostack runs a **WireGuard** network between its nodes (WireGuard is in Debian's kernel; `roostack-agent` manages the interface and keys). Every node gets an overlay address (e.g. `100.96.0.x`).
- **No inbound ports at home:** home nodes dial out to reachable nodes (a VPS with a public IP), so a home controller needs no port forwarding. Nodes that can reach each other directly do; others go via a reachable node (hub and spoke first, a mesh later).
- All controller ↔ node traffic runs inside WireGuard **and** uses mutual TLS, so a leaked WireGuard key alone isn't enough.
- **Joining:** the Owner creates a one-time join code in the UI (short-lived, single use) and runs `roostack node join <code>` on the new server (or picks "Join an existing lab" in its setup wizard). The code carries the controller's address and a CA fingerprint; the node gets its WireGuard peer config and a client certificate from the controller's CA.
- ~~"Private" (home network only, §6.10) widens to **home network or Roostack's WireGuard network**.~~ Replaced on 2026-10-17 by "The lab's servers are a trust class of their own", below. The same network is the base for remote access for people later (a phone joining over WireGuard).
  - **Joining servers — as built (2026-10-16, review M23):** a join code's one-time key is a live WireGuard peer for up to an hour, so on the hub anyone on Roostack's network who isn't one of the lab's servers reaches only the lab API (8471), and nothing from them is forwarded; the firewall lets a server in once it has joined (the hub re-applies). A joining server's name loses control characters, as renaming does (it falls back to the server's ID).
  - **The lab's servers are a trust class of their own — Decided (2026-10-17) by the project's Owner, as built (review M23):** a cheap VPS in the lab (the edge, a storage box) was equal to a laptop on the LAN, reaching the UI, private routes, home-only ports and SSH, with no CrowdSec or rate limit in the way. Now the firewall settles the `roostack` interface before any rule by address, as for other labs and the relay (`internal/trust`, §6.10 item 1): a server (an address in `100.96.0.0/17`; the hub gives them out from `100.96.0.0/24`) reaches **the lab API (8471), services' web ports on another server (for the controller's Caddy), backup stores and proxy ports, ping, and an edge Caddy's edge listener**, and nothing else; nothing over Roostack's network is forwarded but the store port, and only from servers. The servers' range is out of the home set, so Caddy's private list leaves it out too. Before deciding, nothing in Roostack was found relying on more: servers talk only on those ports, and a service on another server that calls a private name gets the controller's home address, not its WireGuard one. Nothing is released, so no lab needed telling beyond the pages.
    - **SSH between servers (the Owner's choice): only from the controller,** whatever "who can log in" says (unless Nobody), so the Owner can go on from the server that runs the lab to a cloud server whose SSH is for the home network only; whoever holds the controller has the whole lab anyway. A cheap VPS can't try SSH on the home servers. The firewall request carries the controller's address (`Firewall.Controller`, from a node's point of view). *Considered:* never (a cloud server set to home only would need its provider's console), and from any server, as before (a compromised VPS could still try SSH everywhere).
    - **People's devices (the Owner's choice): a range kept for them now.** `100.96.128.0/17` is for a laptop or phone joining Roostack's network later (remote access for people, not built): it counts as home already, for the firewall (on `roostack`, it goes on to the home rules) and Caddy. *Considered:* deciding when remote access is designed.
    - **Telling people (the Owner's choice): the pages and help.** "Who can log in" says, in a lab of more than one server, "Not from this lab's other servers" (and on another server, "except the one that runs the lab"); who's connected names "the server that runs this lab" or "another server in this lab"; a choice that would cut off an SSH session from another server asks first, "anywhere" included. *Considered:* a one-off Needs attention notice.
    - Checked on VM4 with the agent's sandbox and real traffic (docs/ASSUMPTIONS.md Q13).

### 10.3 Controller ↔ node protocol

- **Nodes pull.** Every node periodically (and when nudged) fetches **its assignment**: the instances placed on it (package, version, settings, secrets it needs) plus lab settings it needs (domain, DNS provider, backup destinations). It generates and reconciles locally with the same code as today, then reports back **status**: service health, apply results, activity logs, backups, updates, restart needs.
- **Pulls — as built (2026-10-17, review M26).** A server fetches its assignment when Roostack starts there and every 15 minutes (every 30 seconds while that fails). The controller hands over the latest assignment it built for that server, and builds them (an apply on every server, the controller's firewall reload included) only when there's none yet, after the controller restarted. A server asking again within 10 seconds of its last fetch is refused (429), so a taken-over server can't keep the controller applying. Until then every fetch applied.
- **Offline-tolerant:** if the controller is unreachable, a node keeps running its last assignment and queues its reports (§1.3 local-first). Assignments carry a version; nodes apply only newer ones.
- **Actions** (restart a service, run an action hook, restore, update now) are requests the node picks up on its next pull (or immediately when nudged), with results in the report. The same request types the in-process code uses today (e.g. the agent's JSON API) cross the network unchanged.
- **Secrets:** user-provided secrets travel only to the nodes that need them, over mTLS inside WireGuard; generated secrets are made on the node that uses them and never leave it (backups hold them, encrypted).
- **Backups per node:** each node backs up its own services to **its own repository** (or its own folder at the same destination) with **its own key**. The recovery key is added to every repository as a second key (restic supports several), so the Owner can restore anything with it, while a compromised node exposes only its own backups and its key can be revoked.
- **Packages:** the controller's catalog is the source of truth; nodes fetch package files they don't have (same version pinning).
- **Certificates (2026-09-28):** each server's certificate (from the controller's CA) lasts a year and renews automatically when 120 days are left: nodes ask the controller over the lab API with their current certificate; the controller signs its own. TLS picks up a renewed certificate without a restart. The controller records the certificate each server may use (its serial) and its lab API accepts only that one, plus the one it replaced until the new one is first used (in case the reply was lost). Removing a server therefore revokes its certificate as well as its WireGuard peer; a server rejoining gets a new one. Nodes accept requests only from the controller. Settings → Servers shows each certificate's expiry; one within 30 days of expiring (renewal failing) needs attention. The CA itself (20 years) isn't renewed yet.
- **Before the domain is set up**, Caddy waits for its DNS credentials and the rest of the lab (services, backup stores, storage for others) is applied without it.

### 10.4 Placement and moving services

- Every instance has a **`host`** (a node ID); default: the controller. The install form asks where to run it when the lab has more than one node, with hints (RAM, disk, GPU, home or cloud).
- **Moving** a service = back up on the old node, restore on the new one, switch its route, remove the old copy (existing per-service backup and restore, §6.9). Portability is the requirement from §4.

### 10.5 Public access through a cloud node ("edge")

For services hosted at home but public (e.g. Immich shared with family), without opening ports 80/443 at home:

- A cloud node can act as an **edge**. It forwards with Caddy's layer-4 plugin (`caddy-l4`, added to Roostack's Caddy image like the DNS plugins; ASSUMPTIONS to verify SNI routing and PROXY protocol). Public DNS records point to the edge's public IP; the edge forwards each connection **over WireGuard** to the home node that runs the service.
- **TLS passthrough by default:** the edge routes on the TLS SNI name and never decrypts; certificates and keys stay on the home node, so the cloud provider can't read the traffic (in line with "own your data", §4; unlike the Cloudflare proxy, §6.5.1). Visitors' IP addresses reach the home node via the PROXY protocol, so private checks, rate limiting and CrowdSec (§6.10) still see real visitors.
- Terminating TLS at the edge (caching, fewer hops) is an option per service later, clearly marked as letting the edge see the traffic.
- The home firewall stays closed to the internet; only WireGuard (outbound) is needed. The same mechanism is how a **Roostack Cloud relay** would work for people behind CGNAT (§6.5.1).
- Home devices keep reaching home services directly (local DNS records, §6.5.1), not via the edge.
- **As built (2026-10-11):** prototyped first (docs/ASSUMPTIONS.md Q1–Q11), then built and tried for real: VM3 (a controller at home, behind two NATs, no port forwarded) made Vaultwarden public through `roostack-test` (a Linode in Sydney, in the lab by the controller dialling it, §10.2), and a visit from the internet got Vaultwarden with VM3's own certificate, its admin path refused, plain HTTP redirected, Roostack's own pages not passed on, and VM3's log showing the visitor's real address.
  - **Choosing it:** Settings → Public access, **How people reach your public services**: port forwarding at home, or **through <a cloud server> in this lab** (any server but the controller with a public address: where the controller dials it, or where it connects from). Saved as `public.edge` (the server's ID) in `lab.yaml`, applied without a restart. A lab on the internet is reached directly and isn't offered it. The service's own public checklist then says there's nothing to change on the router.
  - **The edge server** gets Roostack's Caddy (servers other than the controller otherwise have none), built the same way with `caddy-l4` v0.1.2 added to the image, publishing TCP 80 and 443 only. Its config comes in its assignment: the lab's public names (and their old ones while those work) are passed through by the TLS name to the controller's 443 over WireGuard, with a PROXY v2 header; plain HTTP for them is redirected; anything else gets nothing. No certificates or DNS logins on it.
  - **The controller's Caddy** believes PROXY headers only from the edges' WireGuard addresses, and its private checks treat those addresses as outside ("not (private and not an edge)"), so a connection from the edge without a header (a bug, or a broken edge) reaches nothing private. **Changed from the design the same day:** a separate edge port (8443, WireGuard only, header required) was the plan; Caddy's options can't require a header from a trusted source anyway (Q4), and treating the edge as outside fails safe where a separate port wouldn't, with no second listener or duplicated sites.
  - **Changed again (2026-10-16, review H4): edges get their own listener after all.** Believing headers on 443 let an edge (a compromised VPS, or one of Cloud's relay edges, another trust domain) send `PROXY TCP4 192.168.1.5 …` and reach every private route and the UI "from home": only the edge's own address was outside, not the addresses it claimed. Now Caddy believes headers only on **port 8474** (`servers :8474`, `proxy_protocol` with the edges' addresses), whose sites are the same wildcard sites again (same snippets, same certificates) with `vars roostack_edge yes`, and every private check is "not (private, not through an edge, and not from an edge)": through the edge listener, nobody is private, whatever the header says, and the UI isn't served there at all. Port 443 believes no header. The firewall redirects TCP 443 from `roostack-relay`, and from the lab's edges' addresses on `roostack`, to 8474 (an `inet` nat chain), and only they reach 8474, so neither the lab's edge config nor Cloud's edges change. Plain HTTP still redirects to 443. Considered: a layer-4 guard on 443 rejecting proxied private sources (one port, but it depends on caddy-l4's listener wrapper and on getting every form of a private address right; a gap there grants home access); the earlier objection to a second port (no way to require a header) doesn't matter here, since that listener grants nothing private either way. Checked with Caddy on VM4 (docs/ASSUMPTIONS.md Q12).
  - **The edge is one of the lab's servers (2026-10-17, §10.2):** over Roostack's network it reaches the controller's edge listener (its 443, redirected) and what every server reaches, never the UI or private routes on 443 or SSH.
  - **Public DNS records** point at the edge's public address while it's the way in (`public.Chosen`, asked each time), else the home's.
  - **TLS ends on the controller**, where every public name's certificate is (a service on another server is still proxied by the controller's Caddy, §10.9): so the edge passes to the controller, whichever server runs the service. A lab whose controller is in the cloud already serves public names itself and needs no edge; passing visitors through to a home server undecrypted there would need Caddy on that server (later).
  - **Through Roostack Cloud's relay — as built (2026-10-11), its first slice:** a third way in, for a lab linked to Cloud whose address is its roost.ac name (custom domains in Cloud's second slice). Choosing it asks Cloud first (`PUT /v1/lab/relay` in `cloudapi`: the relay WireGuard key and the public names; an account without the pilot grant is refused, and the page says so); the agent makes a separate interface, `roostack-relay`, keeping its key, which dials every edge Cloud names (addresses in 100.81.0.0/16, a keepalive). The controller's Caddy believes PROXY headers from the edges' relay addresses and treats them as outside, as for the lab's own edge; Cloud points the relayed names at its edges in DNS; the names follow the public ones after each apply (in the background, as Cloud may be slow; since 2026-10-14 one update at a time, sending the countries as they are then and nothing once the relay is off, so a slow update never undoes a newer change). **The firewall accepts only TCP 443 from `roostack-relay`, before the home-network rules** its addresses (inside 100.64.0.0/10) would otherwise match: an edge reaches Caddy and nothing else (since 2026-10-16 its 443 goes to Caddy's edge listener, and the relay's range isn't home at all, §6.10 item 1). Tried over the internet (2026-10-11): VM3 through the test edge in Sydney, Vaultwarden with VM3's own certificate, its admin path refused, the visitor's real address in VM3's log.
    - **Visitors by country, and the lab's bans at the edges — as built (2026-10-11), the relay's second slice:** while relayed, Settings → Public access has "Visitors by country": anyone (the default), only visitors from chosen countries, or everyone except them, and "Let everyone in" for a day to a month (travel), after which the limit comes back by itself. Kept in `lab.yaml` (`public.countries`), sent with the relay request (`RelayRequest.Countries`, Cloud checks it; a refusal isn't saved), enforced at Cloud's edges before visitors reach the lab. No countries are kept out by default (Cloud's DESIGN §5, changed 2026-10-11: a refused visitor gets a bare connection error, with no page saying why). The controller sends CrowdSec's own bans (origin `crowdsec` or `cscli`, bans of an address or range; not the community's lists) every 5 minutes (`PUT /v1/lab/relay/bans`, at most 1,000, newest first); Cloud drops them an hour after the last. Countries apply only through the relay for now: port forwarding and the lab's own edge reach the lab's Caddy directly. Tried over the internet (2026-10-11) with VM3: only New Zealand refuses a visitor in Australia and only Australia lets them in, "Let everyone in" and ending it, a CrowdSec ban refused at the edge within a minute of being sent and let in again when lifted.
    - **The lab's own domain through the relay — as built (2026-10-12), the relay's third slice:** a lab whose address is its own domain (not a roost.ac name) can choose the relay too. Failover is service-specific, so packages declare what they support:

- **none** (default): if the node is down, the service is down; the UI says so.
- **cold standby:** a second node keeps recent backups of the service; if the primary is unreachable for a set time, the Owner (or, when enabled, Roostack) restores the latest backup there and switches the route. Data since the last backup is lost; suits most home services.
- **replicated:** the service keeps a live copy on another node with its own replication (e.g. Postgres streaming, Vaultwarden via its database), declared per package. Much later.
- Automatic failover needs a way to tell "node down" from "network split" (at least a third node or the edge as a witness), so it comes after manual failover.

### 10.7 What to build now (no networking yet): seams

So single-server code doesn't paint us into a corner:

1. **`host` on every instance**, defaulting to the controller; loading services filters by host.
2. **Controller/node split in code:** the UI-facing manager (desired state, users, placement) talks to a **`Node` interface** for everything that touches a server (apply, status, hooks, actions, restores, activity, updates, restarts, firewall). Today: one in-process implementation. Later: a remote implementation speaking the same plain-data requests.
3. **Status, activity and restart state are per node**, and the UI's "This server" areas are per node (e.g. `/settings/servers/<id>/updates`) once there's more than one.
4. **Node identity:** every install gets a stable node ID and name at setup.

Then a **two-VM prototype**: a second dev VM joins the first over WireGuard and runs one service placed on it.

### 10.8 Decisions (2026-09-27)

- **Network layout:** hub and spoke (servers talk through a reachable node, usually a VPS). Direct links between two networks behind NAT (hole-punching, full mesh) only when a real case needs them.
- **Edge forwarding:** Caddy's `caddy-l4` plugin, not a forwarder of our own.
- **Keys:** the recovery key protects the state replicas and is added to every node's backup repository, but is stored only on the controller; each node has its own backup key (§10.3).
- **Roostack Cloud:** nodes run by Roostack Cloud are trusted like any hosting provider (a server running your services can see them; there's no real alternative). Roles that don't run services stay **zero-knowledge**: a relay or edge uses TLS passthrough, and a backup target only ever receives restic-encrypted data. Billing is out of scope until Roostack Cloud exists.

### 10.9 Prototype as built (2026-09-27)

What the two-VM prototype does, where it refines the design above:

- **Hub:** the controller is the WireGuard hub (`100.96.0.1`, UDP 51820; network `100.96.0.0/24`). A reachable hub other than the controller comes later.
- **Joining:** the Owner makes a code in Settings → Servers and runs `sudo roostack node join <code>` on the new server. The code carries a **one-time WireGuard key**, so only the hub's UDP port needs to be reachable (no public TLS endpoint).
- **The controller dials out — as built (2026-10-11):** when the controller can't be reached (at home, behind its router) and the new server can (a cloud server), the code is made with **None: this server connects to the new one instead** and the new server's public address. The code then says *listen*, without an endpoint: the new server listens on WireGuard's port (Roostack's firewall opened for the join by a fixed agent call, then kept open by its assignment), and the hub dials it at that address with a keepalive, before and after it joins (`servers.dial`). Everything else about joining is unchanged. The rule underneath is the one direct links use: whichever side can be reached is dialled. Both ways round now work: a controller in the cloud with servers at home (they dial it), and a controller at home with a server in the cloud (it dials the server); two servers both behind NAT still need a reachable hub (later). **Tried for real (2026-10-11):** VM3 (a controller behind two NATs: QEMU's and the home router's) joined a Linode in Sydney, with nothing forwarded at home. **Not yet:** if the cloud server's address changes, the hub keeps dialling the old one (re-join it, for now). Over WireGuard, the server checks the controller's CA against the code's fingerprint, sends its own WireGuard key and a CSR, and gets its certificate; the hub then replaces the one-time key with the server's own. Codes work once and expire after an hour.
- **Protocol:** every server serves a lab API on its overlay address (port 8471), mutual TLS with the lab's CA. The controller **sends** assignments and makes requests directly (status, service states, activity, hooks, actions, secrets, backups, restores, updates, restarts, settings); a node also **pulls** its assignment when it starts and every 15 minutes, and keeps its last one (without secrets) to run while the controller is away. Assignments carry a version; older ones are ignored. The controller works out every server's assignment on every change, but **sends only what changed**: a server that already has the same assignment, and applied it without error, isn't sent it again (it would only look busy, e.g. "Applying changes on vps" while a service installs elsewhere); one whose last apply failed is sent it again, as its retry. Typed-in secrets travel once and are never stored on disk.
- **Web routes of a service on another server:** the server publishes them on its overlay address (firewall: WireGuard interface only) and the controller's Caddy forwards to it (TLS ends on the controller for now; passthrough is §10.5's edge).
- **Nodes** run no UI, Caddy or DNS. Per-server pages live under `/settings/servers/<id>/…`.

### 10.10 Backups across servers, and moving services — Locked (2026-09-27)

Builds on §6.9 (restic, recovery key, 3-2-1) and §10.3 (each server backs up its own services to its own repository with its own key).

**Destinations are chosen per server, from providers the lab knows.**
- A **provider** is a place backups can go: a cloud account (B2, S3, …), an SFTP server, **a server's own disk**, or **another server offering storage** (below). A provider is set up once (its credentials) and any server can use it; the Backups page of each server picks one (and later extra copies, for 3-2-1).
- Every server's repository goes in **its own folder**, always, even if only one server uses the provider: `<provider path>/roostack/<lab id>/<server id>/`. Moving a lab or adding servers never reshuffles folders. On a rest-server store the server's own area comes first instead (`/<server id>/<lab id>`), because private repositories are named after the user; at another lab's store it is the same, `/<server id>/<lab id>`, since each server has its own user there too (2026-10-17, below; backups set up there before then stay at `/<guest user>/<server id>`, under the lab's shared user).
- **The controller creates each repository** (decided 2026-09-27): it runs `restic init` at the destination with the recovery key, adds a new key for the server, and gives the server only that key. The recovery key never leaves the controller. So the controller must reach every destination, which the next point guarantees.

**Disks are offered over Roostack's network (restic's rest-server).**
- A server's own disk is used through a small **rest-server** on that server, listening only on Roostack's network. The controller creates repositories through it like any other destination, and the server backs up to itself through it too. One mechanism covers "local disk", "the NAS at home" and "a friend's server".
- rest-server runs **append-only** for backup clients, so a compromised server can add backups but not delete or overwrite old ones (ransomware protection, §6.9; verified on a VM, docs/ASSUMPTIONS.md O1). It can still add any new file, including junk that stops restic (below, "Junk in a repository"). Pruning is done by a key that can delete, held by the controller (see open question 2).
- **What a server can delete — as built (2026-10-16).** A server never prunes a repository the controller made; the controller does, with its own credential. Whether the server's *own* credential can delete its backups depends on the destination (`manager.Access`, `BackupAccess`; destinations are resolved once into a typed kind, `destination.go`, instead of a prefix switch in each place):
  - **Can't delete (append-only):** another server's disk in the lab (rest-server `--append-only --private-repos`; on the server's *own* disk it can delete the files directly, so that one can); a friend's lab (its rest-server, append-only too); Roostack Cloud (keys for the server's own folder that can only add).
  - **Can hide, not erase: Backblaze B2**, with a key Roostack makes. The key has `listBuckets, listFiles, readFiles, writeFiles`, no `deleteFiles`. Through B2's S3-compatible API, `writeFiles` deletes a file by name by hiding it (a delete marker), which is all restic does with its lock files, so backups run as usual; erasing a version needs `deleteFiles`. A server that's taken over can hide its backups but not erase them; the account's key brings them back. Backblaze erases hidden files as the bucket's **lifecycle rule** says, so the backup counts as safe only when the bucket keeps hidden files for at least 30 days, or for good (`b2.Client.KeepsHidden`, read with the account's key and cached for an hour; the setup log and the card say what it is). The controller's prune, with the account's key, hides too: pruned space is freed only when the lifecycle rule erases it, so 30 days is also how long pruned data is paid for. Roostack reads the rule and never changes the bucket. Considered: setting the rule for the Owner, which would need `writeBuckets` and change a bucket they own; not chosen (Owner, 2026-10-16). Considered: keeping `deleteFiles` (restic needs to remove its locks); not needed, as above, and verified on the fake and then on a real B2 bucket (docs/ASSUMPTIONS.md N1–N6). A server can also overwrite files there (new versions); recovering from a taken-over server means rolling its folder back with the account's key (N4), which the backup's Manage does since 2026-10-17 ("Rolling back", below). Keys made on Backblaze's website can't make keys, so in practice the Owner needs one from Backblaze's command-line tool (N6). **Saying so — as built (2026-10-16):** a B2 backup whose server holds the account's key (`Access.B2` with `CanDelete`) says why on its card ("…it uses the account's key, because the key Roostack was given can't make a key for each server. Give Roostack one that can…"; reworded 2026-10-17), links to Change the key (below), and under "Tell me more" gives the commands, `b2 account authorize` then `b2 key create roostack listBuckets,listFiles,readFiles,writeFiles,deleteFiles,writeKeys,deleteKeys,listKeys`, each in a copy box, with what follows (the key reaches every bucket, as Backblaze won't limit a key that makes keys to one bucket; only the controller keeps it; delete the old key). The plan's ransomware suggestion then points to that card rather than suggesting Backblaze. The "Online storage" form says the same once the endpoint is Backblaze's (Alpine, the same test as `b2.IsB2`); considered: always showing it folded, not chosen as noise for other providers (Owner, 2026-10-16).
  - **Can delete:** online storage other than B2 (the server holds the account's key), B2 when the account's key can't make keys, drives and folders on the server, and what a server's setup wizard chose. A credential that can't delete at all doesn't work instead: restic can't remove its locks, a backup longer than about 22 minutes is stopped when its lock refresh fails, and the leftover locks block `check` and pruning (docs/ASSUMPTIONS.md N1). So for generic S3 the way to protection is a versioned bucket with a lifecycle rule and a key without `s3:DeleteObjectVersion`, which Roostack checks since 2026-10-17 (below), and then counts as "can hide, not erase".
- **Removing a server — as built (2026-10-16).** Besides its network access and certificate, the controller deletes its Backblaze keys and forgets backups stored *on its disk* (its own and other servers' main backups and copies: nothing can reach them now, and a change of recovery key would otherwise wait for them for ever; other servers are told to stop copying there, and the log says which main backups need a new place). *Since 2026-10-17* such a server is also told at once: the controller records the lost main backup (`lost_backups`: the server, the removed server's name, when) until that server has a new main backup, and meanwhile its plan says so in a notice with "Choose a new place" (opening the chooser for the main backup), and "needs attention" says the same instead of each nightly failure there. Its copies carry on. Considered: telling the server to stop backing up to the lost place; not chosen, as the main backup isn't optional and "backups aren't set up" would hide the reason. Its own backups elsewhere stay recorded: the recovery key still reads and prunes them, and a key change reaches them. The removed server's log and the Servers page say which **shared credentials** it still holds (`SharedCredentials`): an online storage account's key (usable from anywhere: change it) and a friend's lab's storage password (reached only through the lab's network, which it has left). The page says to give Roostack a new key for the account (below) and then delete the old one. Review finding M22 (2026-10-16).
- **A new key for an online storage account — as built (2026-10-16).** Under **Manage** on any backup at an S3 or B2 account, "Change the key for *account*…" takes a new key (`ChangeS3Key`, from any server's Backups page, Owner only). Roostack checks it first, so a typo changes nothing: on B2 it must sign in and reach the bucket (`b2.Client.CanMakeKeys`, which also says whether it has `writeKeys`), and with any provider it must open a repository already there (`restic key list`), since the controller prunes with it. Then the account's record changes, and in the background (a log on each card at that account) every server backing up there gets new credentials, the controller last (its Roostack restarts): on B2 with a key that can make keys, a key of its own limited to its folder (`scopedB2Key`; a server that has one keeps it); otherwise the new key itself. A main backup is handed over with `SetBackupDestination`, a copy with `SetBackupCopies`; the server's repository key stays. A server that can't be reached keeps the old key: the log says so, the key made for it is deleted again, and giving the same key again finishes the job. The log ends by saying the old key can now be deleted with the provider; Roostack never deletes the account's keys. Considered: a settings page listing the accounts; not chosen (Owner, 2026-10-16): the backup's card is where the warning is, and no new page is needed. Also covers the B2 account whose key couldn't make keys: a new key that can moves every server onto its own key.
- **Checking an S3 bucket — as built (2026-10-17).** Other than on Backblaze, every server at an account has its key, so whether a taken-over server can destroy its backups there depends on the bucket and the key's permissions, which Roostack can't read directly. So it checks (`S3Check`, `internal/manager/s3check.go`, over a small S3 client of its own, `internal/s3api`, signed with `awssig`): the bucket's versioning (`GetBucketVersioning`); then a **probe**, a small file `roostack-check` in the lab's folder (`<folder>/roostack/<lab id>/`), written, deleted by name (a delete marker) and then its old version erased (`DeleteObject` with `versionId`), which a safe key is refused (`AccessDenied`); then the lifecycle rule (`GetBucketLifecycleConfiguration`: the shortest enabled `NoncurrentVersionExpiration` reaching the lab's folder; none is "for good"; rules for tagged objects don't count, as restic tags nothing; a key not allowed to read it is "not known"). A bucket that keeps versions with a key that can't erase them is `Access.HidesOnly` with the days as `KeepsHidden`, so the same 30-day rule as Backblaze decides "safe from ransomware"; the probe's versions stay until the lifecycle rule erases them, like a server's. The result is saved (`state/s3-checks.json`, by endpoint, bucket, folder and key ID, so a new key is checked again) for 8 days (an hour after a failure); it's checked again when a backup is added there, when the key changes, and weekly with the prune, each saying the result in its log, and the Backups page reads the saved one (checking only when there's none). Considered: asking the provider's IAM (each provider differs, and many have none); trusting the Owner's word (a tick box can't be checked); making scoped keys per server on AWS, MinIO or Wasabi (session policies, as Roostack Cloud does): left for later (TASKS), as it needs each provider's own API. Object Lock was considered as another way to count as safe and not chosen for now (Owner, 2026-10-17).
- **Rolling back — as built (2026-10-17).** A server that's taken over can hide its backups at storage that keeps versions, and overwrite their files with new versions, but not erase what was there (N4). Under **Manage** on any backup whose storage keeps old versions (`Access.Versioned`: Backblaze always, or a bucket the check found versioned), "Bring back what was hidden or changed…" takes a date and a time (two fields: Chrome's single date-and-time field is too wide for a phone at that depth) and **checks first** what going back to then changes (`CheckRollback`; the result is shown above the button, and the details in a log): every version in the server's folder is listed (`ListObjectVersions`, over the S3 API for Backblaze too; versions are gathered by file and sorted by time, as Backblaze lists delete markers apart from versions, N9) and each file is put back as it was then. A file hidden or overwritten since gets its version from then **copied back on top** (`CopyObject` from that `versionId`); a file added since is **hidden** (deleted by name); restic's `locks/` are left alone. The check says it in restic's terms people know ("1 backup (a snapshot) and 1 other file hidden since then come back", "The repository's config file overwritten since then is put back as it was", "3 backups (snapshots) added since then are hidden"), and offers "Go back to *time*" with a confirmation; it's accepted only for the time just checked, within the hour. It runs as a **maintenance job** (`RollBack`) with the account's key, working out the changes again (backups may have run since the check), bringing things back config first and snapshots last, and hiding the other way round, so nothing reading the backups meanwhile sees a snapshot without its data. Then `restic unlock` (stale locks only) and `restic check`, and the log says how many backups are there and the newest. The Owner's request is audited. **Nothing is ever erased**, so it works with a key that can't erase versions (the safe S3 setup above) and can be undone by going back to a time just before it; the versions it leaves are erased by the bucket's lifecycle rule like any. A file whose newest version already matches the one from then (by ETag and size) is left, so going back to the same time again changes nothing. The page says to remove a server that was taken over first. Chosen with the Owner (2026-10-17) over Backblaze's own API erasing every version since that time (exact, nothing left over, but irreversible, Backblaze only, and needing a key that can erase). Roostack Cloud's own rollback is Cloud's (its repository). **Tried on a real Backblaze bucket (2026-10-17, N9):** a snapshot hidden and `config` overwritten with the server's own key came back, and `restic check` passed.

- **Junk in a repository — as built (2026-10-17, review M24).** Append-only stores stop deletes and overwrites, not additions (docs/ASSUMPTIONS.md O1–O3): a server that's taken over, or at a friend's lab before 2026-10-17 any server of the guest lab (M21, below), can add files restic can't read. A junk lock, or a junk key sorting before the real one, stops every command on the repository; a junk index or snapshot stops backups, prunes and restores (O4). The controller looks for them (`backup.FindJunk`, `manager.JunkJob`) in every repository it made: weekly, just before the prune, and within the hour after a server's backup or copy fails with an error junk causes (`backup.LooksLikeJunk`; at most every 6 hours per repository). A key file is junk when restic couldn't try it (not a restic key, or scrypt parameters restic refuses); lock, snapshot and index files are junk when `restic cat` fails restic's authentication check (`ciphertext verification failed`), twice, a minute apart. That check fails only for a file not made with the repository's key; network errors, files still being uploaded and files rotted on disk fail differently and are left. `data/` isn't looked at: a junk pack does no harm, and the next prune deletes it. Junk is **removed at once, without asking**, where the controller has its own access: through the admin access on a server's backup store or at a friend's lab (a `DELETE`), or with `rm` in a folder on the controller (launched as restic is). With junk keys removed it looks again, as they hide the rest from restic. Each finding is logged (the controller's journal and the activity log: path, size, reason) and recorded until the Owner clears it: Needs attention says what was removed from whose backups and who could have written there (the server, and whoever holds the files: the storing server, the friend's lab, the provider's key holders), with **Details** (`/backups/junk`, Owner only). On online storage and Roostack Cloud the controller has no such access: the item is a problem, and the page lists the files to delete with the provider's tools. **Decided with the Owner (2026-10-17):** automatic rather than the Owner's click, because junk is of no use to restic and leaving it stops backups until someone acts; and no copies are kept, because a file that fails the authentication check can't be recovered by anyone, so a copy would only guard against a bug in Roostack's own check. Considered: a click per finding; locks automatic and the rest on a click; keeping copies up to a size for 30 days. A key that restic can try but whose scrypt `p` is huge isn't junk, yet makes every open slow (O5): see "Key hints", below.
- **Key hints — as built (2026-10-17, ASSUMPTIONS O5, O6).** Every restic command Roostack runs says which key file to try (`RESTIC_KEY_HINT`), so a slow key someone added is never read, by the server backing up or the controller pruning. Each server keeps the IDs in `state/backup-key-hints.json` (`backup.KeyHints`), by repository address and key (a hash of both: the file names no key), and records them as keys are made: the recovery key's when the controller makes a repository (just after `restic init`, when no one can have added another), a server's own key's when the controller adds it (`restic key add` says its ID), which then travels with the server's backup settings (`key_hint` in `node.BackupDestination` and `BackupCopy`), and the new recovery key's during a change of key. A repository made before this, or one whose ID wasn't handed over, has its ID asked of restic once (`key list`, the one open that can still be slow), at most hourly while that fails. A wrong hint costs nothing: restic then tries every key. Considered: a column per key ID in the controller's `backup_targets` and copies, passed around explicitly; rejected as it would have to follow every place a key or address changes (a change of recovery key, a promoted copy, a new account key), where keying the hints by address and key follows them by itself. **A full-lab restore (as built 2026-10-18, ASSUMPTIONS O13):** a fresh server has no hints, and the restored state's are from its last backup, for repositories that may have moved since (a drive mounted elsewhere). So the restore keeps its own, in `state/restore-key-hints.json` (never backed up; removed when the restore finishes or the first Owner is created instead): the search asks restic once per repository it finds which key the recovery key opens (`Repo.LearnKey`, a `key list`), and stops there if that fails (another lab's backups), so the failure isn't paid for twice. Every later command of the search and the restore gives that hint. Once the restored state is back, these hints are added to its `backup-key-hints.json`, over any it had for the same repository and key, so the restored lab's first backups and prunes are fast too. Repositories the search didn't see (an off-site copy) use the hints that came back with the state, or ask restic once as above. Considered: restic's `--key-hint` from the restored state's file (it can't be read before the repository is opened); passing the key IDs through `labrestore.Found` (hints keyed by address and key already follow the repository into the restored lab).

**A server can be a backup target for other labs (friends and family).**
- The Owner of the storage server creates a **storage invite** (like a join code) with a **quota**; the other lab's Owner adds it as a provider. Each invited lab gets its **own rest-server repository area with its own size limit**, reached over a WireGuard link that allows **only** that port (it isn't a server in the host's lab and can reach nothing else).
- **A user per server of the guest lab — as built (2026-10-17, review M21).** Until then every server of a guest lab shared one store user, so with `--private-repos` keeping users apart but not servers, a server that was taken over could add junk to its siblings' repositories (stopping their backups: "Junk in a repository" above) and read their ciphertext (docs/ASSUMPTIONS.md O3). Now the invite carries only the guest lab's user name (`g<id>`, its admin access's, which can delete, for its controller's prune) and admin password; no store password. When a server's backups are first set up at the friend's lab, the guest's controller makes it a password (kept in the provider's record, like the admin password) and gives the host its bcrypt hash over the guest API (`PUT /v1/guest/users/<server id>`, with the admin password; again on every setup, in case the host lost it). The host keeps it (`storage_guest_users`) and writes one line per server into that guest's store password file (`.htpasswd`; rest-server reloads it within 30 seconds, ASSUMPTIONS O8). The server backs up through its controller's proxy, as before, but as itself, to `/<server id>/<lab id>`. Removing a server from the guest lab removes its user at the host (`DELETE /v1/guest/users/<server id>`), so it no longer appears among what a removed server keeps. The host checks every name and hash (a plain name, a bcrypt hash: nothing that could add a line) and allows 64 users per guest lab; a removed guest can't add any. Servers that join the guest lab later get theirs the same way, when they first choose that place. Labs linked before keep the shared password for backups set up then (it's still in their record and the host's file); choosing the place again moves a server to its own user (in a new repository). Considered: a proxy at the guest's controller allowing each server only its own path (by its address on the lab network): one more thing that has to be right, where the host's rest-server already separates users. Considered: a way to change these passwords (Manage → "Change the passwords at …"); not built (Owner, 2026-10-17): the store is reachable only over the WireGuard link from the guest's controller, so a leaked password is of no use outside the lab, and a server's own password only adds to its own repository, which it could do anyway.
- The host only ever sees encrypted data and sizes (zero-knowledge, like §10.8's backup targets).
- **Invite form — as built (2026-10-03):** the address guests connect to is filled in when Roostack knows it (on a lab on the internet, the server's public address; at home, the home's public address once DNS records know it), with "Use a different address" to change it; otherwise it's typed. The form says how much more the server can offer (free space, less what other labs have been given but not used yet, less 10% headroom), starts at 50 GB or that much if it's less, and says, as the number changes, how much free space that leaves for the lab's own services and backups. The page opens with the offering server's disk (the same block as Settings → Servers: free and total, a bar with the unused promised space, what uses it, warnings) and how much more other labs can be given. A new invite is shown in place of the form, with a Copy button, until "Make another invite". On a lab on the internet the help is about the provider's firewall rather than port forwarding.
- **Storage management:** the host sets and can change each guest's quota; Roostack keeps free-space headroom on the disk and refuses quotas that don't fit (new invites and quota changes); both sides see usage (the guest: "8.2 of 50 GB used at Mum's"); warnings at 80% and when a backup fails for lack of space; the host can remove a guest (their data is deleted after a grace period, with notice).

**Restoring across the lab — Locked (2026-10-04)**

Until now each server's backups could only be restored onto that server, and a full-lab restore brought back only the controller: moving two servers onto one new server, or rebuilding after losing a node, had no path. Decided:

- **A repository per server stays.** Considered: one repository for the whole lab. Rejected: a restic key opens a whole repository, so every server would hold a key that decrypts every other server's data; servers would contend for its lock; and the per-server append-only credentials (ransomware protection) would go. It would only gain deduplication across servers, which matters little (services rarely share data).
- **One snapshot per service.** Each backup makes the server's own snapshot (`roostack`, `server`: Roostack's state and the Podman secrets store) and then one per service (`roostack`, `service=<name>`: its data folders and its secrets, saved to `backup-secrets/<name>.json` in the state folder for the upload and removed after). So "which backups have Photos" is a tag query in any repository, and a service's backup carries what it needs to run on any server, even after its own server is gone. Retention groups by tags (`--group-by host,tags`), so each service keeps its own 7 daily, 4 weekly and 6 monthly backups: a service that's no longer backed up keeps its last ones rather than losing them to others' newer backups. Considered: one snapshot per server, finding a service by its paths (fewer snapshots, but restore stays tied to the folder layout).
- **One restore page per service, for the whole lab.** "Restore Photos" lists its backups from every server's repository and every copy, through the controller (which opens them all with the recovery key). The newest is chosen for you and said in one line ("Last night's backup, 03:00 (read from USB drive BACKUP)"); the others are under "Choose a different backup", for when the newest is already broken. It goes onto the server the service runs on, or another one chosen there. Restoring onto another server reuses moving through a backup.
  - **The Backups page is the lab's (2026-10-04):** with several servers, "Each server's backups" (the server switcher, one line per server showing how its backups are doing, then that server's status, latest run and plan) and "Your whole lab" (restoring every service, by the server it runs on; storage at other labs; the recovery key), the same whichever server is chosen. Until then the whole page was one server's: a service could only be restored from its own server's page, once that server had backups, and the recovery key showed only on the controller's.
  - **Moments, not places (2026-10-04):** every backup is in several places (the main backup and each copy), so the list shows each backup moment once, grouped as the clean-up thins them out (this week, this month, older: about 17 at most), and the place to read it from is chosen for you (the main backup, usually at home and quickest), with "Read it from" listing only the places that have that moment, for when the main one can't be read. Every snapshot of one run is tagged `run=<time>` so copies group exactly; older untagged ones group by server, within an hour. Considered: a flat list of every snapshot (about 50 rows with two copies, the same night three times), and filters (unneeded for a list this short).
- **Restoring a whole lab onto fewer servers.** After the controller is restored, services that were on servers that aren't there show as a plan: tick which come back onto this server (all, when they fit in its free space; otherwise none), with sizes. Servers still running reconnect by themselves, so nothing is assumed lost until the Owner says so. Services not chosen stay **waiting to be restored** ("Waiting to be restored, from nas", with its latest backup's size), each restorable later onto any server (one added later included) with the normal restore. Considered: placing them automatically (simple, but may fill a disk or put things where the Owner doesn't want them).
- **Backups of services waiting to be restored are kept.** Retention never ages them out (above). "Needs attention" says how many are waiting (information, not a problem: not in the problems email). Only "Remove and delete its backups…" on the service's page deletes them. Once no service from a lost server is waiting, the server leaves the lab; its backups stay (the recovery key still reads them).
- **Gone for good? — as built (2026-10-11):** the controller records when it first sees a server not answering (kept across restarts, forgotten when it answers). Settings → Servers says "Not connected since …", and a server without services offers "Remove it from the lab". After three days unreached, "Needs attention" stops saying only "can't reach" and says plainly "Roostack hasn't reached *server* since …. If it's gone for good (reinstalled, or switched off for good), remove it from the lab", or, if it had services, that they can come back from their backups on another server (the page below). Found with a reinstalled test VM that stayed in a lab for days. Considered: WireGuard's last handshake as the date (lost when the controller restarts).
- **As built (2026-10-04):** Settings → Servers shows a server that can't be reached as "Not connected" and offers "*server* is gone: restore its services…" (for any server that can't be reached, not only after a full restore: a node dying in a running lab is the same case). That page lists its services with the newest backup that can still be read and its size (from the snapshot's summary), all ticked when they fit in 90% of the chosen server's free space (otherwise none), one server for the whole batch; confirming "*server* isn't coming back" marks every one of its services `waiting` (their `host` still names it, so its backup records stay and it's in no assignment, even if it comes back), then the controller restores the ticked ones one after another (the restore through the controller above). Restoring the last waiting service, or removing it, takes the server out of the lab; removing it by hand is refused while services wait on its backups. "Remove *service* and delete its backups…" lists every repository first and deletes nothing if one can't be read (its backups there would stay unseen), then forgets every snapshot tagged with the service.

**Moving a service between servers: two ways, the UI suggests one.**
- **Copy directly** (quick, for smaller data or servers on the same network): copy the data to the new server over Roostack's network *while the service keeps running*, then stop it, copy what changed, start it on the new server and switch its web address. Downtime is only the final pass. The old copy is kept until the Owner confirms.
- **Through a backup** (large data, slow or unreliable links, or servers far apart): back up on the old server, then restore on the new one from the old server's repository. The controller adds a temporary key to that repository for the new server and removes it afterwards. Resumable, and reuses restore (§6.9).
- The move page shows the data size and suggests a way (through a backup above 10 GB, when the old server's backups are set up through Roostack).
- As built (2026-09-28): data travels **through the controller** in both ways (it is the hub every server already connects through); in the backup way the controller reads the old server's repository itself with the recovery key (`restic dump`), so no repository keys or store passwords are shared between servers. The service's Podman secrets are copied from the old server (or its backup). *Since 2026-10-16* only those the service's generated files name are taken, on moves and restores alike; anything else the old server or its backup offers is left out, logged and said in the activity, so a compromised server can't plant another service's password, or one of Roostack's own, where the service lands (security review M20). Data already on the new server is kept aside (`<dir>.before-move-<time>`), and the old server's copy is renamed (`<dir>.moved-to-<server>-<time>`), both kept until the Owner deletes them. *Since 2026-10-17* the new server checks each tar stream before GNU tar unpacks it into `<dir>.incoming` (`node.checkStream`): a member under a symbolic link (sent earlier, or left by an earlier pass of the copy, which tar follows: ASSUMPTIONS L19), a folder in place of a link, a hard link through one, or a name with `..` stops the copy with an error saying which file, so a taken-over old server, or a forged backup, can't write outside that folder. Links themselves are allowed (services' data has them), as tar never follows those within one stream.

**Decisions (2026-09-27)**
1. ~~Provider credentials~~ **Decided (2026-09-27): scoped where cheap and stable, shared elsewhere.** rest-server gets a user per server (`--private-repos`), on a server's disk and, since 2026-10-17, at a friend's lab; B2 gets an application key per server limited to its folder (plain HTTP API, deleted when the server is removed), and since 2026-10-16 without `deleteFiles` ("What a server can delete" above). Other providers use the shared credentials, and the server's Backups page says so ("Every server uses this account's key, which can delete what's there"). More providers get scoped keys one at a time when there's a need.
2. ~~Pruning~~ **Decided (2026-09-27):** the controller runs `restic forget/prune` weekly with the recovery key, over a separate non-append-only credential. For friends' storage, the guest lab's controller does it. **Stale locks first — as built (2026-10-17):** before each repository's prune the controller runs `restic unlock` (`backup.Repo.Unlock`), which removes only stale locks (a restic on the same host that's no longer running, or a lock not refreshed for 30 minutes), so a running backup's lock stays and the prune waits for it as before. Without it a backup that crashed or was killed blocked every prune and check of that repository for good: restic doesn't skip stale locks when it locks a repository (docs/ASSUMPTIONS.md N1). The log says how many it cleared. Considered: `unlock --remove-all`, which would also remove a running backup's lock; not chosen.
3. ~~rest-server as a dependency~~ **Decided (2026-09-27):** run it as a pinned container (`docker.io/restic/rest-server`), like Caddy: containers where possible make other distributions easier to support later.
4. ~~Guest link~~ **Decided (2026-09-27): a separate WireGuard interface for guests** (`roostack-guests`, its own address range, e.g. `100.97.0.0/24`, and its own UDP port, default 51821). The firewall drops everything arriving on it except the rest-server port; the lab API and web routes are never reachable from it. Turning "storage for others" off takes the interface down. *As built (2026-10-16, review H3: until then only the accepts existed, and the drop didn't):* the guest API and each guest's own store pair, from that guest's address only, then a drop (§6.10 item 1). The guest API (port 8472, on the host's address on the link) answers joining, usage, and since 2026-10-17 the guest's servers' store users (§10.10).
   - **Protecting the WireGuard ports — Locked (2026-10-03):** UDP 51820 and 51821 are open only while used (a lab network with other servers; storage for others). WireGuard answers nothing without a key (a scan can't tell the port is open), lets in only the peers' keys Roostack added (join codes and invites add a one-time key, useless without their expiring token), has nothing to guess, and has cookies against handshake floods. On top, Roostack's firewall drops a source's new handshakes beyond 5 a second (burst 20); peers whose handshake was answered pass through conntrack first. Checked on VM1: 500 fake handshakes in a second, 25 reached WireGuard, and VM2's link from the same address kept working. Not CrowdSec: WireGuard logs no failed attempts for it to read, and blocking shared addresses (CGNAT, mobile) could silently cut off a friend's backups; a host-wide firewall bouncer was considered and not chosen.
   - **Joining from the first-run page — as built (2026-10-03):** a fresh server's first-run page asks for the setup code first (remembered for that browser for 30 minutes, and checked again at the end), then "What's this server for?" with nothing chosen: a new lab, add it to a lab you already have, or restore a lab from its backups. Joining takes the join code and a name (the hostname by default), does what `roostack node join` does from inside Roostack (the agent sets up WireGuard), and Roostack restarts as part of the lab; the page says where to manage it (join codes now carry the lab's name and `roost.<domain>`). A failure says why and is undone (the link and anything saved for the lab), so it can be retried. Joining gives up after 20 seconds without a WireGuard handshake, as storage for others does. The lab's "Add a server" shows the code to paste first, and the command under it. A server that's part of a lab has no UI of its own, so its address now serves one page: which lab it belongs to, and a link to manage it there (the lab's name and address are kept from the join code). Tried end to end on 2026-10-03 (a fresh VM joining VM1's lab from its page): a wrong setup code, a code to nowhere (refused after 20 seconds and undone), then a real join; it showed that Roostack didn't restart afterwards (restarts wait for the setup wizard, which a joining server never finishes), now fixed. Considered: keeping joining on the command line only (the one step that needed a terminal), and preselecting "A new lab" (most installs, but too easy to click past).
   - **The address — as built (2026-10-03):** the join code and the storage invite carry the address the other side connects to, chosen each time (it depends on where the other side is) from what Roostack knows: this server's home-network addresses (joining only; one per real network interface), a name from the domain (`link.<domain>`), the public address (the home's, or the server's on a lab on the internet), or another address (a VPN, a router forwarding another outside port, another dynamic DNS name, a test VM behind QEMU's NAT). The last one used is suggested; otherwise the home-network address for joining at home, else the name. **`link.<domain>`:** at home Roostack keeps it pointing at the home's public address (it changes), but only once someone first chooses it, so a lab that never needs it doesn't publish its home's address; it doesn't wait for CrowdSec (it isn't a website); on a lab on the internet the wildcard covers it. `link` is reserved: no service can use it. Considered: a lab-wide setting (but the right address depends on where each new server or lab is), and keeping a free-text field (error-prone, kept as "another address").
   - **Direct links between servers — as built (2026-10-04):** servers dial only the controller, so a server backing up to another server's disk went through it (and before this, couldn't at all: the hub didn't forward). Now, where one of the two can reach the other, they get a WireGuard link of their own, carrying only their traffic: the controller hands each its links in its assignment (peers marked `# roostack link` in its interface file, so its link to the controller is never touched; a server dialled directly listens on UDP 51820, opened in its firewall). Where a server is reached: an address the Owner typed on Settings → Servers ("Direct links", host:port), else its home-network address when both are at home (never one the other has too: VMs behind one NAT), else the address it connects to the controller from when it's somewhere else (a server on the internet). A link with no WireGuard handshake within 3 minutes is dropped for a day (a new address retries at once), and their backups go through the controller: it forwards only the backup store port between servers (its interface alone forwards; every server's forward chain drops anything else to, from or within Roostack's network). The backup plan says which path a backup to another server's disk takes. Considered: always through the controller (simple, but twice the controller's traffic, and its upload at home); a full mesh with hole punching (only when a real case needs it, as before).
   - **UDP and port forwarding:** a guest must be able to reach the host's port from the internet. Roostack opens the UDP port in its own firewall, then **explains port forwarding** on the storage page: which port (UDP, not TCP), to which server (its home-network address), a short how-to with common router names, and a **reachability check** (the guest's first connection, or a check from Roostack Cloud later) so the Owner knows it worked. As built (2026-10-03): the guest gives up after 20 seconds without a WireGuard handshake (the port can't be reached; waiting longer doesn't help) and says so, naming the provider's firewall and the router; a link that's up but unanswered is reported separately. The button shows "Connecting…" meanwhile. The same applies to the servers port (51820) when a server outside the home joins; the join page gets the same explanation. A Roostack Cloud relay can later remove the need for port forwarding (§10.5).

- **Storage for others on any server (2026-09-28):** the Owner chooses which server offers it (e.g. one with a big disk; the controller by default), only while no other lab stores anything. That server runs the guests' WireGuard link (`roostack-guests`, UDP 51821), their stores, and holds their data; the controller keeps the records and answers guests' requests (joining, usage), which that server forwards to it over Roostack's network (only from the server offering storage). A removed guest lab keeps its link for 30 days, hears about the removal (its Backups page and "needs attention" show when its backups there are deleted), and its data is then deleted (hourly check), or sooner if the host chooses.
